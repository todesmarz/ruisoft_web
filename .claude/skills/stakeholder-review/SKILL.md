# ステークホルダーレビュー 業務フロースキル

このスキルは成果物の **ステークホルダー視点でのレビュー実行手順を定義** する。
「何を不整合とするか」「何を不明点として質問するか」「代替案をどこまで網羅するか」の価値判断基準は `self-review` エージェントの職種定義を準用すること。

本スキルは `self-review` と補完関係にある。
- `self-review`：成果物自体の品質（不整合・誤字・わかりやすさ・ファクト・より良い方法・目的達成性）
- `stakeholder-review`：ステークホルダー視点での目的整合性・前工程整合性・関心事カバレッジ・不明点質問・代替案網羅

両者は併用推奨。本スキル単独でも実行可能だが、品質面の担保が必要な場合は `self-review` を直後に実行すること。

---

## 適用する標準手法・フレームワーク

本スキルは以下の確立された手法を組み合わせて実行する。各 Step で明示的に参照し、根拠を示すこと。

| 手法 | 由来 | 適用 Step | 役割 |
|---|---|---|---|
| **ステークホルダー・サリエンスモデル** | Mitchell, Agle & Wood (1997) | Step 1 | ステークホルダーを力・正当性・緊急性の3属性で分類し優先順位を付ける |
| **デザインレビュー** | IEEE 1028 | Step 1-8 | 設計・成果物をステークホルダー視点で静的検証する標準レビュー手法 |
| **要求妥当性確認** | REBoK | Step 3, 4 | 要求がステークホルダーの真のニーズを満たすか検証する活動 |
| **トレーサビリティ** | Vモデル / IEEE 830 | Step 4 | 要件→設計→実装→テストの追跡可能性。前工程との整合を担保 |
| **Vモデル** | V-Model XT | Step 4 | 上流工程と下流工程の対応関係。各成果物が上位成果物を満たすか検証 |
| **アクティブリスニング** | カール・ロジャーズ | Step 6 | 不明点を「確認」として受け手側から問い直す姿勢 |
| **5W1H分析** | ジャーナリズム / 問題解決手法 | Step 6 | 不明点を Who/What/When/Where/Why/How で構造化して洗い出す |
| **前提・暗黙知の明示化** | Nonaka & Takeuchi | Step 6 | 暗黙の前提を形式知として言語化し確認対象にする |
| **トレードオフ分析** | システム工学 | Step 7 | 代替案を複数軸で比較し根拠を明示する |
| **SCAMPER法** | Bob Eberle | Step 7 | 代替案を7視点（代替/結合/適応/修正/他用途/削除/逆転）で網羅的に発想 |
| **デビルズアドボカート** | 反証思考 | Step 7 | あえて反対立場から代替案を提示し前提を疑う |
| **ルーブリック評価** | 教育評価法 | Step 8 | 4段階評価で整合性の重大度を分類 |

### ステークホルダーレビューの位置付け

```
前工程成果物（要件定義/設計/企画/依頼文）
        │
        ▼
   成果物（設計書/テスト設計/記事/コード）
        │
        ▼  ┌─ Step 1: ステークホルダーと目的の把握
        │  ├─ Step 2: 前工程資料の収集とトレーサビリティ確認
        │  ├─ Step 3: 目的整合性の検証
        │  ├─ Step 4: 前工程との整合性検証（トレーサビリティ）
        │  ├─ Step 5: ステークホルダー関心事のカバレッジ確認
        │  ├─ Step 6: 不明点・前提の洗い出しと質問
        │  ├─ Step 7: 代替案の網羅的提案
        │  └─ Step 8: レビュー報告書の作成（必須）
        ▼
   修正後の再レビュー（Step 9）
```

## Step 1: ステークホルダーと目的の把握

レビュー対象の成果物を読み込み、**誰が何のためにこの成果物を求めているか** を明確にする。ステークホルダーが不明だと整合性判断の基準が定まらないため最重要 Step。

### 1-1. ステークホルダーの特定

ステークホルダー・サリエンスモデル（Mitchell et al., 1997）に基づき、関与者を3属性で分類する。

| 属性 | 意味 | 判断材料 |
|---|---|---|
| **力（Power）** | 成果物の承認・却下・変更強制力を持つ | 発注者・意思決定者・予算保持者 |
| **正当性（Legitimacy）** | 成果物に対する正当な利害関係を持つ | 利用者・法務・セキュリティ・業務部門 |
| **緊急性（Urgency）** | 即時対応が求められる利害を持つ | 期限が迫る受け手・障害影響を受ける者 |

3属性の保有数で優先度を分類する。

| 分類 | 属性数 | 優先度 | 対応 |
|---|---|---|---|
| **決定的ステークホルダー** | 3 | 最優先 | 全ての関心事を必ずカバー |
| **支配的ステークホルダー** | 2（力+正当性） | 高 | 関心事を必ずカバー |
| **危険的ステークホルダー** | 2（力+緊急性） | 高 | 関心事を必ずカバー |
| **依存的ステークホルダー** | 2（正当性+緊急性） | 中 | 関心事を推奨カバー |
| **休眠的ステークホルダー** | 1（力） | 中 | 関心事を確認対象 |
| **裁量的ステークホルダー** | 1（正当性） | 低 | 関心事を検討対象 |
| **要求的ステークホルダー** | 1（緊急性） | 低 | 関心事を検討対象 |

### 1-2. ステークホルダーマップのテンプレート

```
成果物：{ファイル名・タイトル}
種類：  {要件定義書/設計書/テスト設計/ブログ記事/コード/...}

ステークホルダー一覧：
| ID | ステークホルダー | 役割 | 力 | 正当性 | 緊急性 | 分類 | 関心事 |
|---|---|---|---|---|---|---|---|
| SH-001 | 発注者 | 意思決定・承認 | ○ | ○ | ○ | 決定的 | 〇〇を決定できること |
| SH-002 | エンドユーザー | 利用者 | × | ○ | ○ | 依存的 | 〇〇が使いやすいこと |
| ... | | | | | | | |
```

### 1-3. 目的と成功基準の明確化

各ステークホルダーが「成果物を受け取った後に何をできるか・何を決定できるか」を成功基準として明示する。

```
目的：{ステークホルダーが成果物を読んで〇〇を決定/実行できる}
成功基準：{具体的な達成状態・判定可能な条件}
```

ステークホルダーや目的が読み取れない場合は **不明点リスト** に蓄積し、Step 6 でユーザーに確認する。

## Step 2: 前工程資料の収集とトレーサビリティ確認

成果物がどの前工程資料から派生したかを特定し、**照合の土台** を整える。

### 2-1. 収集対象

| 対象 | 例 | 確認ポイント |
|---|---|---|
| **直前工程の成果物** | 設計書→テスト設計なら設計書、企画→記事なら企画書 | 直前成果物との整合 |
| **依頼文・発注仕様** | ユーザーの元依頼文・発注者の要件・チャット指示 | 依頼の趣旨から逸脱していないか |
| **上流工程すべて** | 要件定義→設計→テストの全上流資料 | 上流からの伝播が正しいか |
| **関連ドキュメント全般** | README・仕様書・過去の類似成果物・規約・ガイドライン | 周辺資料との矛盾がないか |

### 2-2. トレーサビリティマトリクスの作成

成果物の各要素（章・機能・テストケース・節）が、どの前工程資料のどの要素に由来するかを対応表にする。**Vモデルの縦方向整合** を担保する。

```
| 成果物要素 | 前工程資料 | 前工程要素 | 由来 | 状態 |
|---|---|---|---|---|
| §3.2 ログイン機能 | 要件定義書 | FR-005 | 直接派生 | ✓整合 |
| §4.1 パスワード要件 | セキュリティ規約 | §2.1 | 参照 | ✓整合 |
| §5.1 バッチ処理 | （該当なし） | — | 追加 | ⚠要確認 |
```

「該当なし」の要素は **前工程にない追加** であり、Step 6 で必ず確認対象とする。

### 2-3. 収集結果の記録

収集した前工程資料は **前提資料リスト** として報告書に記載する。読み取れなかった資料は不明点リストに蓄積する。

## Step 3: 目的整合性の検証（REBoK 妥当性確認）

Step 1 で定義した目的に対して、成果物が **ステークホルダーの真のニーズを満たすか** を検証する。REBoKの要求妥当性確認活動に相当する。

### 3-1. 目的達成の論理検証

```
目的：「ステークホルダーが〇〇を決定/実行できること」
   ↑
論理：成果物の§X は 〇〇 を提供する → 目的を達成する
   ↑
成果物：§X の記述
```

この論理が全ての目的に対して成立するかを確認する。

### 3-2. 目的からの逸脱検出

| 逸脱パターン | 例 | 対処 |
|---|---|---|
| **スコープ超過** | 依頼にない機能が追加されている | 削除候補・確認候補 |
| **スコープ不足** | 依頼にある要素が成果物にない | 追加必須・確認候補 |
| **目的変質** | 依頼の趣旨が別の目的にすり替わっている | 要再確認 |
| **読者不一致** | 想定読者と実際の記述レベルが合わない | 表現調整 |

### 3-3. ステークホルダー別の目的達成確認

各ステークホルダー（Step 1-2）の関心事に対して、成果物が回答を提供しているか確認する。

```
SH-001（発注者）の関心事「〇〇を決定できる」
  → 成果物§X が〇〇を提供 ✓/✗
  → 根拠：{該当箇所の引用}
```

### 目的整合性チェックリスト
- [ ] 全ステークホルダーの関心事に対する回答が成果物に含まれる
- [ ] 依頼文・発注仕様から逸脱していない
- [ ] スコープ超過・不足がない（ある場合は確認対象）
- [ ] 想定読者と記述レベルが合致する
- [ ] 目的達成の論理が全目的で成立する

## Step 4: 前工程との整合性検証（トレーサビリティ）

Step 2 で作成したトレーサビリティマトリクスに基づき、**前工程資料と矛盾しないか** を検証する。Vモデルの縦方向整合に相当する。

### 4-1. 用語・概念の整合

- 前工程で定義した用語が成果物で同一の意味で使われているか
- 前工程で定義した概念が成果物で別の意味にすり替わっていないか
- 略語の定義が前工程と一致しているか

### 4-2. 数値・仕様の整合

- 前工程で示した数値（応答時間・件数・閾値・優先度）が成果物で同一か
- 前工程で「Must」とした要件が成果物で「Should/Won't」に格下げされていないか
- 前工程で「対象外」としたものが成果物で実装/記述されていないか

### 4-3. 機能・要件のカバレッジ

- 前工程の全機能要件が成果物に対応する記述/実装があるか
- 対応が欠落している場合、意図的除外か漏れかを判定する
- 前工程の非機能要件が成果物で考慮されているか

### 4-4. 論理の伝播

- 前工程の前提が成果物でも前提として扱われているか
- 前工程の制約が成果物で守られているか
- 前工程の判断根拠が成果物で覆されていないか（覆す場合は根拠明示が必要）

### 4-5. 逆方向の整合（成果物→前工程）

- 成果物にのみ存在する要素（前工程にない追加）は、追加根拠が明示されているか
- 成果物で暗黙に追加された前提はないか

### 前工程整合性チェックリスト
- [ ] 用語・概念が前工程と一致する
- [ ] 数値・仕様が前工程と一致する
- [ ] 優先度の格下げがない
- [ ] 対象外のものが混入していない
- [ ] 前工程の全機能要件に対応がある
- [ ] 前工程の非機能要件が考慮されている
- [ ] 前工程の前提・制約が守られている
- [ ] 成果物独自の追加に根拠がある

## Step 5: ステークホルダー関心事のカバレッジ確認

Step 1 で特定したステークホルダー全員の **関心事が成果物でカバーされているか** を検証する。

### 5-1. 関心事マトリクス

```
| ステークホルダー | 関心事 | 成果物での対応 | カバレッジ |
|---|---|---|---|
| SH-001 発注者 | 予算内で完了すること | §6 で実装コスト明示 | ✓ |
| SH-002 エンドユーザー | 使いやすさ | §3 UI設計 | ✓ |
| SH-003 セキュリティ担当 | 認証強度 | （記述なし） | ✗ 要確認 |
```

### 5-2. カバレッジ不足の判定

カバレッジが ✗ の場合、以下を判定する。

| 状態 | 判定 | 対処 |
|---|---|---|
| 意図的除外 | 対象外として明示されている | 報告書に明示 |
| 漏れ | 言及すべきだが漏れている | 必須修正候補 |
| 前工程で未定義 | 前工程に関心事がなく成果物でも未対応 | Step 6 で確認 |

### 5-3. 優先ステークホルダーの重点確認

Step 1 で「決定的」「支配的」「危険的」と分類した優先ステークホルダーの関心事は **必ずカバー** されている必要がある。1件でも未カバーは必須修正候補とする。

### 関心事カバレッジチェックリスト
- [ ] 全ステークホルダーの関心事を列挙した
- [ ] 各関心事の成果物での対応を確認した
- [ ] 未カバー関心事について意図的除外か漏れかを判定した
- [ ] 優先ステークホルダーの関心事は全てカバーされている

## Step 6: 不明点・前提の洗い出しと質問（アクティブリスニング）

**本Stepは本スキルの核心**。ステークホルダー視点で「分からないこと」「確認が必要なこと」「暗黙に前提にしていること」を網羅的に洗い出し、ユーザーに質問する。

### 6-1. 5W1H構造化による不明点抽出

成果物を読んで「ステークホルダーが判断できないこと」を5W1Hで構造化して抽出する。

| 観点 | 問い | 抽出例 |
|---|---|---|
| **Who** | 誰がやるのか・誰が対象か | 「担当者が未定」「対象ユーザーが不明」 |
| **What** | 何をやるのか・何を意味するか | 「〇〇の定義が不明」「要件の範囲が曖昧」 |
| **When** | いつやるのか・いつまでに | 「期限が未定」「時期が不明」 |
| **Where** | どこでやるのか・どこに適用するか | 「適用範囲が不明」「環境が未定」 |
| **Why** | なぜやるのか・なぜその仕様か | 「背景が不明」「判断根拠が不明」 |
| **How** | どうやるのか・どう確認するか | 「手順が未定」「検証方法が不明」 |

### 6-2. 暗黙の前提の明示化

成果物が「言っていないが前提にしていること」を言語化し、確認対象にする。Nonaka & Takeuchi の暗黙知形式知変換に相当する。

| 前提の種類 | 例 |
|---|---|
| 技術前提 | 「〇〇ライブラリが使える」「〇〇環境が利用可能」 |
| 業務前提 | 「担当者が〇〇を知っている」「業務フローが〇〇である」 |
| 制約前提 | 「予算は〇〇以内」「期間は〇〇まで」 |
| スコープ前提 | 「〇〇は対象外」「〇〇は既存システムに依存」 |
| 用語前提 | 「〇〇は△△を意味する」 |

### 6-3. 質問リストの作成

抽出した不明点・前提を **確認可能な質問** に変換してリスト化する。質問は「はい/いいえ」や選択肢で回答可能な形にする。

```
Q-001: [Who] §3.2 の「担当者」は誰を想定していますか？
  選択肢：a) 営業部門 / b) 開発部門 / c) 両方
  背景：担当者によって必要な権限・画面が異なるため

Q-002: [前提] §4.1 は「〇〇ライブラリが利用可能」を前提としていますが、確認済みですか？
  選択肢：a) 利用可能（確認済み）/ b) 未確認（要調査）/ c) 別ライブラリ使用
  背景：利用可否によって実装方針が変わるため
```

### 6-4. 質問の優先度付け

| 優先度 | 意味 | 対応 |
|---|---|---|
| **必須確認** | 回答がないとレビュー判定が不可能 | 即時質問 |
| **推奨確認** | 回答で精度が上がる | 質問推奨 |
| **検討確認** | 将来の改善材料 | 記録のみ |

### 6-5. 質問時の姿勢（アクティブリスニング）

- 確認ではなく **「受け手側から問い直す」** 姿勢を持つ
- ステークホルダーの立場に立って「これで意思決定できるか」を問う
- 成果物の批判ではなく **確認** であることを明示する
- 質問には必ず **背景（なぜ聞くか）** と **選択肢** を添える

### 不明点質問チェックリスト
- [ ] 5W1H全観点で不明点を抽出した
- [ ] 暗黙の前提を網羅的に明示化した
- [ ] 各不明点を確認可能な質問形式に変換した
- [ ] 質問に背景と選択肢を添えた
- [ ] 質問に優先度（必須/推奨/検討）を付与した
- [ ] 優先ステークホルダーに関わる不明点は必須確認にした

## Step 7: 代替案の網羅的提案

ステークホルダー視点で **より良い方法を網羅的に** 提案する。self-review の「より良い方法」観点を拡張し、SCAMPER法とデビルズアドボカートで網羅性を担保する。

### 7-1. SCAMPER法による代替案発想

現在の成果物に対して7視点で代替案を発想する。

| 視点 | 問い | 適用例 |
|---|---|---|
| **S**ubstitute（代替） | 別の手段・技術・構成に置き換えられないか | ライブラリA→B、構成C→D |
| **C**ombine（結合） | 複数の要素を統合できないか | 機能XとYを1画面に統合 |
| **A**dapt（適応） | 別分野の手法を適用できないか | 別プロジェクトの成功パターンを適用 |
| **M**odify/Magnify（修正/拡大） | スケールや特性を変更できないか | 処理をバッチ化・非同期化 |
| **P**ut to other use（他用途） | 別の目的・対象に転用できないか | 社内向けツールを顧客向けに拡張 |
| **E**liminate（削除/簡略化） | 削れる要素はないか | 不要機能の削除、KISS原則 |
| **R**everse/Rearrange（逆転/再配置） | 順序・前提を逆にできないか | プル型→プッシュ型、同期→非同期 |

### 7-2. デビルズアドボカートによる反証案

あえて **反対立場** から成果物を批判し、代替案を提示する。前提を疑うことで盲点を発見する。

```
反論：「本当にこの機能は必要か？」
  → 代替案：機能Xを削除し、既存機能Yで代替する
  → 根拠：Yで同等の要件を満たせる、保守コストが下がる

反論：「この仕様は過剰ではないか？」
  → 代替案：〇〇要件をShouldに格下げし、まずMustのみでリリース
  → 根拠：MVPで早期フィードバックを得る方が価値が高い
```

### 7-3. 代替案の網羅的列挙と比較

思いつく限りの代替案を列挙し、トレードオフ分析で比較する。**網羅性を優先** し、絞り込みはユーザーに委ねる。

#### 代替案提示フォーマット

```
代替案ID: A-001
分類: SCAMPER/Substitute
現状: {現在の記述・実装}
代替案: {より良いと考えられる方法}
根拠: {なぜ代替案が良いか}
影響: {変更による影響・コスト・リスク}
推奨: 必須 / 推奨 / 検討
```

#### 代替案比較マトリクス

```
| ID | 代替案 | 効果 | コスト | リスク | 推奨度 |
|---|---|---|---|---|---|
| A-001 | ライブラリA→B | 高 | 低 | 低 | 推奨 |
| A-002 | 機能X削除 | 中 | 極低 | 中 | 検討 |
| A-003 | 構成を非同期化 | 高 | 高 | 中 | 検討 |
| ... | | | | | |
```

### 7-4. 提案時の姿勢

- **網羅的に列挙** することが本スキルの要件。1-3案で打ち切らないこと。
- 代替案は **批判ではなく提案** として出す。現状の否定ではなく選択肢の拡張。
- トレードオフは **効果・コスト・リスクの3軸** で明示する。
- 推奨度は根拠付きで付与するが、最終判断はユーザーに委ねる。
- ステークホルダー毎の恩恵を明示する（SH-001には〇〇、SH-002には△△の恩恵）。

## Step 9: 修正後の再レビュー

ユーザーがStep 8の報告書に基づいて修正・回答を行った後、**修正が正しく適用されたか・質問回答が反映されたか** を再確認する。

### 9-1. 修正確認
- 各不整合（I-xxx）が是正されたか
- 各質問（Q-xxx）の回答が成果物に反映されたか
- 各前提（P-xxx）が確認済みとなり前提が確定したか
- 修正によって新たな不整合が発生していないか

### 9-2. 回帰チェック
- 修正の影響範囲で前工程との整合が壊れていないか
- 代替案採用によって他のステークホルダー関心事が損なわれていないか
- 前提の確定によって別の前提が影響を受けていないか

### 9-3. 再レビュー結果の記録
Step 8 の報告書 §13 に再レビュー結果を記録し、最終判定を下す。

## 他スキル・他エージェントとの関係

| スキル | 関係 | 使い分け |
|---|---|---|
| **self-review** | 補完関係 | 成果物自体の品質（誤字・ファクト等）は self-review。ステークホルダー視点の整合性・不明点・代替案は本スキル。併用推奨。 |
| **requirements-analyzer** | 上流工程 | 要件定義書の作成が requirements-analyzer、要件定義書のステークホルダーレビューが本スキル。 |
| **system-architect** | 上流工程 | 設計書の作成が system-architect、設計書のステークホルダーレビューが本スキル。 |
| **unit-test-designer** | 下流工程 | テスト設計書の作成が unit-test-designer、テスト設計書のステークホルダーレビューが本スキル。 |
| **blog-director / blog-planner / blog-writer** | 適用先 | ブログ企画・記事のステークホルダー（読者・編集長・発注者）レビューに本スキルを適用。 |

### 典型的な併用パターン

```
[要件定義] requirements-analyzer → [レビュー] stakeholder-review → [設計] system-architect → [レビュー] stakeholder-review → [テスト設計] unit-test-designer → [レビュー] stakeholder-review
```

各工程の成果物を次工程に渡す前に stakeholder-review を挟むことで、前工程との整合性とステークホルダー合意を担保する。
