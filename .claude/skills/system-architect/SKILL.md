# システム設計 業務フロースキル

このスキルはソフトウェア開発における **システム設計（基本設計）の実行手順を定義** する。
「どのアーキテクチャを採用するか」「どこでモジュールを切るか」「非機能要件をどう満たすか」の価値判断基準は `system-architect` エージェントの職種定義を参照すること。

**前提**: 要件定義書（requirements-analyzer 出力）が存在する場合は Step 1 で必ず読み込む。未整備の場合は Step 0 で要件の骨子を確認してから設計に進む。

---

## 適用する標準手法・フレームワーク

本スキルは以下の確立された手法を組み合わせて実行する。各 Step で明示的に参照し、根拠を示すこと。

| 手法 | 由来 | 適用 Step | 役割 |
|---|---|---|---|
| **C4モデル** | Simon Brown | Step 3, 5 | アーキテクチャを Context / Container / Component / Code の4層で描画 |
| **DDD** | Eric Evans | Step 3, 4 | ドメイン駆動設計。ユビキタス言語・境界付けられたコンテキスト・集約でモジュール分割 |
| **クリーンアーキテクチャ** | Robert C. Martin | Step 4 | 依存方向の制御。エンティティ→ユースケース→IFアダプタ→フレームワークの層分離 |
| **12 Factor App** | Heroku | Step 6 | クラウドネイティブ設計原則（設定の外部化・ステートレス・ログのイベント化 等） |
| **ACID / BASE** | DB理論 | Step 5 | トランザクション一貫性の判断基準 |
| **REST / GraphQL / gRPC** | 各種 | Step 5 | APIスタイル選定の判断軸 |
| **CAP定理** | Brewer | Step 5 | 分散システムの整合性 vs 可用性のトレードオフ判断 |
| **ISO/IEC 25010** | SQuaRE | Step 6 | 非機能要件の8品質特性を設計に落とし込む（requirements-analyzer と同じ分類を使用） |
| **STRIDE** | Microsoft | Step 7 | 脅威モデリング。Spoofing/Tampering/Repudiation/Info Disclosure/DoS/Elevation |
| **ADR (Architecture Decision Record)** | Michael Nygard | Step 8 | 設計判断の意思決定記録。後追い可能な根拠を残す |
| **ATAM** | SEI | Step 9 | アーキテクチャ評価。品質属性シナリオで設計の妥当性を検証 |

## Step 0: 要件の確認（要件定義書がない場合）

要件定義書が未整備の場合、以下の最小限の骨子をユーザーに確認する。整備済みの場合は Step 1 へ。

| 確認項目 | 内容 |
|---|---|
| 目的 | 何を達成したいか |
| 利用者 | エンドユーザー / 管理者 / システム間 |
| 主要機能 | Must要件の洗い出し |
| 規模感 | 想定ユーザー数・データ量・トラフィック |
| 制約 | 予算・スケジュール・利用可能技術・運用体制 |

不明点は Step 2 で質問する。requirements-analyzer スキルの適用を推奨する旨をユーザーに伝えること。

---

## Step 1: 要件定義書の読み込みと解釈

要件定義書（requirements-analyzer 出力）を読み込み、設計に必要な情報を抽出する。

| 抽出項目 | 設計への影響 |
|---|---|
| 機能要件（MoSCoW） | モジュール分割の単位・優先実装対象 |
| 非機能要件（ISO 25010） | アーキテクチャ制約・技術選定の判断軸 |
| 制約条件 | 選択肢の絞り込み（言語・インフラ・予算） |
| 受け入れ基準 | 設計の検証基準・テスト戦略の起点 |
| データ要件 | DB設計・IF設計の入力 |

読み込めない項目は **不明点リスト** に蓄積し、Step 2 で質問する。

---

## Step 2: コンテキスト収集と制約の明示化

既存資産・技術的制約を収集し、設計の前提を固める。

### 収集対象
- 既存システムのアーキテクチャ（改修の場合）
- 関連コード・設定ファイル・インフラ構成
- 組織の技術スタック標準・利用可能なマネージドサービス
- セキュリティ・コンプライアンス要件（データ保護・監査・居住地）
- 運用体制（オンコール・SLA・監視の既存基盤）

### 明示化する制約
- **硬い制約**: 変更不可（コンプライアンス・既存システムとのIF・予算上限）
- **柔らかい制約**: 議論可能（技術選定・開発手法・優先順位）

収集結果は **前提条件** として設計書に記載する。

---

## Step 3: アーキテクチャスタイルの選定（C4 Context/Container）

**C4モデルの Context 層 → Container 層** を描き、システム全体像を決定する。

### 3-1. アーキテクチャスタイル候補の評価

要件・制約に対して複数候補を評価し、**トレードオフを明示** して選定する。

| 候補 | 適用条件 | 注意点 |
|---|---|---|
| モノリス | 小規模・単一チーム・MVP | スケール時の限界・デプロイ衝突 |
| マイクロサービス | 大規模・複数チーム・独立デプロイ必要 | 運用複雑度・分散トランザクション |
| モジュラモノリス | 中規模・単一デプロイ・明確な境界 | 境界規律の維持コスト |
| サーバーレス | トラフィック変動大・イベント駆動 | コールドスタート・ベンダーロックイン |
| イベント駆動 | 非同期・疎結合・高スループット | 順序保証・デバッグ難易度 |
| CQRS | 読み書き負荷が非対称 | 整合性維持・実装複雑度 |

**選定基準**: チーム規模・デプロイ頻度・スケール要件・運用能力・ドメイン境界の明確さを総合判断。**過剰設計を避け、要件を満たす最も単純な構成** を選ぶ。

### 3-2. C4 Context 図

システムを外部システム・利用者との関係で描く。

```
[利用者] ──→ [システム] ←──→ [外部システムA]
                              ←──→ [外部システムB]
```

### 3-3. C4 Container 図

システム内部のコンテナ（プロセス単位）を描く。

```
[Web Frontend] ──HTTPS──→ [API Server] ──→ [DB]
                              ↓
                          [Message Queue] ──→ [Worker]
```

## Step 4: モジュール分割（DDD + クリーンアーキテクチャ）

**DDDの境界付けられたコンテキスト（Bounded Context）** でモジュールを切り、**クリーンアーキテクチャ** で依存方向を制御する。

### 4-1. ドメイン分析
- **ユビキタス言語**: 業務用語を統一（要件定義書の用語集と整合）
- **境界付けられたコンテキスト**: 業務領域ごとに境界を設定
- **集約（Aggregate）**: 整合性の単位を定義
- **コンテキストマップ**: コンテキスト間の関係（共有・顧客/供給者・ACL 等）

### 4-2. モジュール構成

各コンテキストをクリーンアーキテクチャの層にマッピングする。

```
┌─────────────────────────────┐
│  Frameworks & Drivers       │ ← Web/DB/MQ/外部API
├─────────────────────────────┤
│  Interface Adapters         │ ← Controller/Gateway/Presenter
├─────────────────────────────┤
│  Use Cases (Application)    │ ← アプリケーションサービス
├─────────────────────────────┤
│  Entities (Domain)          │ ← ビジネスルール・ドメインモデル
└─────────────────────────────┘
       依存方向は常に内側へ
```

### 4-3. 依存関係の原則
- ドメイン層は外部に依存しない（フレームワーク非依存）
- ユースケース層はドメイン層のみに依存
- IFアダプタ層が外部技術を包み隠す
- **依存性の逆転** で外部IFを抽象化

---

## Step 5: データ設計・IF設計

### 5-1. データモデル設計
- **ER図**: エンティティ・リレーション・カーディナリティ
- **正規化判断**: 第3正規化基準。性能要件で非正規化する場合は根拠を明示
- **集約境界**: トランザクション一貫性の範囲を定義
- **データライフサイクル**: 生成・更新・参照・削除・アーカイブ

### 5-2. ストレージ選定
| 種別 | 適用条件 |
|---|---|
| RDB | 強い一貫性・複雑な結合・トランザクション |
| NoSQL（KVS） | 高スループット・単純アクセス・水平スケール |
| ドキュメントDB | スキーマ柔軟性・階層データ |
| 列指向DB | 集計・分析・OLAP |
| 時系列DB | メトリクス・ログ・IoT |
| オブジェクトストレージ | 画像・動画・バックアップ |

**CAP定理** で整合性 vs 可用性の優先を判断し、**ACID / BASE** でトランザクション方針を決定。

### 5-3. API設計
**APIスタイル選定**:
| スタイル | 適用条件 |
|---|---|
| REST | リソース指向・CRUD・標準的 |
| GraphQL | クライアント多様・取得フィールド柔軟 |
| gRPC | 高性能・内部サービス間・ストリーミング |
| メッセージング | 非同期・疎結合・イベント通知 |

**REST設計原則**:
- リソース指向のURI設計（名詞・複数形）
- HTTPメソッドの適切な使用（GET/POST/PUT/PATCH/DELETE）
- ステータスコードの統一（2xx/4xx/5xx）
- バージョニング（URI or ヘッダー）
- ページネーション・フィルタ・ソートの統一
- 冪等性の確保（PUT/DELETE は冪等、POST は要考慮）

### 5-4. IF契約（OpenAPI/Protobuf）
- スキーマ定義をコード生成の起点にする
- 後方互換性の維持方針（追加は可・削除は非推奨・型変更は不可）
- 契約テストの実施方針

## Step 6: 非機能要件の具現化（12 Factor + ISO 25010）

要件定義書の非機能要件を具体的な設計に落とし込む。

| 品質特性 | 設計で考慮する項目 |
|---|---|
| **機能適合性** | 要件カバレッジの確認・受け入れ基準との対応 |
| **信頼性** | 冗長化・フェイルオーバー・リトライ・サーキットブレーカー・デッドレターキュー |
| **性能効率性** | キャッシュ戦略・非同期処理・水平スケール・N+1回避・インデックス設計 |
| **使用性** | レスポンシブ・アクセシビリティ（WCAG）・エラー表示・ローディング状態 |
| **保守性** | モジュール結合度・テスト容易性・ログ/メトリクス・設定外部化 |
| **移植性** | コンテナ化・IaC・クラウド非依存抽象化 |
| **セキュリティ** | 認証認可・暗号化・最小権限・シークレット管理・監査ログ |
| **互換性** | API後方互換・データ移行・ブラウザ対応範囲 |

### 12 Factor App の適用
1. コードベース: バージョン管理された単一コードベース
2. 依存関係: 明示的宣言
3. 設定: 環境変数で外部化
4. バックエンドサービス: アタッチされたリソースとして扱う
5. ビルド/リリース/実行: 段階の分離
6. プロセス: ステートレス
7. ポートバインディング: 自己完結
8. 並行性: プロセス単位のスケール
9. 廃棄容易性: 高速起動・グレースフルシャットダウン
10. 開発/本番の同等性: 環境差の最小化
11. ログ: イベントストリーム
12. 管理プロセス: タスクとしての実行

## Step 7: セキュリティ設計（STRIDE脅威モデリング）

**STRIDE** で各コンポーネントの脅威を抽出し、対策を設計に組み込む。

| 脅威 | 対象 | 対策例 |
|---|---|---|
| **S**poofing（なりすまし） | 認証 | MFA・トークン署名・クライアント証明書 |
| **T**ampering（改ざん） | データ整合性 | HMAC・入力バリデーション・DB制約 |
| **R**epudiation（否認） | 監査 | 監査ログ・タイムスタンプ・署名 |
| **I**nformation Disclosure（情報漏洩） | 機密性 | 暗号化（保管/通信）・最小権限・マスキング |
| **D**enial of Service（DoS） | 可用性 | レートリミット・WAF・オートスケール |
| **E**levation of Privilege（権限昇格） | 認可 | 最小権限・ロール分離・入力検証 |

### セキュリティ設計の基本原則
- **デフォルトで安全**: 安全でない状態を許容しない
- **多層防御**: 単一障壁に依存しない
- **最小権限**: 必要最小限のアクセス権
- **ゼロトラスト**: 暗黙の信頼を置かない
- **シークレット管理**: ソースコードに秘密を書かない（Vault/KMS/Secret Manager）

## Step 8: 設計判断の記録（ADR）

重要な設計判断は **ADR (Architecture Decision Record)** として記録する。

### ADRフォーマット
```markdown
# ADR-XXX: {決定事項のタイトル}

## ステータス
Accepted / Proposed / Deprecated / Superseded

## コンテキスト（背景）
- なぜこの判断が必要か
- どのような制約・要件があるか

## 検討した選択肢
- 選択肢A: ...
- 選択肢B: ...
- 選択肢C: ...

## 決定
{採用した選択肢}

## 理由
- なぜこの選択肢か
- どのトレードオフを受け入れたか

## 結果・影響
- ポジティブな影響:
- ネガティブな影響:
- 後追いすべき事項:
```

### ADRを記録すべき判断
- アーキテクチャスタイルの選定
- 主要技術・フレームワークの選定
- データストアの選定
- APIスタイルの選定
- 外部サービスの導入判断
- セキュリティ上重要な判断

## Step 9: アーキテクチャ評価（ATAM）

**ATAM (Architecture Tradeoff Analysis Method)** で設計の妥当性を検証する。

### 9-1. 品質属性シナリオの策定
各非機能要件について、**環境 + 刺激 + 応答 + 測定値** の形式でシナリオを定義する。

```
【性能】
環境: 平日ピーク時
刺激: ユーザーが一斉にログイン
応答: システムが認証を処理
測定値: 95%ile応答時間 2秒以内

【可用性】
環境: 通常運用中
刺激: DBプライマリがダウン
応答: フェイルオーバー発生
測定値: 30秒以内に復旧、データ損失0件
```

### 9-2. 設計の検証
- 各シナリオに対して設計が応答可能か確認
- ボトルネック・単一障害点（SPOF）の特定
- トレードオフの明示と合意

### 9-3. リスク・感度ポイントの抽出
- **リスク**: 設計上の懸念点
- **感度ポイント**: 特定の品質属性に大きく影響する設計箇所
- **トレードオフ**: 複数の品質属性が相反する箇所

## Step 11: レビューと合意形成

設計書を提示後、以下を確認する。

- [ ] 要件定義書の全機能要件がモジュールに対応しているか
- [ ] 全非機能要件に設計上の対応があるか
- [ ] トレードオフが明示され、合意可能か
- [ ] ADRで判断根拠が追跡可能か
- [ ] SPOF・ボトルネックが特定されているか
- [ ] セキュリティ脅威が洗い出され対策があるか
- [ ] 運用（デプロイ・監視・リカバリ）が設計されているか

合意後、詳細設計（API仕様書・DB定義書・クラス図 等）のフェーズへ移行する。

## システム設計のコツ（実践的指針）

### 🎯 設計の基本姿勢
1. **シンプルさ優先**: 要件を満たす最も単純な構成を選ぶ。過剰設計は保守コストを増やす
2. **トレードオフの明示**: 完璧な設計はない。何を優先し何を諦めるかを必ず明示する
3. **後追い可能性**: 判断根拠をADRに残す。3ヶ月後の自分がなぜその判断をしたか分かるように
4. **境界の明確化**: モジュール・コンテキスト・責務の境界を明確に。曖昧な境界は技術負債の温床
5. **依存方向の統一**: 依存は常に一方向へ。循環依存は即リファクタ対象

### 🏗️ アーキテクチャ選定のコツ
- **チーム規模が小さいならモノリス**: マイクロサービスは組織の成熟度が前提
- **ドメイン境界が不明確ならモジュラモノリス**: 境界は後から見えることもある
- **読み書きの負荷が非対称ならCQRSを検討**: ただし整合性維持のコストを忘れない
- **イベント駆動は疎結合の強力武器**: ただしデバッグ難易度が跳ね上がることを承知で
- **サーバーレスは運用コスト低減に有効**: ただしロックインとコールドスタートを評価

### 📐 モジュール分割のコツ
- **ドメイン境界で切る**: 技術層（Controller/Service/DAO）で切らない
- **集約を小さく**: トランザクション一貫性の範囲は狭いほど安全
- **インターフェースで結合**: 実装ではなく抽象に依存させる
- **変更頻度で分ける**: 変わりやすいものと安定したものを分離

### 🔒 セキュリティ設計のコツ
- **入力を信用しない**: 全入力を検証。外部境界で検証し内部では前提を置く
- **シークレットを書かない**: コード・ログ・エラーメッセージに秘密を出さない
- **最小権限**: デフォルト拒否・必要時のみ許可
- **多層防御**: 一層が破られても次で止める

### ⚡ 性能設計のコツ
- **N+1を避ける**: ORMの遅延ロードは明示的に制御
- **キャッシュ階層**: CDN → アプリ内キャッシュ → DB。無効化方針を必ず決める
- **非同期化**: ユーザー待ちにしなくてよい処理はキューへ
- **インデックス設計**: クエリパターンから逆算。過剰インデックスは書き込み性能を下げる

### 🔄 変更容易性のコツ
- **設定の外部化**: 環境差・チューニング値をコード外へ
- **Feature Flag**: 未完成機能を本番に安全にデプロイ
- **後方互換維持**: IF変更は追加から始め、削除は猶予期間を置く
- **テスト容易性**: 設計段階で「これをテストする方法」を考える

## 出力形式

### テンプレート（設計工程ごとに使い分け）
以下のテンプレートを本スキルフォルダ内に配置済み。設計対象の粒度に応じて使い分けること。

| テンプレート | パス | 用途 | 対応Step |
|---|---|---|---|
| システム設計書（基本設計） | `templates/system-design-template.md` | アーキテクチャ全体像・モジュール分割・非機能 | Step 10 |
| 詳細設計書 | `templates/detailed-design-template.md` | クラス・メソッド・シーケンス・状態遷移 | Step 10 後 |
| API仕様書 | `templates/api-spec-template.md` | IF設計の物理仕様（REST/GraphQL/gRPC） | Step 5 |
| DB定義書 | `templates/db-design-template.md` | テーブル・インデックス・制約・移行 | Step 5 |
| ADR | `templates/adr-template.md` | 設計判断記録 | Step 8 |

### 共通して使える要素（どの設計書にも流用）
- **メタ情報ヘッダ**: ドキュメントID・バージョン・作成日・レビュー状況
- **変更履歴**: バージョン・日付・変更者・変更内容
- **要件との対応**: 要件ID → 設計要素のトレーサビリティ
- **未解決事項**: 後追い課題のリスト
- **Mermaid図**: 共通の描画記法

### 固有にすべき要素（テンプレートを分けた理由）
- **要件定義書**: MoSCoW/Kano/INVEST/SMART/Vモデルという要求分析固有の構造（requirements-analyzer スキルが所管）
- **基本設計書**: C4モデル・アーキテクチャスタイル選定・非機能要件の具現化
- **詳細設計書**: クラス図・シーケンス図・状態遷移・アルゴリズム・例外階層
- **API仕様書**: エンドポイント・スキーマ・エラーコード・レートリミット
- **DB定義書**: ER図・カラム定義・インデックス・制約・マイグレーション

### 保存先
- **基本設計書**: `docs/design/{システム名}-system-design.md`
- **詳細設計書**: `docs/design/{システム名}-detailed-design.md`
- **API仕様書**: `docs/design/{システム名}-api-spec.md`
- **DB定義書**: `docs/design/{システム名}-db-design.md`
- **ADR**: 設計書内に統合、または `docs/adr/ADR-XXX-{title}.md` として個別保存
- **図**: Mermaid記法を用いてMarkdown内に埋め込み（C4図・ER図・シーケンス図 等）

## 実行時の注意

1. **過剰設計を避ける**: 全手法を機械的に適用しない。規模・重要度に応じて適用範囲を調整する
2. **ユーザーとの対話**: 不明点・トレードオフの判断は随時ユーザーに確認する
3. **既存資産の尊重**: 改修案件では既存アーキテクチャとの整合性を優先する
4. **ドキュメントの鮮度**: 設計書は生き物。実装進行に合わせて更新を促す
5. **実装可能性の確認**: 設計したアーキテクチャが現実の技術スタックで実装可能か検証する
