# セキュリティチェック 業務フロースキル

このスキルは **ソフトウェア・Webアプリ・インフラのセキュリティを体系的に監査し、修正案を生成する手順を定義** する。
「何を脆弱性とするか」「修正優先度をどう付けるか」「リスク許容か否か」の価値判断基準は `security-check` エージェントの職種定義を参照すること。

---

## 🔄 全体フロー

```
Phase 1: 監査対象とスコープの把握
    ↓
Phase 2: 脅威モデリング（攻撃面の特定）
    ↓
Phase 3: 自動スキャン実行（可能な場合）
    ↓
Phase 4: 7カテゴリセキュリティ監査
    ↓
Phase 5: 脅威シナリオとリスク評価
    ↓
Phase 6: 脆弱性の統合と優先度付け
    ↓
Phase 7: セキュリティ監査レポート生成
    ↓
Phase 8: （必要なら）修正実装と再検証
```

## Phase 1: 監査対象とスコープの把握

以下を明確にする。不明点は質問する。

- **対象システム**：Webアプリ / API / モバイルアプリ / インフラ / CLI / ライブラリ
- **対象範囲**：全ファイル / 特定モジュール / インフラ設定 / 依存ライブラリ
- **データ感度**：取り扱う個人情報・機密情報の有無と分類
- **コンプライアンス要件**：PCI DSS / GDPR / 個人情報保護法 / HIPAA 等の該当
- **監査深度**：L1（基本）/ L2（標準）/ L3（高度・金融グレード）
- **実行環境**：本番 / ステージング / ローカル
- **許容された攻撃範囲**：ペンテストの場合、実施してよい攻撃の範囲（本番NG等）

## Phase 2: 脅威モデリング（攻撃面の特定）

### 2.1 STRIDE脅威カテゴリの特定

| 脅威 | 日本語 | 例 |
|------|--------|-----|
| **S**poofing | なりすまし | 認証バイパス・ID盗用 |
| **T**ampering | 改ざん | データ・設定・通信の改ざん |
| **R**epudiation | 否認 | 操作ログなし・取引否認 |
| **I**nformation Disclosure | 情報漏洩 | 機密データ・エラーメッセージからの漏洩 |
| **D**enial of Service | サービス拒否 | DoS/DDoS・リソース枯渇 |
| **E**levation of Privilege | 権限昇格 | 一般ユーザーが管理者権限取得 |

### 2.2 攻撃面のマッピング

- **信頼境界**：外部入力が入る箇所（UI/API/ファイル/環境変数/他システム）
- **データフロー**：機密データの流れ（入力→処理→保存→出力）
- **特権境界**：権限が変わる箇所（認証前後・管理者操作・システム間連携）
- **外部依存**：サードパーティライブラリ・API・インフラ

### 2.3 アセットと脅威主体の特定

- **保護すべきアセット**：個人情報・認証情報・決済データ・システム可用性・知的財産
- **脅威主体**：外部攻撃者・内部犯行・マルウェア・誤操作
- **動機・能力・機会**：攻撃者のリソース・標的型か機会型か

## Phase 3: 自動スキャン実行（可能な場合）

以下を活用し、自動検出可能な脆弱性を洗い出す。

### 3.1 静的解析（SAST）
- **言語別**: ESLint security plugin / Bandit (Python) / Brakeman (Ruby) / Semgrep
- **汎用**: SonarQube / CodeQL
- **検出対象**: ハードコードされた秘密・危険関数・インジェクション可能性

### 3.2 依存ライブラリスキャン（SCA）
- **npm**: `npm audit` / Snyk / Dependabot
- **Python**: `safety check` / `pip-audit`
- **汎用**: OWASP Dependency-Check / Trivy
- **検出対象**: 既知CVEを持つパッケージ・ライセンス違反

### 3.3 動的解析（DAST）・コンテナ・IaC
- **DAST**: OWASP ZAP / Burp Suite
- **コンテナ**: Trivy / Grype / Clair
- **IaC**: tfsec / Checkov / Terrascan
- **シークレットスキャン**: TruffleHog / GitLeaks / detect-secrets

自動スキャンが不可能な場合は手動監査（Phase 4）で代替する。ただし自動スキャンは検出可能な問題の一部に過ぎないことを必ず注記する。

## Phase 4: 7カテゴリセキュリティ監査

### 4.1 認証・認可（OWASP A07, A01 / CWE-287, CWE-862）

#### 認証
- [ ] パスワードハッシュが強アルゴリズムか（bcrypt/argon2/scrypt、平文・MD5/SHA1はNG）
- [ ] パスワードポリシーが適切か（最小長・複雑性・履歴・ロックアウト）
- [ ] ブルートフォース対策があるか（レート制限・アカウントロック・CAPTCHA）
- [ ] セッション管理が安全か（推測困難なID・有効期限・HttpOnly/Secure/SameSite）
- [ ] MFA（多要素認証）が実装されているか（機密システム）
- [ ] トークン（JWT等）の有効期限・署名検証・失効が適切か
- [ ] 認証情報のリセットフローが安全か（推測困難なトークン・有効期限）
- [ ] 「デフォルト/弱い資格情報」が残っていないか

#### 認可
- [ ] 認証後に認可チェックがあるか（認証≠認可）
- [ ] IDOR（Insecure Direct Object Reference）対策があるか（IDの所有権確認）
- [ ] 権限昇格（垂直・水平）が不可能か
- [ ] 管理者機能のアクセス制御が適切か
- [ ] APIエンドポイントに認可チェックがあるか
- [ ] 機能レベル・データレベルの両方で制御されているか

### 4.2 入力バリデーション・インジェクション（OWASP A03 / CWE-78, CWE-89, CWE-79）

- [ ] 全入力（UI/API/ファイル/ヘッダー/URL）がバリデーションされているか
- [ ] ホワイトリスト方式か（ブラックリストは不十分）
- [ ] **SQLインジェクション**対策：パラメータ化クエリ/プリペアドステートメント
- [ ] **OSコマンドインジェクション**対策：シェル呼び出し回避・引数の配列渡し
- [ ] **XSS**対策：出力エスケープ・CSP・`innerHTML`回避
- [ ] **XXE**対策：XML外部エンティティの無効化
- [ ] **パストラバーサル**対策：パス正規化・許可ディレクトリ制限
- [ ] **SSRF**対策：内部向けリクエストの禁止・URLスキーム制限
- [ ] **LDAP/NoSQL/ORMインジェクション**対策
- [ ] ファイルアップロードの検証（MIME・拡張子・サイズ・内容・保存先）
- [ ] コンテンツタイプ・文字エンコーディングの検証

### 4.3 機密情報の取り扱い（OWASP A02 / CWE-200, CWE-312）

- [ ] 通信がTLS化されているか（HTTPS・HSTS・TLS 1.2+）
- [ ] 機密データが平文保存されていないか（保存時暗号化）
- [ ] 機密データが平文伝送されていないか（伝送時暗号化）
- [ ] 秘密情報（API鍵・パスワード・トークン）がハードコードされていないか
- [ ] 秘密情報が環境変数・シークレットマネージャで管理されているか
- [ ] 秘密情報がソース・コメント・ログ・エラーメッセージに漏れていないか
- [ ] 個人情報の収集が最小限か（データ最小化原則）
- [ ] 個人情報の保持期間が定義されているか
- [ ] 個人情報の削除・匿名化の仕組みがあるか
- [ ] エラーメッセージがスタックトレース・内部情報を漏洩していないか
- [ ] ログに機密情報（パスワード・トークン・カード番号）が出力されていないか
- [ ] PIIのマスキング（部分伏せ）がされているか

### 4.4 依存ライブラリ・サプライチェーン（OWASP A06 / CWE-1104）

- [ ] 依存ライブラリに既知CVEがないか（`npm audit` / `safety` / Snyk等）
- [ ] ライブラリがメンテナンスされているか（放棄・非推奨でないか）
- [ ] ライブラリのライセンスが許容範囲か（GPL等の制限ライセンス混入）
- [ ] lockファイル（package-lock.json / requirements.txt ピン留め）があるか
- [ ] 依存関係の固定（SemVer範囲の過度な緩さ）が適切か
- [ ] サプライチェーン攻撃対策（署名検証・出所確認）があるか
- [ ] 外部スクリプト・CDNの整合性（SRI: Subresource Integrity）があるか
- [ ] ビルドパイプラインが安全か（権限最小化・シークレット分離）

### 4.5 インフラ・設定（CIS Benchmarks / OWASP A05）

- [ ] ファイアウォール・セキュリティグループが最小権限か
- [ ] 不要なポート・サービスが開いていないか
- [ ] デフォルトアカウント・デフォルトパスワードが変更されているか
- [ ] OS・ミドルウェアのパッチが最新か
- [ ] 管理ポート（SSH/RDP）のアクセス元が制限されているか
- [ ] クラウドストレージ（S3/Blob等）が公開設定になっていないか
- [ ] IAM権限が最小権限か（ワイルドカード権限の回避）
- [ ] セキュリティヘッダが設定されているか（CSP/HSTS/X-Frame-Options/X-Content-Type-Options/Referrer-Policy）
- [ ] CORS設定が過度に緩くないか（`Access-Control-Allow-Origin: *` + 認証はNG）
- [ ] データベースが外部公開されていないか
- [ ] バックアップの暗号化・アクセス制御があるか
- [ ] ログ収集・監視・アラートがあるか

### 4.6 セッション・トークン管理（OWASP A07 / CWE-384, CWE-613）

- [ ] セッションIDが推測困難か（暗号学的乱数）
- [ ] セッションIDがURLに露出していないか
- [ ] セッション有効期限が適切か（アイドルタイムアウト・絶対タイムアウト）
- [ ] ログアウトでセッションが無効化されるか
- [ ] パスワード変更時に全セッションが無効化されるか
- [ ] CSRFトークンが実装されているか（状態変更リクエスト）
- [ ] SameSite属性が適切か（`Strict`/`Lax`）
- [ ] JWTの署名検証・有効期限・失効リストがあるか
- [ ] リフレッシュトークンのローテーションがあるか
- [ ] トークン保存場所が安全か（localStorageはXSSで漏洩リスク）

### 4.7 ログ・監査・インシデント対応（NIST CSF / OWASP A09）

- [ ] 認証・認可イベントがログ記録されているか（成功・失敗）
- [ ] 権限変更・設定変更がログ記録されているか
- [ ] 機密データアクセスがログ記録されているか
- [ ] ログに改ざん耐性があるか（追記のみ・外部保存・WORM）
- [ ] ログに機密情報が含まれていないか
- [ ] 異常検知・アラートの仕組みがあるか
- [ ] インシデント対応手順が定義されているか
- [ ] バックアップ・復旧手順があるか
- [ ] 監査ログの保持期間が要件を満たすか

## Phase 5: 脅威シナリオとリスク評価

### 5.1 攻撃シナリオの作成

検出した脆弱性を組み合わせた現実的な攻撃シナリオを記述する。

```markdown
### シナリオ例：認証バイパス→権限昇格→データ漏洩
1. 攻撃者は未検証のJWTペイロードで認証をバイパス（CVE-XXXX-XXXX）
2. 認可チェック不備により管理者APIにアクセス（CWE-862）
3. 全ユーザーの個人情報を取得（CWE-200）
4. ログ監視不備により検知されず（CWE-778）
```

### 5.2 DREADリスク評価

各脆弱性を以下5軸で1-10点評価し、合計でリスクを算出。

| 軸 | 質問 | 高得点の例 |
|----|------|------------|
| **D**amage | 被害の大きさ | 全データ漏洩・全サービス停止 |
| **R**eproducibility | 再現の容易さ | 毎回再現可能 |
| **E**xploitability | 攻撃の難易度 | 素人が数分で実行可能 |
| **A**ffected users | 影響ユーザー数 | 全ユーザー |
| **D**iscoverability | 発見の容易さ | 誰でも気づく |

### 5.3 CVSS v3.1 スコアリング（既知CVEの場合）

NVDのCVSS v3.1 基本評価値を参照し、重大度を分類。

| スコア | 重大度 | 対応目安 |
|--------|--------|----------|
| 9.0-10.0 | Critical | 即時対応 |
| 7.0-8.9 | High | 1週間以内 |
| 4.0-6.9 | Medium | 1ヶ月以内 |
| 0.1-3.9 | Low | 機会改修 |

## Phase 6: 脆弱性の統合と優先度付け

検出した脆弱性を以下の優先度で分類する。CVSSスコアとDREADリスクを総合して判断する。

| 優先度 | 定義 | 対応目安 |
|--------|------|----------|
| **P0（Critical）** | RCE・認証バイパス・大規模データ漏洩・サービス完全停止 | 即時（24時間以内） |
| **P1（High）** | 権限昇格・重要データ漏洩・既知CVE（High）・インジェクション可能性 | 1週間以内 |
| **P2（Medium）** | 設定不備・情報漏洩（軽微）・既知CVE（Medium）・緩い認証 | 1ヶ月以内 |
| **P3（Low）** | ハードニング余地・既知CVE（Low）・ログ監視改善 | 機会改修 |

## Phase 8: 修正実装と再検証（必要な場合）

ユーザーが修正実装も依頼した場合、修正実装は code-implementer スキルが担う。本スキルは修正案を生成し、実装を code-implementer に委譲する。ただし修正後の再検証（再スキャン・再監査）は本スキルの責務。

- 修正実装は code-implementer スキルに委譲する
- 各修正後に回帰テスト（再スキャン・再監査）で解消確認
- 修正が新たな脆弱性を生んでいないか確認
- 修正内容をコミット単位でまとめる
- 修正後のレポート（差分）を生成

## ⚠️ 注意事項

- **自動スキャンは検出可能な脆弱性の一部に過ぎない**。必ず手動監査を併用する
- **ペネトレーションテストは許可された環境でのみ実施** する。本番環境への攻撃的テストは事前承認必須
- **脆弱性の悪用・実証は最小限** にし、本番データへの影響を避ける
- **ゼロデイ脆弱性**（CVE未登録）は公開前にベンダーへ責任ある開示（CVD）を行う
- **個人情報・機密情報は監査レポートに転記しない**（マスキング・抽象化する）
- **修正案は「防御の重層化」を意識** し、単一対策に依存しない
- **セキュリティはトレードオフ**（利便性・コスト・性能とのバランス）。過剰セキュリティも指摘対象
- **法的規制（GDPR/個人情報保護法/PCI DSS）の該当** がある場合は、違反が法的リスクになる旨を明記する
- 本スキルは監査・提案を担う。最終的な修正判断・リスク許容判断はユーザー（責任者）が行う
