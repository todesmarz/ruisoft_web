# リリース管理 業務フロースキル

このスキルはソフトウェア開発における **リリース管理の実行手順を定義** する。
「どの変更をリリースに含めるか」「バージョン番号をどう付けるか」「リリース判定をどう行うか」「告知範囲をどこまで広げるか」の価値判断基準は `release-manager` エージェントの職種定義を参照すること。

**前提**: 設計書（system-architect 出力）・実装（code-implementer 出力）・テスト設計書（unit-test-designer 出力）・CI/CD設計書（ci-cd-builder 出力）が存在する場合は Step 1 で必ず読み込む。未整備の場合は Step 0 で前提を確認してからリリース管理に進む。

**必須出力**: 本スキルは以下の4つを必ず作成・出力する。リリースノートのみを出力して完了とすることは不可。
1. **リリース計画書**（Markdown）— Step 2 で作成。リリース対象・スケジュール・判定基準・告知計画
2. **Changelog**（Markdown）— Step 4 で更新。変更履歴を版管理
3. **リリースノート**（Markdown）— Step 5 で作成。ユーザー向け・開発者向けの2種類
4. **リリース報告書**（Markdown）— Step 8 で作成。リリース結果・事後検証・残課題

## 適用する標準手法・フレームワーク

本スキルは以下の確立された手法を組み合わせて実行する。各 Step で明示的に参照し、根拠を示すこと。

| 手法 | 由来 | 適用 Step | 役割 |
|---|---|---|---|
| **セマンティックバージョニング (SemVer)** | semver.org | Step 3 | MAJOR.MINOR.PATCH の版番号規約。後方互換性で版を決定 |
| **Conventional Commits** | Angular Team | Step 3, 4 | コミットメッセージ規約。feat/fix/breaking で変更種別を明示 |
| **Keep a Changelog** | Olivier Lacan | Step 4 | Changelogの標準フォーマット。Added/Changed/Deprecated/Removed/Fixed/Security |
| **リリース判定（Go/No-Go）** | ITIL / SRE | Step 6 | 品質ゲート・リスク評価・承認でリリース可否を判定 |
| **リリース計画（Release Plan）** | PMBOK / Agile | Step 2 | リリース対象・スケジュール・責任者・リスクを計画 |
| **カナリアリリース** | Google SRE | Step 7 | 少数ユーザーに先行公開・段階拡大でリスク低減 |
| **ブルーグリーンデプロイ** | Martin Fowler | Step 7 | 現行/新環境切替でゼロダウンタイム・即時ロールバック |
| **Feature Flag** | Martin Fowler | Step 7 | 機能ON/OFFをランタイム制御。デプロイとリリースの分離 |
| **ロールバック** | SRE / DevOps | Step 7 | 障害時の即時復旧。事前定義された手順 |
| **リリースノート（Release Notes）** | ソフトウェア工学 | Step 5 | ユーザー向け・開発者向けの変更説明 |
| **告知計画（Communication Plan）** | PMBOK | Step 5 | リリース告知の対象・手段・タイミング |
| **ポストリリース検証** | SRE / ITIL | Step 8 | リリース後の健全性確認・SLO維持確認 |
| **トレーサビリティ** | Vモデル | Step 8 | 要件→変更→リリースの対応関係 |
| **冪等性** | 分布システム | Step 7 | リリース手順は再実行可能・副作用なし |

### リリース管理ライフサイクルと本スキルStepの対応

```
開発完了 ───→ Step 1: 前提資料の読み込み
          └──→ Step 2: リリース計画の立案
          └──→ Step 3: バージョニングと変更分類
          └──→ Step 4: Changelogの更新
          └──→ Step 5: リリースノートと告知計画の作成
          └──→ Step 6: リリース判定（Go/No-Go）
          └──→ Step 7: リリース実行と監視
          └──→ Step 8: リリース後検証と報告書
```

## Step 0: 前提の確認（設計書・実装がない場合）

設計書・実装・テスト設計書・CI/CD設計書が未整備の場合、以下の最小限の骨子をユーザーに確認する。整備済みの場合は Step 1 へ。

| 確認項目 | 内容 |
|---|---|
| リリース対象 | どのプロジェクト・モジュールをリリースするか |
| 現在の版 | 現在のバージョン番号 |
| 含める変更 | 今回リリースに含める変更一覧 |
| リリース先 | GitHub Pages / npm / GAS / Chrome Web Store / その他 |
| リリース頻度 | 日次 / 週次 / 月次 / 不定期 |
| 告知対象 | ユーザー / 開発チーム / 経営層 / 外部 |

不明点は **不明点リスト** に蓄積し、Step 2 で質問する。system-architect / code-implementer / unit-test-designer / ci-cd-builder スキルの適用を推奨する旨をユーザーに伝えること。

## Step 1: 前提資料の読み込みと解釈

設計書・実装・テスト設計書・CI/CD設計書を読み込み、リリース管理に必要な情報を抽出する。

### 1-1. 抽出項目

| 抽出項目 | リリース管理への影響 |
|---|---|
| 設計書の変更履歴 | リリースに含める変更の特定 |
| 実装のコミット履歴 | 変更種別（feat/fix/breaking）の分類 |
| テスト設計書・テスト結果 | 品質ゲート判定の入力 |
| CI/CD設計書 | リリース手順・デプロイ戦略 |
| 非機能要件 | 性能・セキュリティのリリース基準 |
| 既存のChangelog・版番号 | 版番号の継続性 |

### 1-2. 変更履歴の収集
- 前回リリースからのコミット履歴を全て抽出
- Conventional Commits 規約に基づき変更を分類
- マージ済みPR・解決済Issueを対応付け

### 1-3. 確認ポイント
- リリース対象の変更が全てマージされているか
- テストが全て成功しているか
- CI/CDパイプラインが緑状態か
- 既存Changelogとの整合性

| 変更ID | 種別 | 内容 | 関連Issue | 関連PR |
|---|---|---|---|---|

## 3. スケジュール
| マイルストーン | 日時 | 担当 | 状態 |
|---|---|---|---|
| コード凍結 |  |  |  |
| リリース判定 |  |  |  |
| リリース実行 |  |  |  |
| 事後検証 |  |  |  |

## 4. 判定基準（Go/No-Go）
- [ ] 全テスト成功

- [ ] コードレビュー完了
- [ ] 品質ゲート基準クリア
- [ ] ドキュメント更新完了

| リスク | 確度 | 影響 | 軽減策 |

### 2-2. リリース種別の決定

| 種別 | 条件 | 例 |
|---|---|---|
| **メジャー（MAJOR）** | 後方互換性のない変更 | API破壊的変更・UI大幅改修 |
| **マイナー（MINOR）** | 後方互換性のある機能追加 | 新機能追加・拡張 |
| **パッチ（PATCH）** | バグ修正のみ | バグ修正・軽微な改善 |
| **ホットフィックス** | 緊急障害対応 | 本番障害の緊急修正 |

### 2-3. 不明点の質問
リリース対象・スケジュール・判定基準で判断に迷う事項は **不明点リスト** をユーザーに提示し、回答を得てから計画を確定する。

## Step 3: バージョニングと変更分類

**セマンティックバージョニング (SemVer)** と **Conventional Commits** で版番号と変更分類を決定する。

### 3-1. セマンティックバージョニング

```
MAJOR.MINOR.PATCH
  1     .2    .3
```

| 版番号 | 更新条件 | 例 |
|---|---|---|
| **MAJOR** | 後方互換性のない変更 | API削除・引数変更・DBスキーマ変更 |
| **MINOR** | 後方互換性のある機能追加 | 新機能・新API・オプション追加 |
| **PATCH** | 後方互換性のあるバグ修正 | バグ修正・リファクタリング |

### 3-2. Conventional Commits による変更分類

| プレフィックス | 意味 | 版番号への影響 |
|---|---|---|
| `feat:` | 新機能 | MINOR アップ |
| `fix:` | バグ修正 | PATCH アップ |
| `BREAKING CHANGE:` | 破壊的変更 | MAJOR アップ |
| `perf:` | 性能改善 | PATCH アップ |
| `refactor:` | リファクタリング | 版番号変更なし（内部改善） |
| `docs:` | ドキュメント | 版番号変更なし |
| `style:` | フォーマット | 版番号変更なし |
| `test:` | テスト追加 | 版番号変更なし |
| `chore:` | 雑務・ビルド | 版番号変更なし |
| `ci:` | CI設定 | 版番号変更なし |

### 3-3. 版番号決定フロー

```
1. 前回リリースからの全コミットを収集
2. 各コミットを Conventional Commits で分類
3. 分類結果から最も影響の大きい変更を特定：
   - BREAKING CHANGE が1つでもあれば → MAJOR アップ
   - feat: が1つでもあれば → MINOR アップ
   - fix: のみ → PATCH アップ
   - その他のみ → リリース不要判定も可
4. 新版番号 = 旧版番号 + 該当桁のインクリメント
```

### 3-4. プレリリース・ビルドメタデータ

```
1.2.3-alpha.1    （プレリリース）
1.2.3+20260811   （ビルドメタデータ）
1.2.3-alpha.1+20260811
```

| プレフィックス | 用途 |
|---|---|
| `-alpha` | 初期テスト版 |
| `-beta` | 機能完成・テスト中 |
| `-rc` | リリース候補 |

## Step 4: Changelogの更新

**Keep a Changelog** フォーマットに従い、Changelogを更新する。

### 4-1. Keep a Changelog フォーマット

```markdown
# Changelog

本プロジェクトの全ての重要な変更はこのファイルに記録されます。

## [Unreleased]

## [1.2.3] - 2026-08-11

### Added
- ニュース収集機能に経済指標カテゴリを追加（#123）

### Changed
- Slack通知フォーマットをグループ別に整理（#145）

### Deprecated
- 旧APIエンドポイント `/v1/news` は非推奨（v2.0.0で削除予定）

### Removed
- 廃止されたレガシー設定項目 `legacy_mode` を削除（#150）

### Fixed
- トリガー重複実行のバグを修正（#148）

### Security
- Slackトークンを環境変数に移行（#152）

## [1.2.2] - 2026-07-15
...
```

### 4-2. 変更カテゴリの意味

| カテゴリ | 内容 |
|---|---|
| **Added** | 新機能 |
| **Changed** | 既存機能の変更 |
| **Deprecated** | 非推奨化 |
| **Removed** | 機能削除 |
| **Fixed** | バグ修正 |
| **Security** | セキュリティ関連 |

### 4-3. Changelog更新の原則

- **ユーザー視点**: 開発者内部の都合でなく、ユーザーへの影響を記述
- **簡潔**: 1項目1行。詳細はPR・Issueを参照
- **関連リンク**: Issue/PR番号を付与
- **版番号順**: 新しい版を上に記載
- **Unreleasedセクション**: 次回リリース予定の変更を蓄積

### 5-1. ユーザー向けリリースノート

## 🔄 変更
- **Slack通知の見やすさ改善**: 指標がグループ別に整理され、読みやすくなりました

## 🐛 バグ修正

## ⚠️ 廃止予定
- 旧API `/v1/news` はv2.0.0で削除予定です。新API `/v2/news` へ移行してください

## 📦 アップグレード方法
1. パッケージを更新：`npm update {project}@1.2.3`
2. 設定ファイルの確認：`config.yml` に新項目 `economic_indicators` を追加
3. トリガーの再登録：`npm run setup-triggers`

## Step 6: リリース判定（Go/No-Go）

**リリース判定** でリリース可否を最終決定する。

### 6-1. 品質ゲート基準

| 基準 | 必須/推奨 | 判定方法 |
|---|---|---|
| 全単体テスト成功 | 必須 | CI結果 |
| 全結合テスト成功 | 必須 | CI結果 |
| 全E2Eテスト成功 | 必須 | CI結果 |
| カバレッジ目標達成 | 必須 | CI結果 |
| リンタ・型チェック成功 | 必須 | CI結果 |
| セキュリティスキャン成功 | 必須 | SAST/SCA結果 |
| 性能基準クリア | 推奨 | 性能テスト結果 |
| ドキュメント更新完了 | 必須 | レビュー |
| Changelog更新完了 | 必須 | 確認 |
| 承認者署名 | 必須 | 承認プロセス |

### 6-2. リスク評価

| リスク | 確度 | 影響 | 軽減策 |
|---|---|---|---|
| 新機能の不具合 | 中 | 高 | カナリアリリース・Feature Flag |
| 性能劣化 | 低 | 高 | 性能テスト・段階公開 |
| 外部API互換性 | 低 | 中 | 事前接続テスト |
| ユーザー混乱 | 中 | 中 | 事前告知・移行ガイド |

### 6-3. Go/No-Go判定

```
判定結果：Go / No-Go / 条件付きGo

判定根拠：
- 品質ゲート：全項目クリア
- リスク評価：残リスクは軽減策あり
- 承認状態：承認者署名完了

条件（条件付きGoの場合）：
- {リリース後に必須となる対応}

判定者：{リリース責任者}
判定日時：{日時}
```

### 6-4. No-Go時の対応
- 原因となった問題を特定
- 修正後、Step 1 から再実行
- スケジュール調整・告知変更

## Step 7: リリース実行と監視

**カナリアリリース・ブルーグリーン・Feature Flag** を活用し、安全にリリースを実行する。

### 7-1. リリース戦略の選定

| 戦略 | 適用条件 | リスク | 復旧速度 |
|---|---|---|---|
| **ローリング** | 段階的切替可能 | 中 | 中 |
| **ブルーグリーン** | ゼロダウンタイム必要 | 低 | 高（即時切戻） |
| **カナリア** | 段階的検証必要 | 低 | 高 |
| **Feature Flag** | デプロイとリリース分離 | 低 | 高（フラグ切替） |
| **一斉公開** | 小規模・低リスク | 高 | 低 |

### 7-2. カナリアリリースの段階公開

```
段階1: 1%ユーザー公開 → 1時間監視
段階2: 10%ユーザー公開 → 4時間監視
段階3: 50%ユーザー公開 → 8時間監視
段階4: 100%ユーザー公開
```

各段階で監視項目を確認し、異常があれば即時ロールバック。

### 7-3. リリース時の監視強化

| 監視項目 | 通常時 | リリース時 |
|---|---|---|
| エラー率 | 5分間隔 | 1分間隔 |
| レイテンシ | 5分間隔 | 1分間隔 |
| アラート閾値 | 通常基準 | 厳格基準（半減） |
| オンコール | 通常体制 | 強化体制 |

### 7-4. ロールバック判断基準

| 条件 | 判断 |
|---|---|
| エラー率 5%超過（5分継続） | 即時ロールバック |
| レイテンシ 2倍劣化（10分継続） | 即時ロールバック |
| ユーザー報告 異常多数 | 即時ロールバック |
| SLO違反 | 即時ロールバック |

### 7-5. ロールバック手順

```
1. ロールバック判定（責任者承認）
2. 前版アーティファクトへ切戻し
3. Feature Flag で新機能無効化（使用時）
4. 監視で復旧確認
5. ポストモーテム作成
```

## スキル間連携

- **前段**: `system-architect`（設計書）→ 本スキルが変更履歴を抽出
- **前段**: `code-implementer`（実装）→ 本スキルがコミット履歴を分類
- **前段**: `unit-test-designer`（テスト設計書）→ 本スキルが品質ゲート判定に使用
- **前段**: `ci-cd-builder`（CI/CD）→ 本スキルがリリース手順・監視を連携
- **前段**: `integration-test-designer`（結合テスト）→ 本スキルがE2E結果を判定材料に
- **後段**: `ops-monitor-designer`（運用監視）→ 本スキルがリリース時監視強化を連携
- **後段**: `debugger`（デバッグ）→ リリース後障害の原因特定を委譲
