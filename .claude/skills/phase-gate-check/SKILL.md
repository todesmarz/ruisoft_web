# 工程ゲートチェック 業務フロースキル

このスキルは **各開発工程の成果物が「その工程で最低限決めなければいけないこと」を網羅しているかを検証し、次工程への進行可否を判定する手順を定義** する。
「何を未決定とするか」「次工程に進めるか」の価値判断基準は `self-review` エージェントの職種定義を準用すること。

本スキルは `self-review`・`stakeholder-review` と補完関係にある。
- `self-review`：成果物自体の品質（不整合・誤字・わかりやすさ・ファクト・より良い方法・目的達成性）
- `stakeholder-review`：ステークホルダー視点（目的整合性・前工程整合性・関心事カバレッジ・不明点質問・代替案網羅）
- `phase-gate-check`：工程の完了基準（「決めるべきこと」の網羅性・未決定項目の抽出・進行可否判定）

---

## 🔄 全体フロー

```
Phase 1: 対象工程と成果物の特定
    ↓
Phase 2: 成果物の読込と対象工程チェックリストの選択
    ↓
Phase 3: チェックリストに照らした網羅性検証
    ↓
Phase 4: 未決定項目の分類（必須/推奨/確認事項）
    ↓
Phase 5: 進行可否判定（Go/Conditional Go/No-Go）
    ↓
Phase 6: ゲートチェック報告書の生成
```

## 適用する標準手法・フレームワーク

| 手法 | 由来 | 適用 Phase | 役割 |
|---|---|---|---|
| **Phase Gate Review** | PMBOK / PMI | Phase 1, 5 | 工程完了時のゲートレビュー。完了基準を満たさないと次工程へ進めない |
| **Definition of Ready (DoR)** | Scrum / Agile | Phase 3 | 次工程に進むための準備完了基準。未決定項目がある場合は Ready でない |
| **Definition of Done (DoD)** | Scrum / Agile | Phase 3, 5 | 工程完了の定義。各工程で「完了」とみなすための基準 |
| **Vモデル** | V-Model XT | Phase 2, 3 | 各設計工程に対応する検証工程を紐付け。トレーサビリティの基盤 |
| **MoSCoW法** | DSDM / Agile | Phase 3 | 未決定項目の優先度分類（Must決定/Should決定/Could決定/Won't決定） |
| **チェックリストベースレビュー** | ISTQB / Fagan | Phase 3 | 事前定義されたチェックリストに照らした体系的検証 |
| **IEEE 830** | IEEE | Phase 3 | 要件定義の品質基準（完全・一貫・検証可能・追跡可能・変更可能） |
| **ISO/IEC 25010** | SQuaRE | Phase 3 | 非機能要件の8品質特性。設計工程での網羅性チェックに使用 |
| **C4モデル** | Simon Brown | Phase 3 | 設計書の4層（Context/Container/Component/Code）網羅性チェック |
| **SemVer** | Semantic Versioning | Phase 3 | リリース準備工程でのバージョニング決定事項チェック |

## Phase 1: 対象工程と成果物の特定

ユーザーから対象工程と成果物を特定する。

### 1.1 対象工程の特定

以下のいずれかを特定する。明示されていない場合はヒアリングする。

| 工程ID | 工程名 | 主な成果物 | 前段スキル |
|---|---|---|---|
| `requirements` | 要件定義 | 要件定義書 | requirements-analyzer |
| `design` | 設計 | システム設計書・詳細設計書 | system-architect |
| `implementation` | 実装 | 実装コード・実装報告書 | code-implementer |
| `test-design` | テスト設計 | テスト設計書・テストケース | unit-test-designer / integration-test-designer |
| `release-prep` | リリース準備 | リリース計画書・Changelog・リリースノート | release-manager |

### 1.2 成果物の特定

対象工程の成果物（ファイルパス・ドキュメント）を特定する。複数ある場合はすべて対象とする。

### 1.3 前段成果物の確認

前段工程の成果物が存在する場合は、トレーサビリティ確認のためにあわせて読み込む。
- 例：設計工程のチェック時は、要件定義書も読み込み、要件が設計に反映されているかを確認

---

## Phase 2: 成果物の読込と対象工程チェックリストの選択

### 2.1 成果物の読込

Phase 1 で特定した成果物を読み込む。Markdown・コード・YAML等の形式を問わない。

### 2.2 対象工程チェックリストの選択

対象工程に応じたチェックリスト（Phase 3 の工程別チェックリスト）を選択する。

---

## Phase 3: チェックリストに照らした網羅性検証

対象工程のチェックリストに照らして、成果物が各項目を「決定しているか」を検証する。

### 3.0 検証の基本原則

- **「決定している」の基準**: 成果物に明示的に記載され、一意に解釈できる状態。曖昧な記述・「検討中」「TBD」「後日決定」は未決定とみなす
- **「未決定」の基準**: 記載がない、複数解釈可能、前提が明示されていない、参照先が不明、のいずれか
- **「部分的決定」の基準**: 一部は決定しているが網羅性に欠ける（例：性能要件はあるが可用性要件がない）
- **推測で補完しない**: 記載がなければ未決定として扱う。文脈から推測して「決まっているだろう」と判断しない
- **トレーサビリティ重視**: 前段成果物の各項目が後段成果物で扱われているかを確認する

### 3.1 要件定義工程（`requirements`）のチェックリスト

| # | 決定事項 | 必須/推奨 | 検証観点 |
|---|---|---|---|
| R1 | **目的・背景**（なぜやるか） | 必須 | ビジネス目的・解決すべき課題が明記されているか |
| R2 | **ステークホルダー・利用者**（誰のためか） | 必須 | エンドユーザー・管理者・システム間の利用者が明記されているか |
| R3 | **機能要件**（何をするか） | 必須 | Must/Should/Could/Won't の優先度付きで列挙されているか |
| R4 | **非機能要件**（ISO 25010の8品質特性） | 必須 | 機能適合性・性能効率性・互換性・使用性・信頼性・セキュリティ・保守性・移植性が検討されているか。未必要な場合は「対象外」と明記されているか |
| R5 | **性能要件の定量値** | 必須 | レスポンスタイム・スループット・同時接続数等が数値で示されているか |
| R6 | **可用性要件** | 必須 | 稼働時間・許容停止時間・RTO/RPOが明記されているか |
| R7 | **制約条件** | 必須 | 予算・スケジュール・利用可能技術・運用体制・法的制約が明記されているか |
| R8 | **対象外**（やらないこと） | 必須 | スコープアウトする機能・要件が明示されているか |
| R9 | **受け入れ基準**（完了の定義） | 必須 | 各機能要件に対する受け入れ条件がSMART（Specific/Measurable/Achievable/Relevant/Time-bound）で示されているか |
| R10 | **用語定義** | 推奨 | ドメイン用語・略語の定義集があるか |
| R11 | **前提条件・依存関係** | 必須 | 外部システム依存・前提条件・制約となる既存資産が明記されているか |
| R12 | **優先度・マイルストーン** | 推奨 | リリース優先度・段階的リリース計画があるか |
| R13 | **トレーサビリティ** | 推奨 | 要件IDが振られ、後段工程で追跡可能な構造になっているか |

### 3.2 設計工程（`design`）のチェックリスト

| # | 決定事項 | 必須/推奨 | 検証観点 |
|---|---|---|---|
| D1 | **アーキテクチャスタイル** | 必須 | モノリス/マイクロサービス/サーバーレス等が選定され、理由が記載されているか |
| D2 | **技術スタック** | 必須 | 言語・FW・DB・インフラが明記され、各選定理由（ADR）があるか |
| D3 | **モジュール構成** | 必須 | 責務分割・モジュール境界・依存方向が示されているか（C4のContainer/Componentレベル） |
| D4 | **データ設計** | 必須 | スキーマ・ER図・トランザクション境界・整合性制約が示されているか |
| D5 | **IF設計** | 必須 | API仕様（OpenAPI等）・プロトコル・認証方式・エラーレスポンスが定義されているか |
| D6 | **非機能要件の具現化** | 必須 | 性能目標値・SLO・可用性設計（冗長化・フェイルオーバー）が設計に反映されているか |
| D7 | **セキュリティ設計** | 必須 | STRIDE等で脅威が洗い出され、各脅威に対応策が紐付いているか |
| D8 | **エラー処理・例外設計** | 必須 | エラー分類・ハンドリング方針・リトライ方針・ユーザーへの表示方針があるか |
| D9 | **ログ・監視設計** | 必須 | ログレベル・出力項目・監視メトリクス・アラート条件が定義されているか |
| D10 | **デプロイ・運用設計** | 必須 | デプロイ方式・環境構成・ロールバック方針が示されているか |
| D11 | **ADR（設計判断の記録）** | 必須 | 複数候補から選んだ判断・将来変更可能性のある判断がADRとして記録されているか |
| D12 | **要件とのトレーサビリティ** | 必須 | 要件定義書の各要件がどの設計要素で満たされるか追跡可能か |
| D13 | **キャパシティプランニング** | 推奨 | リソース要件・スケール戦略・成長見込みが示されているか |
| D14 | **データ移行設計** | 推奨 | 既存データの移行が必要な場合、移行方式・切替方式が示されているか |

### 3.3 実装工程（`implementation`）のチェックリスト

| # | 決定事項 | 必須/推奨 | 検証観点 |
|---|---|---|---|
| I1 | **コーディング規約** | 必須 | 命名規則・フォーマット・コメント規約が定義されているか（外部規約の参照でも可） |
| I2 | **ディレクトリ構成** | 必須 | モジュール配置・命名が設計書と一致しているか |
| I3 | **依存ライブラリ** | 必須 | package.json/requirements.txt等でバージョンが固定されているか |
| I4 | **エラーハンドリング** | 必須 | 設計書のエラー処理方針が実装に反映されているか |
| I5 | **ログ出力** | 必須 | 設計書のログ設計が実装に反映されているか |
| I6 | **設定値の外部化** | 必須 | 環境変数・設定ファイルで外部化すべき値がハードコードされていないか |
| I7 | **設計との対応** | 必須 | 設計書の各モジュール・関数・クラスが実装されているか（過不足なし） |
| I8 | **単体テスト** | 必須 | ビジネスロジックに対する単体テストが実装されているか。unit-test-designer の設計書がある場合はそれに従っているか |
| I9 | **CI上の検証項目** | 必須 | lint・型チェック・テストがCIで実行される構成になっているか |
| I10 | **README・セットアップ手順** | 必須 | セットアップ手順・実行方法・依存関係が文書化されているか |
| I11 | **シークレット管理** | 必須 | APIキー・パスワード等がソースに埋め込まれていないか |
| I12 | **実装報告書** | 必須 | 実装対象・設計との対応・テスト結果・残課題が文書化されているか |
| I13 | **リファクタリングの切出** | 推奨 | 振る舞い変更を伴わない改善項目が別課題として切出されているか |

## Phase 4: 未決定項目の分類（必須/推奨/確認事項）

Phase 3 で抽出した未決定項目を以下の3つに分類する。

### 4.1 分類基準

| 分類 | 説明 | 次工程への影響 |
|---|---|---|
| **必須未決定**（Must） | 必須項目が未決定。次工程に進む前に決定が必要 | No-Go（次工程進行不可） |
| **推奨未決定**（Should） | 推奨項目が未決定。次工程に進めるが早期決定を推奨 | Conditional Go（条件付き進行） |
| **確認事項**（Could） | 記載はあるが曖昧・複数解釈可能・前提が不明。ユーザーへの確認推奨 | Conditional Go（要確認） |

### 4.2 未決定項目の記録形式

各未決定項目について以下を記録する。

```
- 項目ID: <R1/D1/I1/T1/L1 等>
- 決定事項: <何を決めるべきか>
- 現状: <未記載/部分的/曖昧/参照先不明>
- 分類: <必須/推奨/確認事項>
- 影響: <次工程で何に影響するか>
- 推奨アクション: <誰がいつまでに決めるべきか・判断材料>
```

## Phase 5: 進行可否判定（Go/Conditional Go/No-Go）

Phase 4 の分類結果に基づき、次工程への進行可否を判定する。

### 5.1 判定基準

| 判定 | 条件 | 次工程の扱い |
|---|---|---|
| **Go** | 必須項目がすべて決定済み。推奨未決定・確認事項はあっても進行可能 | 次工程に進んでよい |
| **Conditional Go** | 必須項目は決定済みだが、確認事項がありユーザー確認が必要。または推奨未決定が多く次工程で手戻りリスクあり | 条件付きで次工程に進んでよい（確認事項の解消・推奨項目の早期決定を条件とする） |
| **No-Go** | 必須項目に未決定がある。次工程に進む前に決定が必要 | 次工程に進めない。未決定項目の解消を優先 |

### 5.2 判定の記録

判定結果とその根拠（どの必須項目が未決定か・いくつの推奨項目が未決定か）を明記する。

## Phase 6: ゲートチェック報告書の生成

以下の構成でゲートチェック報告書（Markdown）を生成する。

### 6.1 報告書の構成

## 🔗 他スキルとの連携

- **前段**: 各工程の成果物を作成するスキル（requirements-analyzer / system-architect / code-implementer / unit-test-designer / release-manager）が対象
- **併用推奨**: `self-review`（成果物自体の品質チェック）・`stakeholder-review`（ステークホルダー視点の整合性確認）
- **後段**: 未決定項目の解消後、次工程のスキルに進む。本スキルの報告書は次工程の入力として活用
