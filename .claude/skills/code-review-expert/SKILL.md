# コードレビューエキスパート 業務フロースキル

このスキルは **コードを6観点で体系的にレビューし、修正案を生成する手順を定義** する。
「何を問題とするか」「修正必須か推奨か」の価値判断基準は `code-review-expert` エージェントの職種定義を参照すること。

---

## 🔄 全体フロー

```
Phase 1: レビュー対象の把握
    ↓
Phase 2: 静的解析の実行（可能な場合）
    ↓
Phase 3: 6観点レビュー
    ↓
Phase 4: 問題点の統合と優先度付け
    ↓
Phase 5: レビューレポート生成
    ↓
Phase 6: （必要なら）修正実装
```

---

## 適用する標準手法・フレームワーク

| 手法 | 由来 | 適用 Phase | 役割 |
|---|---|---|---|
| **SOLID原則** | Robert C. Martin | Phase 3 | オブジェクト指向設計原則 |
| **OWASP Top 10** | OWASP | Phase 3 | セキュリティ脆弱性チェック |
| **Clean Code** | Robert C. Martin | Phase 3 | 可読性・保守性の基準 |
| **Faganインスペクション** | Michael Fagan | Phase 1-5 | 欠陥発見→記録→修正のサイクル |
| **ピアレビュー原則** | ソフトウェア工学 | Phase 1-6 | 客観視点での検証 |
| **AST解析** | 静的解析全般 | Phase 2 | 構文・型・複雑度の自動検出 |
| **Cyclomatic Complexity** | Thomas McCabe | Phase 3 | 関数の複雑度評価（10以下が目安） |
| **DRY原則** | Andy Hunt/Dave Thomas | Phase 3 | 重複コードの検出 |
| **KISS原則** | 工学一般 | Phase 3 | 過剰設計の排除 |
| **YAGNI原則** | XP | Phase 3 | 不要機能の検出 |

## Phase 1: レビュー対象の把握

以下を明確にする。

- **対象ファイル/PR**：レビューするコード
- **変更意図**：何のために変更されたか（機能追加・バグ修正・リファクタリング）
- **対象言語/フレームワーク**：言語仕様・フレームワーク規約の把握
- **レビュー深度**：全観点 or 特定観点に絞るか
- **プロジェクト規約**：コーディング規約・Lint設定の有無

---

## Phase 2: 静的解析の実行（可能な場合）

以下を活用し、自動検出可能な問題を洗い出す。

- **Linter**：ESLint / Pylance / RuboCop 等（構文・スタイル・型）
- **型チェッカー**：TypeScript / mypy / Pyright 等
- **セキュリティスキャナ**：npm audit / safety / Snyk 等
- **複雑度計測**：Cyclomatic Complexity / Cognitive Complexity

自動解析が不可能な場合は手動レビュー（Phase 3）で代替する。

## Phase 3: 6観点レビュー

### 3.1 SOLID原則（設計）

- [ ] **S（単一責任）**：1クラス/関数は1責任か。複数理由で変更される箇所はないか
- [ ] **O（開放閉鎖）**：拡張に開き・修正に閉じているか。新機能追加で既存コードを書き換えていないか
- [ ] **L（リスコフ置換）**：派生型が基本型と置換可能か。継承で契約を破っていないか
- [ ] **I（インターフェース分離）**：使わないメソッドを実装させられていないか
- [ ] **D（依存性逆転）**：上位モジュールが下位モジュールに直接依存していないか。抽象に依存しているか

### 3.2 セキュリティ（OWASP Top 10ベース）

- [ ] **インジェクション**：SQL/OSコマンド/NoSQLインジェクション対策（パラメータ化クエリ）
- [ ] **認証不備**：認証バイパス・弱いパスワードポリシー
- [ ] **機密データ露出**：平文保存・ハードコードされた秘密情報
- [ ] **XXE**：XML外部エンティティ攻撃対策
- [ ] **アクセス制御不備**：権限チェック漏れ・IDOR
- [ ] **XSS**：出力エスケープ・CSP
- [ ] **CSRF**：トークン・SameSite属性
- [ ] **安全でないデシリアライズ**：信頼できないデータの復元
- [ ] **既知脆弱性ライブラリ**：依存パッケージのバージョン確認
- [ ] **ログ監視不備**：監査ログ・異常検知

### 3.3 パフォーマンス

- [ ] **アルゴリズム効率**：計算量（O(n²)等）が適切か。最適化余地
- [ ] **N+1問題**：ループ内のDB呼び出し（ORMで頻発）
- [ ] **メモリ使用量**：不要な保持・リーク
- [ ] **キャッシュ活用**：再計算・再取得の回避
- [ ] **遅延評価**：不要な初期化・先読み
- [ ] **バッチ処理**：1件ずつ処理をバッチ化できるか
- [ ] **並列化可能性**：直列処理を並列化できるか
- [ ] **DBインデックス**：クエリにインデックスが効いているか

### 3.4 可読性（Clean Code）

- [ ] **命名**：意図が伝わる名前か。略語・汎用名（data/tmp）の乱用
- [ ] **関数長**：1関数20行以内目安。長すぎる関数の分割
- [ ] **ネスト深さ**：3階層以内目安。早期return・ガード節
- [ ] **コメント**：なぜ（Why）を書いているか。何を（What）は不要
- [ ] **一貫性**：同種処理が同書き方か
- [ ] **マジックナンバー**：定数化されているか
- [ ] **責務の局所化**：1関数1抽象レベルか

### 3.5 テスト容易性

- [ ] **依存の注入**：外部依存（DB/API/時刻）がモック可能か
- [ ] **副作用の局所化**：純粋関数化できるか
- [ ] **テストカバレッジ**：未テスト分岐がないか
- [ ] **境界値テスト**：null/0/空配列/最大値の考慮
- [ ] **テスト独立性**：テスト間で状態共有がないか
- [ ] **テスト可読性**：Arrange-Act-Assert構造か

### 3.6 保守性

- [ ] **DRY**：重複コードがないか
- [ ] **YAGNI**：使われない機能・過剰な抽象化がないか
- [ ] **KISS**：過剰設計でないか。シンプルな解法がないか
- [ ] **結合度**：モジュール間依存が疎か
- [ ] **凝集度**：1モジュール内が関連機能でまとまっているか
- [ ] **変更影響範囲**：変更が局所化されているか
- [ ] **ドキュメント**：公開API・複雑ロジックに説明があるか
- [ ] **エラー処理**：例外の握り潰し・汎化catchがないか

## Phase 4: 問題点の統合と優先度付け

検出した問題を以下の優先度で分類する。

| 優先度 | 定義 | 対応目安 |
|--------|------|----------|
| **P0（Must Fix）** | セキュリティ脆弱性・バグ・データ破壊 | マージ前必須 |
| **P1（Should Fix）** | 設計違反・パフォーマンス重大問題・テスト不足 | マージ前推奨 |
| **P2（Nice to Fix）** | 可読性・保守性の改善余地 | 次回リファクタ |
| **P3（Suggestion）** | 好み・スタイル・将来対応 | 機会改修 |

## Phase 5: レビューレポート生成

以下のフォーマットでMarkdownレポートを出力する。

```markdown

- 対象ファイル/PR：
- 変更意図：
- 言語/フレームワーク：
- レビュー日：

## 2. サマリ
| 観点 | Must | Should | Nice | Suggestion |
|------|------|--------|------|------------|
| SOLID | ... | ... | ... | ... |
| セキュリティ | ... | ... | ... | ... |
| ...

## 3. 問題点一覧（優先度順）

### P0（Must Fix）
#### CR-001: {問題タイトル}
- 観点：セキュリティ
- 該当箇所：{ファイル:行}
- 問題：{詳細}
- 根拠：OWASP A03:2021 インジェクション
- 修正案：
  ```{lang}
  // 修正前
  ...
  // 修正後
  ...
  ```

### P1（Should Fix）
...

## 4. 良い点
- {積極的に評価すべき実装}

## 5. 改善ロードマップ
- マージ前（P0）：...
- マージ前推奨（P1）：...
- 次回リファクタ（P2）：...
- 機会改修（P3）：...
```

---

## Phase 6: 修正実装（必要な場合）

ユーザーが修正実装も依頼した場合、優先度順に修正する。

- P0から順に対応
- 各修正後に回帰確認（テスト実行・再レビュー）
- 修正はコミット単位でまとめる

## 📋 出力チェックリスト

- [ ] 6観点（SOLID/セキュリティ/パフォーマンス/可読性/テスト容易性/保守性）を確認した
- [ ] 問題点に優先度（P0-P3）が付与された
- [ ] 各問題に根拠（OWASP/Clean Code等）が明記された
- [ ] 修正案に具体的コード例が含まれる
- [ ] 良い点も積極的に評価した
- [ ] 改善ロードマップが提示された

---

## ⚠️ 注意事項

- レビューは「攻撃」ではなく「改善の提案」。人格否定しない
- 良い点も必ず挙げる（モチベーション維持・学習促進）
- 修正案は「なぜそうすべきか」の根拠を必ず添える
- 言語/フレームワークの慣用的書き方を尊重する（独自規約の押し付け禁止）
- パフォーマンス指摘は計測根拠を示す（推測でなく実測）
