# 運用監視設計 業務フロースキル

このスキルはソフトウェア開発における **運用監視設計の実行手順を定義** する。
「どこまでを監視するか」「SLO目標値をどこに置くか」「アラート閾値をどう設定するか」「運用自動化をどこまで進めるか」の価値判断基準は `ops-monitor-designer` エージェントの職種定義を参照すること。

**前提**: 設計書（system-architect 出力）・実装（code-implementer 出力）・CI/CD設計書（ci-cd-builder 出力）が存在する場合は Step 1 で必ず読み込む。未整備の場合は Step 0 で前提を確認してから運用監視設計に進む。

**必須出力**: 本スキルは以下の4つを必ず作成・出力する。監視設定のみを出力して完了とすることは不可。
1. **運用監視設計書**（Markdown）— Step 9 の構成に従い、SLO/SLI・メトリクス・ログ・アラート・ダッシュボードを文書化
2. **監視設定**（IaC/設定ファイル）— Step 6 で実装。Terraform/Prometheus Rule/Grafana JSON/CloudWatch 等
3. **ダッシュボード定義**（JSON/YAML）— Step 7 で作成。主要メトリクスの可視化
4. **運用手順書**（Markdown）— Step 9 で作成。障害対応・アラート対応・定期運用・リカバリ手順

## 適用する標準手法・フレームワーク

本スキルは以下の確立された手法を組み合わせて実行する。各 Step で明示的に参照し、根拠を示すこと。

| 手法 | 由来 | 適用 Step | 役割 |
|---|---|---|---|
| **SRE（Site Reliability Engineering）** | Google SRE Book | Step 3-5 | 信頼性設計の体系。エラーバジェット・SLO・SLI・エラーバジェットポリシー |
| **SLI/SLO/SLA** | Google SRE | Step 3 | SLI（指標）→SLO（目標）→SLA（合意）の階層 |
| **エラーバジェット** | Google SRE | Step 3, 5 | 許容ダウンタイムを予算化。超過時の対応方針 |
| **USEメソッド** | Brendan Gregg | Step 4 | Utilization/Saturation/Errors でリソース監視 |
| **REDメソッド** | Tom Wilkie | Step 4 | Rate/Errors/Duration でサービス監視 |
| **Four Golden Signals** | Google SRE | Step 4 | Latency/Traffic/Errors/Saturation の4指標 |
| **Google SRE 監視の3質問** | Google SRE | Step 4 | 「何を監視すべきでないか」「なぜ監視するか」「誰に伝えるか」 |
| **ログ設計（構造化ログ）** | 12 Factor App | Step 5 | ログをイベントストリーム化。JSON構造化・相関ID |
| **OpenTelemetry** | CNCF | Step 5 | 分散トレーシング・メトリクス・ログの統一規格 |
| **アラート設計（Runbook）** | SRE | Step 6 | アラートに対応手順（Runbook）を必ず紐付ける |
| **アラートファティーグ対策** | SRE | Step 6 | 過剰アラートの抑制。重要度別の通知先分離 |
| **ダッシュボード設計** | SRE / Observability | Step 7 | 直感的可視化。異常が一目で分かる構成 |
| **障害対応（Incident Response）** | Google SRE / ITIL | Step 8 | 検知→トリアージ→緩和→根本対応→ポストモーテム |
| **ポストモーテム（ブラウント分析）** | SRE | Step 8 | 非難なしに事実ベースで再発防止策を策定 |
| **バックアップ・リカバリ設計** | ITIL / DR | Step 8 | RPO/RTO目標・復旧手順・定期的リカバリ訓練 |

| **最小権限の原則** | セキュリティ原則 | Step 6 | 監視システムの権限を必要最小限に |
| **トレーサビリティ** | Vモデル | Step 9 | 設計→監視項目→運用手順の対応関係を明示 |


## Step 0: 前提の確認（設計書・実装がない場合）

設計書・実装・CI/CD設計書が未整備の場合、以下の最小限の骨子をユーザーに確認する。整備済みの場合は Step 1 へ。

| 確認項目 | 内容 |
|---|---|
| 対象システム | どのシステムの運用監視を設計するか |
| 実行環境 | GAS / Cloud Run / GitHub Pages / Vercel / その他 |
| 重要度 | ミッションクリティカル / 業務重要 / 補助 |
| 利用者数 | 想定ユーザー数・トラフィック量 |
| 障害影響 | 障害時の業務影響・金銭影響・法令影響 |
| 運用体制 | オンコール有無・SLA・対応時間帯 |

不明点は **不明点リスト** に蓄積し、Step 2 で質問する。system-architect / code-implementer / ci-cd-builder スキルの適用を推奨する旨をユーザーに伝えること。

## Step 1: 前提資料の読み込みと解釈

設計書・実装・CI/CD設計書を読み込み、運用監視設計に必要な情報を抽出する。

### 1-1. 抽出項目

| 抽出項目 | 監視設計への影響 |
|---|---|
| アーキテクチャ（設計書） | 監視対象コンポーネント・依存関係 |
| 非機能要件（設計書） | SLO目標値・性能・可用性・セキュリティ要件 |
| 外部依存（設計書） | 外部API・DB・メッセージキューの監視対象 |
| 実装コード | ログ出力箇所・メトリクス計測箇所・エラーハンドリング |
| CI/CD設計書 | デプロイ監視・リリース監視・ロールバック検知 |
| 制約条件 | 予算・利用可能監視ツール・運用体制 |

### 1-2. 既存監視資産の確認
- 既存の監視設定（CloudWatch/Prometheus/Grafana/Datadog 等）
- 既存のアラート設定・通知先・Runbook
- 既存のダッシュボード・ログ集約基盤
- 既存の障害対応履歴・ポストモーテム

### 1-3. 確認ポイント
- 設計書の非機能要件が監視可能な形で定義されているか
- 実装にログ・メトリクス計測が組み込まれているか（未組込なら追加提案）
- 既存監視資産を再利用できるか

## Step 2: 監視要件の定義

運用監視で **何を守り、何を検知し、誰にどう伝えるか** を明確にする。

### 2-1. Google SRE 監視の3質問

| 質問 | 答え方 |
|---|---|
| 何を監視すべきでないか | 単なるシステム内部状態・自己解決する一時障害 |
| なぜ監視するか | ユーザー体験の悪化検知・SLI違反検知・デバッグ |
| 誰に伝えるか | オンコールエンジニア・開発チーム・経営層 |

### 2-2. 監視対象の分類

| 分類 | 監視対象 | 例 |
|---|---|---|
| **ユーザー体験** | エンドユーザーが直接影響を受ける指標 | 応答時間・エラー率・可用性 |
| **システム健全性** | システム内部の健全性 | CPU/メモリ/ディスク/DB接続数 |
| **ビジネス指標** | 業務上重要な指標 | 注文数・アクティブユーザー数・処理件数 |
| **セキュリティ** | セキュリティイベント | 不正アクセス・権限違反・異常トラフィック |
| **コスト** | リソースコスト | API呼出回数・実行時間・ストレージ使用量 |

### 2-3. 監視自動化範囲の決定

| 自動化対象 | 自動/半自動/手動 | 理由 |
|---|---|---|
| メトリクス収集 | 自動 | 常時 |
| ログ集約 | 自動 | 常時 |
| 異常検知 | 自動 | 閾値・異常検知アルゴリズム |
| アラート通知 | 自動 | 閾値超過時 |
| 自動スケール | 自動/半自動 | 需要変動対応 |
| 自動ロールバック | 半自動 | 承認ゲートの有無 |
| 障害対応 | 半自動/手動 | 自動復旧は限定的・人間判断必要 |

### 2-4. 不明点の質問
SLO目標値・アラート閾値・運用体制で判断に迷う事項は **不明点リスト** をユーザーに提示し、回答を得てから設計に進む。

## Step 3: SLO/SLI設計（エラーバジェット）

**SRE手法** に基づき、SLI→SLO→エラーバジェットの順で設計する。

### 3-1. SLI（Service Level Indicator）の定義

ユーザー体験を直接反映する指標を定義する。

| SLI種別 | 定義 | 測定方法 |
|---|---|---|
| **可用性** | 成功リクエスト数 / 総リクエスト数 | HTTPステータス・成功率 |
| **レイテンシ** | 応答時間が閾値以下のリクエスト割合 | ヒストグラム・パーセンタイル |
| **スループット** | 単位時間あたりの処理件数 | リクエスト数/秒 |
| **正確性** | 正しい結果を返したリクエスト割合 | データ検証・照合 |
| **鮮度** | データ更新時刻が閾値以内の割合 | 最終更新時刻 |
| **耐久性** | データ損失なしの割合 | バックアップ検証 |

### 3-2. SLO（Service Level Objective）の設定

SLIに対する目標値を設定する。**ユーザー体験に基づき** 決定し、技術的都合で決めない。

| SLO例 | 目標値 | 計算根拠 |
|---|---|---|
| 可用性 | 99.9% | 月間ダウンタイム43分以内 |
| レイテンシ（99%tile） | 500ms以下 | ユーザー離脱率閾値 |
| レイテンシ（99.9%tile） | 2秒以下 | 競合比較 |
| エラー率 | 0.1%以下 | ビジネス影響許容範囲 |
| 処理鮮度 | 95%が1時間以内 | 業務要件 |

### 3-3. エラーバジェットの計算

```
SLO = 99.9%可用性 の場合：
  エラーバジェット = 100% - 99.9% = 0.1%
  月間許容ダウンタイム = 43200分 × 0.1% = 43.2分
```

### 3-4. エラーバジェットポリシー

| 状態 | 対応方針 |
|---|---|
| バジェット消費 < 50% | 正常。新機能リリース可 |
| 50% ≤ 消費 < 100% | 注意。リスク高いリリースは慎重判断 |
| バジェット消費 ≥ 100% | 超過。機能凍結・信頼性改善を優先 |

### 3-5. GASプロジェクト特有のSLO設計

GASのトリガーベース処理では以下のSLI/SLOが現実的。

| SLI | SLO例 | 測定方法 |
|---|---|---|
| トリガー実行成功率 | 99%以上 | StorageService の実行ログ |
| 通知遅延（トリガー時刻→投稿時刻） | 95%が5分以内 | 投稿時刻 - トリガー時刻 |
| API呼出エラー率 | 5%以下 | AIService/Rss のエラーログ |
| データ鮮度（市場指標） | 95%が当日分 | 指標取得日付 |

## Step 4: メトリクス設計（USE/RED/Golden Signals）

**USEメソッド**（リソース）・**REDメソッド**（サービス）・**Four Golden Signals** でメトリクスを網羅する。

### 4-1. USEメソッド（リソース監視）

| 指標 | 対象 | 例 |
|---|---|---|
| **U**tilization | 使用率 | CPU/メモリ/ディスク使用率 |
| **S**aturation | 飽和度 | キュー長・接続プール枯渇 |
| **E**rrors | エラー | ハードウェアエラー・ドロップ |

### 4-2. REDメソッド（サービス監視）

| 指標 | 対象 | 例 |
|---|---|---|
| **R**ate | リクエスト率 | リクエスト数/秒 |
| **E**rrors | エラー率 | HTTP 5xx率 |
| **D**uration | 応答時間 | レイテンシ分布 |

### 4-3. Four Golden Signals

| シグナル | 内容 | 主要メトリクス |
|---|---|---|
| **Latency** | 応答時間 | p50/p90/p99レイテンシ |
| **Traffic** | トラフィック量 | リクエスト数・セッション数 |
| **Errors** | エラー率 | 5xx率・例外発生率 |
| **Saturation** | 飽和度 | CPU/メモリ/接続数の上限接近 |

### 4-4. メトリクス定義書のテンプレート

```
メトリクスM-001: HTTP 5xx エラー率
  種別: RED / Errors
  定義: status >= 500 のリクエスト数 / 総リクエスト数
  収集方法: アクセスログ・APM
  収集間隔: 1分
  関連SLO: エラー率 0.1%以下
  アラート閾値: 1%超過（5分連続）
```

### 4-5. GASプロジェクト特有のメトリクス

| メトリクス | 収集方法 | 用途 |
|---|---|---|
| トリガー実行回数・成功率 | StorageService ログ | 実行健全性 |
| API呼出回数・コスト | AIService ログ | コスト監視 |
| 処理時間 | Main.js 実行時間計測 | 性能監視 |
| 通知送信成功/失敗 | SlackService ログ | 通知到達性 |
| RSS取得成功/失敗 | Rss.js ログ | データソース健全性 |

## Step 5: ログ・トレーシング設計

**12 Factor App** の「ログをイベントストリーム化」と **OpenTelemetry** でログ・トレーシングを設計する。

### 5-1. 構造化ログ設計

JSON形式で構造化し、機械的処理可能性を担保する。

```json
{
  "timestamp": "2026-08-11T09:00:00.123Z",
  "level": "ERROR",
  "service": "gas_ai_agent",
  "trace_id": "abc123",
  "span_id": "def456",
  "trigger_id": "daily_news_20260811",
  "module": "AIService",
  "function": "generateSummary",
  "message": "API timeout",
  "error_type": "TimeoutError",
  "duration_ms": 60000,
  "metadata": {
    "api_endpoint": "https://api.example.com/v1/summary",
    "retry_count": 3
  }
}
```

### 5-2. ログレベルの運用方針

| レベル | 用途 | 通知 |
|---|---|---|
| ERROR | エラー・例外・障害 | アラート対象 |
| WARN | 警告・閾値接近・フォールバック動作 | 監視対象 |
| INFO | 正常イベント・業務処理の開始/終了 | 保持のみ |
| DEBUG | 詳細情報・デバッグ用 | 本番では無効化 |

### 5-3. 相関ID（Trace ID）の設計

分散システム・複数モジュール連携でトレーサビリティを担保する。

- 1つの処理フロー開始時に **Trace ID** を生成
- 全モジュールで Trace ID を伝播・ログに含める
- 障害時に Trace ID で一連の処理を追跡可能にする

### 5-4. ログ保持期間

| ログ種別 | 保持期間 | 理由 |
|---|---|---|
| エラーログ | 1年 | 障害分析・コンプライアンス |
| アクセスログ | 3ヶ月 | セキュリティ分析 |
| 業務ログ | 1年 | 業務証跡・監査対応 |
| デバッグログ | 7日 | 短期デバッグのみ |

### 5-5. 分散トレーシング（OpenTelemetry）

複数サービス連携では **OpenTelemetry** でメトリクス・ログ・トレースを統一する。

- Trace: 1リクエストの全体フロー
- Span: 1モジュール内の処理単位
- Context Propagation: サービス間でTrace IDを伝播

## Step 6: アラート設計（Runbook紐付け）

**SRE手法** に基づき、アラートに必ずRunbook（対応手順）を紐付ける。アラートファティーグ対策を実施する。

### 6-1. アラート設計原則

| 原則 | 内容 |
|---|---|
| **ユーザー影響基準** | ユーザー体験に影響するもののみアラート化 |
| **実行可能性** | アラート受信者が取るべき行動が明確 |
| **Runbook紐付け** | 全アラートに対応手順を必ず紐付ける |
| **重要度分離** | 通知先を重要度別に分離（PagerDuty/Slack/メール） |
| **重複抑制** | 同一障害の複数アラートをグループ化 |
| **閾値の根拠** | 閾値はSLO・過去データ・業務影響に基づく |

### 6-2. アラート重要度

| 重要度 | 通知先 | 対応時間 | 例 |
|---|---|---|---|
| **P1（Critical）** | PagerDuty・電話 | 15分 | サービス全停止・データ損失 |
| **P2（High）** | PagerDuty・Slack | 1時間 | 主要機能障害・SLO大幅違反 |
| **P3（Medium）** | Slack | 営業時間内 | 部分障害・閾値接近 |
| **P4（Low）** | メール・日次レポート | 1営業日 | 補助機能・予兆検知 |

### 6-3. アラート定義のテンプレート

```
アラートA-001: API 5xx エラー率超過
  メトリクス: M-001 HTTP 5xx エラー率
  条件: error_rate > 1% for 5 minutes
  重要度: P2
  通知先: PagerDuty(オンコール) + Slack #alerts
  Runbook: docs/runbooks/A-001-api-5xx.md
  関連SLO: エラー率 0.1%以下
  自動対応: 自動スケールアウト（3分継続時）
```

### 6-4. Runbook（対応手順）のテンプレート

```markdown
# Runbook A-001: API 5xx エラー率超過

## 症状
- APIの5xxエラー率が1%を5分間超過

## 影響範囲
- エンドユーザーへのAPI応答失敗
- 連携システムの処理停滞

## 初動対応（15分以内）
1. ダッシュボードでエラー率推移を確認
2. エラーログから原因API・エラーコードを特定
3. 該当APIが全停止か部分障害かを判定

## 緩和対応
- 該当APIをルーティングから外す（可能場合）
- フォールバック先に切り替え
- キャッシュ延長で負荷軽減

## 根本対応
- エラー原因の特定と修正
- 修正後は段階的にトラフィック復元

## エスカレーション
- 15分で緩和不可 → サービスオーナーへ連絡
- 30分で緩和不可 → 経営層へエスカレーション

## ポストモーテム
- 48時間以内にポストモーテムを作成
- 再発防止策をIssue化
```

### 6-5. アラートファティーグ対策

| 対策 | 内容 |
|---|---|
| 通知先分離 | P1/P2はPagerDuty、P3/P4はSlack/メール |
| グループ化 | 同一障害の複数アラートを1つにまとめる |
| 抑制期間 | 対応中の重複通知を抑制 |

## Step 8: 障害対応・リカバリ設計

**Google SRE / ITIL** に基づき、障害対応プロセスとリカバリ設計を行う。

### 8-1. 障害対応プロセス

```
検知 → トリアージ → 緩和 → 根本対応 → ポストモーテム
  │        │         │          │           │
  自動     人間判断   暫定復旧   完全復旧    再発防止
```

| フェーズ | 内容 | 目標時間 |
|---|---|---|
| 検知 | アラート・監視で異常を発見 | 自動・即時 |
| トリアージ | 影響範囲・重要度を判定 | 5分以内 |
| 緩和 | サービス復旧（暫定可） | 15分〜1時間 |
| 根本対応 | 原因修正・完全復旧 | 24時間以内 |
| ポストモーテム | 再発防止策の策定 | 48時間以内 |

### 8-2. ポストモーテム（ブラウント分析）

**非難なしに事実ベース** で再発防止策を策定する。

```markdown
# ポストモーテム: {障害名}

## 概要
- 発生時刻：
- 影響範囲：
- 復旧時刻：
- 影響ユーザー数：

## タイムライン
- 09:00 アラート検知
- 09:05 トリアージ開始
- 09:15 緩和対応実施
- 09:30 サービス復旧

## 根本原因
- {技術的根本原因}

## 貢献要因
- {原因を拡大・遅延させた要因}

## 学び
- {今回の障害から得た知見}

## アクションアイテム
- [ ] {再発防止策}（担当：〇〇、期限：〇〇）
```

### 8-3. バックアップ・リカバリ設計

| 項目 | 設計内容 |
|---|---|
| **RPO（Recovery Point Objective）** | 許容データ損失量（例：15分） |
| **RTO（Recovery Time Objective）** | 復旧目標時間（例：4時間） |
| **バックアップ頻度** | 日次・時間帯別 |
| **バックアップ保管** | 3世代・暗号化・別リージョン |
| **リカバリ手順** | 復旧手順書・定期的リカバリ訓練 |
| **リカバリ訓練** | 四半期に1回・実環境で検証 |

### 8-4. GASプロジェクト特有のリカバリ

| 障害シナリオ | リカバリ手順 |
|---|---|
| トリガー未発火 | トリガー再登録・手動実行 |
| 外部API長期障害 | フォールバック先へ切替・過去データで代替 |
| スプレッドシート破損 | バックアップから復元・整合性チェック |
| Slackトークン無効化 | トークン再発行・設定更新 |

## スキル間連携

- **前段**: `system-architect`（設計書）→ 本スキルが非機能要件を監視設計に落とし込む
- **前段**: `code-implementer`（実装）→ 本スキルがログ・メトリクス計測箇所を特定
- **前段**: `ci-cd-builder`（CI/CD）→ 本スキルがデプロイ監視・リリース監視を設計
- **後段**: `debugger`（デバッグ）→ 監視で検知した障害の原因特定を委譲
- **後段**: `release-manager`（リリース管理）→ リリース時の監視強化・カナリア監視を連携
