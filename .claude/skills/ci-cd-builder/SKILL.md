# CI/CD構築 業務フロースキル

このスキルはソフトウェア開発における **CI/CDパイプライン構築の実行手順を定義** する。
「どこまで自動化するか」「品質ゲートをどこに置くか」「デプロイ戦略をどうするか」の価値判断基準は `ci-cd-builder` エージェントの職種定義を参照すること。

**前提**: 設計書（system-architect 出力）・実装（code-implementer 出力）・テスト設計書（unit-test-designer 出力）が存在する場合は Step 1 で必ず読み込む。未整備の場合は Step 0 で前提を確認してから構築に進む。

**必須出力**: 本スキルは以下の3つを必ず作成・出力する。ワークフローファイルのみを出力して完了とすることは不可。
1. **CI/CDパイプライン定義**（GitHub Actions ワークフローYAML等）— Step 6 で実装。冪等性を担保
2. **パイプライン設計書**（Markdown）— Step 9 の構成に従い、ステージ・品質ゲート・デプロイ戦略・ロールバックを文書化
3. **運用手順書**（Markdown）— Step 9 で作成。手動トリガ・緊急停止・ロールバック・監視アラートの運用手順

## 適用する標準手法・フレームワーク

本スキルは以下の確立された手法を組み合わせて実行する。各 Step で明示的に参照し、根拠を示すこと。

| 手法 | 由来 | 適用 Step | 役割 |
|---|---|---|---|
| **CI（継続的インテグレーション）** | Martin Fowler | Step 3-6 | 全コミットで自動ビルド・テスト。統合の早期発見 |
| **CD（継続的デリバリー/デプロイ）** | Jez Humble | Step 3-6 | リリース可能状態を常時維持。デプロイの自動化 |
| **パイプライン as Code** | Jenkins Pipeline / GitHub Actions | Step 6 | パイプライン定義をコードで管理。版管理・レビュー対象 |
| **DORA 4 Keys** | Google DORA | Step 2, 9 | デプロイ頻度・変更リードタイム・変更障害率・MTTRで効果測定 |
| **GitFlow / GitHub Flow / Trunk-based** | 各種Git運用 | Step 3 | ブランチ戦略とパイプラインの連携モデル |
| **品質ゲート** | SonarQube / SQuaRE | Step 5 | 次ステージ進入可否を品質基準で判定。基準違反は停止 |
| **シフトレフトテスト** | Larry Smith | Step 5 | テストを上流に移し、欠陥を早期発見 |
| **ブルーグリーンデプロイ** | Martin Fowler | Step 7 | 現行/新環境を切り替え。ゼロダウンタイム・即時ロールバック |
| **カナリアリリース** | Google SRE | Step 7 | 少数ユーザーに先行公開。段階的に拡大 |
| **ローリングデプロイ** | Kubernetes | Step 7 | 古い版を順次入れ替え。段階的リリース |
| **Feature Flag** | Martin Fowler | Step 7 | 機能のON/OFFをランタイム制御。デプロイとリリースの分離 |
| **冪等性** | 分布システム | Step 6 | 同じ入力で同じ結果。再実行で副作用を出さない |
| **シークレット管理** | OWASP / 12 Factor | Step 6 | シークレットをコードに埋め込まず外部化 |
| **最小権限の原則** | セキュリティ原則 | Step 6 | ワークフローの権限を必要最小限に絞る |
| **SBOM（Software Bill of Materials）** | OWASP / CycloneDX | Step 5 | 依存関係の部品表でサプライチェーン可視化 |
| **SAST / SCA / DAST** | AST分類 | Step 5 | 静的解析・依存関係・動的解析でセキュリティ担保 |
| **不変アーティファクト** | DevOps原則 | Step 4 | ビルド成果物は不変。デプロイは同一アーティファクトを使用 |
| **トレーサビリティ** | Vモデル | Step 9 | 設計→実装→テスト→デプロイの対応関係を明示 |

### DORA 4 Keys と本スキルStepの対応

```
設計・実装 ───→ Step 1: 前提資料の読み込み
            └──→ Step 2: パイプライン要件の定義（DORA目標値設定）
            └──→ Step 3: ブランチ戦略とパイプライン全体設計
            └──→ Step 4: ビルド・アーティファクト設計
            └──→ Step 5: 品質ゲートとテスト戦略
            └──→ Step 6: ワークフロー実装（CI/CD as Code）
            └──→ Step 7: デプロイ戦略とロールバック
            └──→ Step 8: パイプラインの検証と最適化
            └──→ Step 9: パイプライン設計書と運用手順書の作成
```

## Step 0: 前提の確認（設計書・実装がない場合）

設計書・実装・テスト設計書が未整備の場合、以下の最小限の骨子をユーザーに確認する。整備済みの場合は Step 1 へ。

| 確認項目 | 内容 |
|---|---|
| 対象リポジトリ | どのプロジェクトのCI/CDを構築するか |
| 技術スタック | 言語・フレームワーク・ビルドツール・パッケージマネージャ |
| デプロイ先 | GitHub Pages / GAS / Cloud Run / Vercel / その他 |
| リリース頻度 | 日次 / 週次 / リリースブランチマージ時 |
| 品質基準 | 必須テスト・カバレッジ閾値・リンタ要件 |
| 環境 | 開発 / ステージング / 本番 の有無と数 |

不明点は **不明点リスト** に蓄積し、Step 2 で質問する。system-architect / code-implementer / unit-test-designer スキルの適用を推奨する旨をユーザーに伝えること。

## Step 1: 前提資料の読み込みと解釈

設計書・実装・テスト設計書を読み込み、CI/CD構築に必要な情報を抽出する。

### 1-1. 抽出項目

| 抽出項目 | CI/CDへの影響 |
|---|---|
| 技術スタック（設計書） | ビルドコマンド・テストコマンド・アーティファクト形式 |
| モジュール構成（設計書） | ビルド対象・テスト対象の分割 |
| 非機能要件（設計書） | 性能・セキュリティ・可用性の品質ゲート基準 |
| 実装コード（code-implementer） | ビルド手順・依存関係・テスト実行方法 |
| テスト設計書（unit-test-designer） | テストスイート構成・カバレッジ目標・テスト戦略 |
| 制約条件 | 予算・スケジュール・利用可能CIリソース・実行時間制限 |

### 1-2. 既存CI/CDの確認
- 既存のワークフローファイル（`.github/workflows/` 等）の有無と内容
- 既存のビルドスクリプト・デプロイスクリプト
- 既存の環境変数・シークレット設定
- 既存のブランチ保護ルール・必須ステータスチェック

### 1-3. 確認ポイント
- 設計書と実装の間に乖離がないか（実装が設計を反映しているか）
- テストが自動実行可能な状態か（CI環境で動くか）
- 既存のCI/CD資産を再利用できるか

## Step 2: パイプライン要件の定義

CI/CDで **何を自動化し、どこまでを自動化するか** を明確にする。DORA 4 Keys で目標値を設定する。

### 2-1. DORA 4 Keys 目標値

| 指標 | 目標値（参考: エリートチーム） | 本プロジェクトの目標 |
|---|---|---|
| デプロイ頻度 | 1日複数回 | {設定値} |
| 変更リードタイム | 1時間未満 | {設定値} |
| 変更障害率 | 0-15% | {設定値} |
| MTTR（平均復旧時間） | 1時間未満 | {設定値} |

### 2-2. 自動化範囲の決定

| 自動化対象 | 自動/半自動/手動 | 理由 |
|---|---|---|
| Lint・フォーマット | 自動 | コミット毎 |
| ビルド | 自動 | コミット毎 |
| 単体テスト | 自動 | コミット毎 |
| 統合テスト | 自動/半自動 | PR毎 or マージ時 |
| セキュリティスキャン | 自動 | コミット毎 or 定期 |
| ステージングデプロイ | 自動 | mainマージ時 |
| 本番デプロイ | 自動/半自動 | 承認ゲートの有無 |
| ロールバック | 半自動 | 手動トリガ or 自動検知 |

### 2-3. 不明点の質問
自動化範囲・デプロイ戦略・品質ゲート基準で判断に迷う事項は **不明点リスト** をユーザーに提示し、回答を得てから設計に進む。

## Step 3: ブランチ戦略とパイプライン全体設計

Git運用モデルとパイプラインの **全体構造** を設計する。

### 3-1. ブランチ戦略の選定

| 戦略 | 特徴 | 適する規模 |
|---|---|---|
| **GitHub Flow** | main + featureブランチ。PRでmain直接統合 | 小〜中規模・高頻度デプロイ |
| **GitFlow** | main/develop/feature/release/hotfix | 大規模・複数リリース並行 |
| **Trunk-based** | main + 短命feature。高頻度統合 | 高頻度デプロイ・CI成熟度高 |
| **Release Flow** | main + releaseブランチ | リリース管理が必要な中規模 |

### 3-2. パイプライン全体構造

```
[Push/PR] → [Lint] → [Build] → [Test] → [Quality Gate]
                                          ↓ (合格)
                                      [Package]
                                          ↓
                                  [Deploy to Staging]
                                          ↓
                                  [Integration Test]
                                          ↓
                                  [Approval Gate] (必要時)
                                          ↓
                                  [Deploy to Prod]
                                          ↓
                                  [Smoke Test]
                                          ↓
                                  [Monitor]
```

### 3-3. トリガ設計

| トリガ | 実行パイプライン | 対象ブランチ |
|---|---|---|
| push | CI（Lint/Build/Test） | feature/*, main |
| pull_request | CI + 品質ゲート | main宛てPR |
| schedule | 定期スキャン・依存関係更新 | 指定時刻 |
| workflow_dispatch | 手動デプロイ・ロールバック | 任意 |
| release published | 本番デプロイ | release/* |

### 3-4. 確認ポイント
- ブランチ戦略がプロジェクトの規模・リリース頻度に合っているか
- トリガが過不足なく設定されているか
- パイプライン全体がシンプルで追跡可能か

## Step 4: ビルド・アーティファクト設計

**不変アーティファクト** を生成し、デプロイは同一アーティファクトを使い回すことを原則とする。

### 4-1. ビルド戦略

| 項目 | 設計内容 |
|---|---|
| ビルドコマンド | {言語/フレームワークに応じたコマンド} |
| キャッシュ戦略 | 依存関係・ビルド成果物のキャッシュで高速化 |
| 並列化 | テストスイートの分割・マトリクスビルド |
| 実行環境 | runner OS / コンテナイメージ / 版固定 |
| タイムアウト | ビルド・テストの最大実行時間 |

### 4-2. アーティファクト設計

| 項目 | 設計内容 |
|---|---|
| 形式 | JAR / Dockerイメージ / 静的ファイル / npm package |
| 命名規則 | `{name}-{version}-{commit_sha}` で一意識別 |
| 保存先 | GitHub Artifacts / Container Registry / リリース添付 |
| 保持期間 | 本番: 永続 / ステージング: n日 |
| 不変性 | 同一名の再pushは不可（CIで拒否） |

### 4-3. バージョニング

| 方式 | 適用場面 |
|---|---|
| セマンティックバージョニング (SemVer) | ライブラリ・API |
| 日付+SHA | 内部ビルド |
| CalVer (YYYY.MM.DD) | 定期リリース |
| Gitタグベース | リリース運用 |

### 4-4. 確認ポイント
- アーティファクトが不変で、ステージングと本番で同一物を使えるか
- キャッシュでビルド時間が妥当か（10分超は要見直し）
- バージョニングでビルドを一意に識別できるか

## Step 5: 品質ゲートとテスト戦略

パイプラインの各ステージに **品質ゲート** を設定し、基準違反は次ステージに進めない。

### 5-1. 品質ゲートの設計

| ステージ | ゲート基準 | 違反時の動作 |
|---|---|---|
| Lint | エラー0件・警告は許容 | 失敗 |
| ビルド | 成功 | 失敗 |
| 単体テスト | 全テスト成功・カバレッジ ≥ {閾値}% | 失敗 |
| 統合テスト | 全テスト成功 | 失敗 |
| SAST（静的解析） | Critical/High 0件 | 失敗 |
| SCA（依存関係） | 既知脆弱性 Critical/High 0件 | 失敗 |
| ライセンスチェック | 禁止ライセンス0件 | 失敗 |
| SBOM生成 | 必須 | 警告 or 失敗 |
| パフォーマンス | 閾値内 | 警告 |

### 5-2. テスト戦略（シフトレフト）

| テスト種別 | 実行タイミング | 実行環境 |
|---|---|---|
| 単体テスト | 全コミット | CI runner |
| 結合テスト | PR / mainマージ | CI runner or コンテナ |
| E2Eテスト | ステージングデプロイ後 | ステージング環境 |
| スモークテスト | 本番デプロイ後 | 本番環境 |
| 負荷テスト | 定期 or リリース前 | 専用環境 |

### 5-3. セキュリティスキャン

| スキャン | ツール例 | 対象 |
|---|---|---|
| SAST | CodeQL / Semgrep | ソースコード |
| SCA | Dependabot / Snyk / OSV-Scanner | 依存関係 |
| DAST | OWASP ZAP | 実行中アプリ |
| コンテナスキャン | Trivy / Grype | コンテナイメージ |
| シークレットスキャン | gitleaks / secretlint | コード・コミット履歴 |

### 5-4. 確認ポイント
- 品質ゲートが緩すぎず厳すぎないか（偽陽性の多さに注意）
- テストがシフトレフトされ、上流で欠陥を捕捉できるか
- セキュリティスキャンが必須項目をカバーしているか

## Step 6: ワークフロー実装（CI/CD as Code）

GitHub Actions ワークフローYAML等で **パイプラインをコードとして実装** する。冪等性を必ず担保する。

### 6-1. 実装の基本原則

- **冪等性**: 同じ入力・同じコミットで同じ結果。再実行で副作用を出さない
- **最小権限**: `permissions` で必要最小限の権限を付与。`write-all` は禁止
- **シークレット外部化**: シークレットは `secrets` 参照のみ。コード・ログに出さない
- **版固定**: actions は `@<commit-sha>` または `@<tag>` で版固定。`@main` は禁止
- **失敗可視化**: ステップ失敗が明確に分かる構造。`if: failure()` で通知
- **タイムアウト**: `timeout-minutes` で無限実行を防止

### 6-2. ワークフロー構造（GitHub Actions例）

```yaml
name: CI
on:
  push:
    branches: [main, 'feature/*']
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  lint:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@<sha>
      - uses: actions/setup-node@<sha>
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run lint

  test:
    needs: lint
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@<sha>
      - uses: actions/setup-node@<sha>
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm test -- --coverage
      - uses: actions/upload-artifact@<sha>
        with:
          name: coverage
          path: coverage/

  build:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<sha>
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@<sha>
        with:
          name: dist
          path: dist/
```

### 6-3. 冪等性の担保

| 項目 | 担保方法 |
|---|---|
| 依存関係 | `npm ci` / `pip install --requirement` でロックファイル使用 |
| ビルド成果物 | 同一コミットから同一アーティファクト。再push不可 |
| デプロイ状態 | デプロイ前に現在状態を確認し、必要なら冪等適用 |
| DB移行 | up/down可逆。再実行で副作用を出さない |
| 並列ジョブ | 共有状態に依存しない。必要なら `needs` で直列化 |

### 6-4. シークレット管理

| 項目 | 方針 |
|---|---|
| 保存 | GitHub Secrets / 外部シークレットマネージャ |
| 参照 | `${{ secrets.NAME }}` のみ。コードに直書きしない |
| ログ | マスクされることを確認。`::add-mask::` で追加マスク |
| ローテーション | 定期的な更新手順を運用手順書に記載 |
| スコープ | 環境（dev/stg/prod）ごとに分離 |

### 6-5. 確認ポイント
- ワークフローが冪等か（再実行で副作用が出ないか）
- 権限が最小化されているか
- actions の版が固定されているか
- シークレットが漏洩しないか
- 失敗時に通知が飛ぶか

## Step 7: デプロイ戦略とロールバック

デプロイの **安全性と復旧速度** を設計する。MTTR目標値（Step 2）を達成できる戦略を選ぶ。

### 7-1. デプロイ戦略の選定

| 戦略 | 特徴 | 適用場面 | ロールバック |
|---|---|---|---|
| **ローリング** | 古い版を順次入れ替え | コンテナ・K8s | 前版に再デプロイ |
| **ブルーグリーン** | 現行/新環境を切り替え | ゼロダウンタイム必須 | 切り替えを戻す（即時） |
| **カナリア** | 少数ユーザーに先行公開 | 大規模・高リスク | 段階的に縮小→前版 |
| **Feature Flag** | 機能ON/OFFをランタイム制御 | 段階リリース・A/B | フラグOFF（即時） |
| **再現デプロイ** | 前版を上書き | 静的サイト・GAS | 前版を再デプロイ |

### 7-2. デプロイメントフロー

```
[アーティファクト取得]
    ↓
[デプロイ先環境の準備]
    ↓
[デプロイ実行]
    ↓
[スモークテスト]
    ↓ (失敗)
[自動ロールバック] ←─── ┐
    ↓ (成功)              │
[監視開始]                │
    ↓ (異常検知)          │
[手動ロールバック] ────────┘
```

### 7-3. ロールバック設計

| 項目 | 設計内容 |
|---|---|
| トリガ | 自動（スモークテスト失敗・監視異常）/ 手動（workflow_dispatch） |
| 手順 | 前版アーティファクトへの再デプロイ / Feature Flag OFF |
| 所要時間 | 目標MTTR以内（Step 2） |
| データ | DB移行の可逆性（down移行）の有無 |
| 検証 | ロールバック後のスモークテスト |

### 7-4. 承認ゲート（必要な場合）

| 項目 | 設計内容 |
|---|---|
| 配置箇所 | ステージング→本番の間 |
| 承認者 | リリース責任者 / 変更承認委員会 |
| 方式 | GitHub Environment Protection Rules / 手動承認ジョブ |
| タイムアウト | 承認待ちの最大時間 |

### 7-5. 確認ポイント
- デプロイ戦略がダウンタイム要件・リスク許容度に合っているか
- ロールバックがMTOR目標時間内に完了するか
- 承認ゲートが過剰でなく、必要十分か
- DB移行の可逆性が確保されているか

## Step 8: パイプラインの検証と最適化

構築したパイプラインを **実際に実行して検証** し、最適化する。

### 8-1. 検証項目

| 検証項目 | 方法 |
|---|---|
| 正常系 | PR作成→CI成功→マージ→デプロイ成功 |
| 異常系 | テスト失敗・Lint違反・ビルド失敗でパイプライン停止 |
| 品質ゲート | カバレッジ閾値下回りで停止 |
| ロールバック | スモークテスト失敗で自動ロールバック |
| 冪等性 | 同じコミットで再実行し同一結果 |
| シークレット | ログにマスクされていることを確認 |
| 権限 | 最小権限で実行されていることを確認 |

### 8-2. パフォーマンス最適化

| 最適化対象 | 手法 |
|---|---|
| 実行時間 | キャッシュ・並列化・テスト分割・incremental build |
| コスト | runner選択（self-hosted / larger runner）・不要ジョブの削除 |
| フィードバック | 失敗時の即時通知・ログの分かりやすさ |
| キャッシュヒット率 | 依存関係キャッシュのキー設計 |

### 8-3. 監視・アラート

| 監視項目 | 手段 |
|---|---|
| パイプライン成功率 | GitHub Insights / カスタムダッシュボード |
| 実行時間 | トレンド監視・異常値検知 |
| デプロイ頻度 | DORA指標の計測 |
| 失敗通知 | Slack / Email / GitHub Discussions |

### 8-4. 確認ポイント
- 正常系・異常系ともに期待通り動くか
- 実行時間が許容範囲か（PRフィードバックは10分以内推奨）
- 失敗時に適切な通知が飛ぶか
- DORA 4 Keys の目標値（Step 2）を達成できそうか

## 付録: よくある落とし穴

| 落とし穴 | 対策 |
|---|---|
| 冪等性を担保しない | Step 6-3 でロックファイル・不変アーティファクト・状態確認を必須化 |
| 権限を広すぎる | Step 6-1 で最小権限を徹底。`write-all` 禁止 |
| actions版を固定しない | Step 6-1 で `@<sha>` または `@<tag>` 固定。`@main` 禁止 |
| シークレットをコードに書く | Step 6-4 で `secrets` 参照のみ。ログマスクを確認 |
| 品質ゲートが緩すぎる | Step 5-1 で必須項目を明示。偽陽性多発は別途調整 |
| 品質ゲートが厳すぎる | 偽陽性が多いゲートは除外・警告化。CI信頼性を損なわない範囲で |
| デプロイ戦略とリスクのミスマッチ | Step 7-1 でダウンタイム要件・リスク許容度に合った戦略を選ぶ |
| ロールバックを設計しない | Step 7-3 でMTTR目標内のロールバックを必ず設計 |
| DB移行の可逆性を忘れる | Step 7-3 でdown移行の有無を確認。不可逆なら別戦略 |
| 検証せず稼働 | Step 8 で正常系・異常系・ロールバックを必ず実行検証 |
| 実行時間を放置 | Step 8-2 でキャッシュ・並列化・テスト分割を適用 |
| 運用手順書を省略 | Step 9 で緊急時・日常時の手順を必ず文書化 |
| DORA指標を計測しない | Step 8-3 で成功率・実行時間・デプロイ頻度を計測 |
| ブランチ戦略とパイプライン不整合 | Step 3 でブランチ戦略とトリガを整合させる |
| 承認ゲートの過不足 | Step 7-4 で必要最小限の承認を配置。過剰承認はリードタイム悪化 |
