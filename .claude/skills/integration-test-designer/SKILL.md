# 結合テスト・E2Eテスト設計 業務フロースキル

このスキルはソフトウェア開発における **結合テストおよびE2Eテスト設計の実行手順を定義** する。
「どこまでを結合テスト対象とするか」「どの結合レベルまで検証するか」「シナリオ網羅の深度をどこに置くか」の価値判断基準は `integration-test-designer` エージェントの職種定義を参照すること。

**前提**: 設計書（system-architect 出力）・実装（code-implementer 出力）・単体テスト設計書（unit-test-designer 出力）が存在する場合は Step 1 で必ず読み込む。未整備の場合は Step 0 で前提を確認してから結合テスト設計に進む。

**必須出力**: 本スキルは以下の3つを必ず作成・出力する。テストコードのみを出力して完了とすることは不可。
1. **結合テスト設計書**（Markdown）— Step 9 の構成に従い、結合レベル・シナリオ・契約検証項目・トレーサビリティを文書化
2. **テストケース**（テスト設計書内の表）— 結合シナリオ・データフロー・IF契約・例外連鎖の各観点で網羅
3. **テストコード**（実装言語のフレームワーク）— FIRST原則・AAA構造に従い、テストケースを自動実装

## 適用する標準手法・フレームワーク

本スキルは以下の確立された手法を組み合わせて実行する。各 Step で明示的に参照し、根拠を示すこと。

| 手法 | 由来 | 適用 Step | 役割 |
|---|---|---|---|
| **Vモデル** | V-Model XT | Step 1, 8 | アーキテクチャ設計↔結合テスト、要件↔E2Eテストの対応関係 |
| **ISTQB シラバス** | ISTQB Foundation / Advanced | Step 3-6 | 結合テスト・システムテスト・E2Eテストの体系 |
| **結合レベル（Integration Levels）** | ISTQB | Step 3 | モジュール間→サブシステム間→システム間の段階的結合 |
| **ビッグバン / トップダウン / ボトムアップ** | ISTQB | Step 3 | 結合戦略。ボトムアップはスタブ不要、トップダウンはスタブ必要 |
| **シナリオテスト** | ISTQB | Step 4 | ユーザージャーニーに沿ったE2E検証 |
| **データフローテスト** | ISTQB | Step 4 | データの生成・使用・破棄の経路検証 |
| **契約テスト (Contract Testing)** | Martin Fowler / Pact | Step 5 | 消費者と提供者のIF契約を独立検証。CDC (Consumer-Driven Contracts) |
| **APIテスト** | REST/GraphQL/gRPC | Step 5 | エンドポイント・ステータスコード・スキーマ・冪等性の検証 |
| **テストピラミッド** | Mike Cohn | Step 3 | 単体>結合>E2E の比率。結合は中間層 |
| **テストトロフィー** | Kent C. Dodds | Step 3 | 統合テストを厚くする現代的指針 |
| **FIRST原則** | xUnit | Step 6 | Fast/Independent/Repeatable/Self-validating/Timely |
| **AAA** | xUnit | Step 6 | Arrange-Act-Assert の構造化 |
| **テストダブル** | Gerard Meszaros | Step 6 | Stub/Spy/Fake/Mock の使い分け。外部依存の隔離 |
| **フィクスチャ管理** | xUnit | Step 6 | テストデータの準備・初期化・後処理 |
| **タグ付け／テストスイート分割** | xUnit | Step 6 | 実行速度・実行タイミング別のスイート分離 |
| **並列実行安全性** | xUnit | Step 6 | テスト間状態共有を排除し並列実行を可能に |
| **トレーサビリティ** | Vモデル / IEEE 830 | Step 8 | 設計→結合テスト、要件→E2Eテストの対応関係 |
| **欠陥ベース** | ISTQB Advanced | Step 7 | 結合部に多い欠陥傾向からテストを補強 |

### Vモデルと本スキルStepの対応

```
アーキテクチャ設計 ───→ Step 1: 設計書の読み込み
                  └──→ Step 3: 結合レベルと戦略の決定
                  └──→ Step 4: 結合シナリオの設計
                  └──→ Step 5: IF契約とデータフローの検証項目
                  └──→ Step 6: テストコードの実装
                  └──→ Step 7: テストの実行と検証
                  └──→ Step 8: 設計とのトレーサビリティ確認
要件定義 ───────────→ Step 4: E2Eシナリオ（ユーザージャーニー）
                  └──→ Step 8: 要件とのトレーサビリティ確認
```

## Step 0: 前提の確認（設計書・実装がない場合）

設計書・実装・単体テスト設計書が未整備の場合、以下の最小限の骨子をユーザーに確認する。整備済みの場合は Step 1 へ。

| 確認項目 | 内容 |
|---|---|
| 結合対象モジュール | どのモジュール間・サブシステム間・外部システム間を結合テストするか |
| IF仕様 | API仕様・データ形式・プロトコル・認証方式 |
| 外部依存 | DB / 外部API / ファイル / メッセージキュー / 時刻 / 乱数 |
| 実行環境 | ローカル / コンテナ / CI / ステージング |
| 品質基準 | 必須シナリオ・実行時間上限・並列実行可否 |

不明点は Step 2 で質問する。system-architect / code-implementer / unit-test-designer スキルの適用を推奨する旨をユーザーに伝えること。

## Step 1: 設計書・実装の読み込みと解釈

設計書・実装・単体テスト設計書を読み込み、結合テスト設計に必要な情報を抽出する。

### 1-1. 抽出項目

| 抽出項目 | 結合テストへの影響 |
|---|---|
| モジュール構成（設計書） | 結合対象の境界・依存関係 |
| IF仕様（API/関数/メッセージ） | 契約検証項目・期待応答 |
| データモデル | データフロー経路・変換点 |
| 状態遷移・ライフサイクル | E2Eシナリオの起点・終点 |
| 非機能要件 | 性能・セキュリティ・可用性の結合検証 |
| 外部依存（設計書） | モック化対象・実物利用の判断 |
| 単体テスト設計書 | 単体テスト済み範囲の確認・重複回避 |

### 1-2. 結合境界の明確化
- 設計書のC4 Container/Component図から結合境界を抽出
- 境界を越えるIFを全て列挙（同期呼び出し・非同期メッセージ・データ共有）
- 各IFの契約（引数・戻り値・例外・タイミング・冪等性）を整理

### 1-3. 確認ポイント
- 設計書にIF契約が過不足なく定義されているか
- 単体テストでカバー済みの範囲と結合テストの責務分担が明確か
- 外部依存のモック化方針（実物 / モック / フェイク）が判断可能か

## Step 2: コンテキスト収集と制約の明示化

実装コード・テスト環境・CI設定・外部依存を収集し、結合テスト設計の前提を固める。

### 収集対象
- 実装コード（結合対象モジュール群）
- 既存の結合テストコード・テストフレームワーク（Jest/Vitest/pytest/Unittest/JUnit/Playwright/Cypress 等）
- CI/CD 設定・テスト実行環境・コンテナ構成
- 外部依存のIF仕様・モックライブラリ・テスト用環境
- 過去の結合部欠陥履歴

### 明示化する制約
- **硬い制約**: テストフレームワーク固定・CI実行時間上限・外部API呼び出し禁止・本番DB接続禁止
- **柔らかい制約**: 結合レベルの深度・モック vs 実物・並列実行の可否

収集結果は **前提条件** として結合テスト設計書に記載する。

## Step 3: 結合レベルと戦略の決定（テストピラミッド・トロフィー）

**テストピラミッド** と **テストトロフィー** に基づき、結合テストの対象レベルと戦略を決定する。

### 3-1. 結合レベルの識別

| 結合レベル | 対象 | 検証内容 | 実行速度 |
|---|---|---|---|
| **モジュール間結合** | 単一モジュール内の関数/クラス間 | 境界を越える呼び出し契約 | 高速 |
| **サブシステム間結合** | 複数モジュールからなるサブシステム間 | IF契約・データ連携 | 中 |
| **システム間結合** | 外部API・DB・メッセージキューとの連携 | プロトコル・認証・エラー処理 | 中〜低速 |
| **E2E（システムテスト）** | ユーザー操作から永続化まで全レイヤ | ユーザージャーニー全体 | 低速 |

### 3-2. 結合戦略の選定

| 戦略 | 特徴 | 適用条件 |
|---|---|---|
| **ボトムアップ** | 下位層から順に結合。スタブ不要 | 下位層が安定している場合 |
| **トップダウン** | 上位層から順に結合。下位はスタブ化 | 上位層の早期検証が必要な場合 |
| **サンドイッチ** | 上位と下位を並行結合。中間層で合流 | 大規模・並行開発可能な場合 |
| **ビッグバン** | 全モジュール完成後に一括結合 | 小規模・単体テストが充分な場合 |

### 3-3. テストピラミッド上の位置付け

```
        E2E（少数・低速・高信頼）
       /                        \
      /  結合テスト（中間層・厚く）  \   ← 本スキルの主戦場
     /                              \
    /    単体テスト（厚く・高速）        \
```

**テストトロフィー指針**: 統合テストを厚くし、E2Eは最小限に抑える。E2Eは脆く・遅く・保守高コストのため。

### 3-4. 優先度付け

| 優先度 | 基準 | 結合レベル |
|---|---|---|
| **S** | 中核業務フロー・金銭計算・セキュリティ境界の結合 | サブシステム間 + E2E |
| **A** | 主要機能のAPI結合・状態遷移を伴う連携 | モジュール間 + サブシステム間 |
| **B** | 補助機能の連携・ユーティリティ結合 | モジュール間 |
| **C** | UI結合・単純CRUD連携 | E2E（最小限） |

## Step 4: 結合シナリオの設計

**シナリオテスト** と **データフローテスト** で結合シナリオを網羅する。

### 4-1. 結合シナリオ（ユーザージャーニー）

ユーザーまたはシステムが開始する一連の処理をシナリオとして記述する。E2Eテストの基本単位。

```
シナリオS-001: ニュース収集→Slack通知
  アクター：GASトリガー（時間主導）
  事前条件：トリガー登録済み・Slackトークン有効
  処理フロー：
    1. トリガー発火 → Main.js がエントリポイント呼び出し
    2. Rss.js がRSS取得 → NewsTopics.js がトピック抽出
    3. AIService.js が要約生成 → EconomicNewsTopics.js が市場指標付与
    4. SlackService.js が通知送信
    5. StorageService.js が実行ログ永続化
  期待結果：
    - Slackチャンネルに通知が投稿される
    - 実行ログがスプレッドシートに記録される
    - トリガーが次回実行予定で再登録される
```

### 4-2. データフローテスト

データが生成・変換・使用・破棄される経路を追跡し、各変換点での整合性を検証する。

| データ項目 | 生成元 | 変換点 | 使用先 | 検証項目 |
|---|---|---|---|---|
| RSS記事 | Rss.js | NewsTopics.js でトピック抽出 | AIService.js | 記事→トピックの対応・欠損なし |
| AI要約 | AIService.js | Prompts.js の指示適用 | SlackService.js | 要約の文字数・フォーマット準拠 |
| 実行ログ | Main.js | StorageService.js で整形 | スプレッドシート | ログ項目の完全性・時刻順 |

### 4-3. 例外連鎖シナリオ

結合部で発生する例外が上位層へどう伝播し、どう回復するかを検証する。

```
シナリオS-010: 外部APIタイムアウト時の挙動
  事前条件：AIService.js のAPI応答を60秒遅延に設定
  処理フロー：
    1. AIService.js がAPI呼び出し → タイムアウト発生
    2. AgentLogic.js がリトライ（最大3回）
    3. 全リトライ失敗 → Main.js がフォールバックメッセージ生成
    4. SlackService.js がエラー通知を投稿
    5. StorageService.js にエラーステータス記録
  期待結果：
    - ユーザーにエラー通知が届く
    - システムが停止しない
    - 次回トリガー実行が継続する
```

### 4-4. 並行・競合シナリオ

並行実行・同時アクセス・重複トリガー時の挙動を検証する。

| シナリオ | 条件 | 期待結果 |
|---|---|---|
| 重複トリガー発火 | 同一時刻に2回トリガー | 排他制御で片方スキップ・重複実行なし |
| 同時API呼び出し | 並列リクエスト | レート制限違反なし・順序保証 |
| 共有リソース競合 | 同一スプレッドシートへ同時書込 | ロック取得・リトライで整合性担保 |

### 4-5. パターン網羅のチェックリスト

- [ ] 全主要ユーザージャーニーをシナリオ化したか
- [ ] 全データフロー経路を網羅したか
- [ ] 全例外連鎖をシナリオ化したか
- [ ] 並行・競合シナリオを検討したか
- [ ] 設計書の全IF契約に対する検証シナリオがあるか
- [ ] 非機能要件（性能・セキュリティ）の結合検証シナリオがあるか

## Step 5: IF契約とデータフローの検証項目

**契約テスト（CDC）** と **APIテスト** でIF契約を検証する。

### 5-1. 契約テスト（Consumer-Driven Contracts）

消費者（呼び出し元）が期待するIF契約を定義し、提供者（呼び出し先）がそれを満たすか検証する。

```
契約C-001: NewsTopics.js → Rss.js
  消費者期待：
    - 関数 fetchFeed(url) が Promise<RssItem[]> を返す
    - RssItem は { title: string, link: string, pubDate: Date } を持つ
    - url が不正な場合、Error を投げる（空配列でない）
  提供者検証：
    - Rss.js の実装が上記契約を満たすか
```

### 5-2. APIテストの検証項目

| 検証項目 | 内容 |
|---|---|
| エンドポイント | URL・HTTPメソッドが仕様通り |
| ステータスコード | 200/400/401/404/500 の使い分け |
| レスポンススキーマ | JSON構造・型・必須項目 |
| リクエストバリデーション | 不正入力時のエラーレスポンス |
| 認証・認可 | トークン有無・権限不足時の挙動 |
| 冪等性 | 同一リクエストの再送で副作用がない |
| ページネーション | 大量データの分割取得 |
| レート制限 | 上限超過時の429応答 |
| タイムアウト | 応答遅延時のクライアント挙動 |

### 5-3. データフロー検証項目

| 検証項目 | 内容 |
|---|---|
| データ整合性 | 変換前後でデータが欠損・破損しない |
| 型変換 | 文字列↔数値↔日付の変換が正確 |
| エンコーディング | マルチバイト・絵文字・制御文字の保持 |
| タイムゾーン | UTC↔ローカル時刻の変換 |
| null/undefined 扱い | 欠損値の伝播・デフォルト値適用 |
| 大量データ | バッチ処理・ストリーミングの境界 |

### 5-4. モック vs 実物の判断基準

| 判断 | 条件 | 理由 |
|---|---|---|
| **実物利用** | ローカルDB・フェイクサーバ・テスト用エンドポイント | 実挙動に近い検証 |
| **モック/スタブ** | 外部有料API・本番環境・応答不安定なサービス | コスト・安定性・速度 |
| **フェイク** | インメモリDB・モックサーバ（WireMock/Mockoon） | 実物に近いが軽量 |
| **契約テスト** | 消費者と提供者が別チーム・別リポジトリ | 契約の乖離を自動検出 |

## Step 6: テストコードの実装

**FIRST原則** と **AAA** に従い、結合テストコードを実装する。

### 6-1. 結合テスト向けFIRST調整

| 原則 | 単体テスト比の調整 |
|---|---|
| **Fast** | E2Eは低速になりがち。重いシナリオはタグ付けでスイート分離し、CIでは軽量スイートを頻回実行 |
| **Independent** | 各シナリオでDB・外部状態を初期化。並列実行安全性を担保 |
| **Repeatable** | 外部APIの応答をモック/録音（VCR等）で固定。時刻は固定クロック注入 |
| **Self-validating** | assert で状態・副作用・ログを検証 |
| **Timely** | 実装と並行して結合テストを追加。後回しは脆化を招く |

### 6-2. フィクスチャ管理

```javascript
// 結合テストのフィクスチャ例
describe('ニュース収集→Slack通知 結合シナリオ', () => {
  beforeEach(async () => {
    // テスト用スプレッドシート初期化
    await resetTestSpreadsheet();
    // Slack API をモック
    mockSlackApi.reset();
    // 時刻を固定
    setSystemClock('2026-08-11T09:00:00Z');
  });

  afterEach(async () => {
    await cleanupTestSpreadsheet();
    restoreSystemClock();
  });

  test('S-001: 正常系 - ニュース収集からSlack通知まで完結', async () => {
    // Arrange
    mockRssFeed('valid-feed.xml');
    mockAiResponse('要約成功');

    // Act
    await Main.runDailyNews();

    // Assert
    expect(mockSlackApi.postedMessages).toHaveLength(1);
    const log = await StorageService.getLatestLog();
    expect(log.status).toBe('success');
  });
});
```

### 6-3. テストダブルの使い分け（結合テスト向け）

| 種類 | 結合テストでの用途 |
|---|---|
| **Stub** | 外部APIの固定応答・エラー応答 |
| **Spy** | 「Slack APIが2回呼ばれた」「DB書込が1回」の検証 |
| **Fake** | インメモリDB・モックHTTPサーバ |
| **Mock** | 「引数Xで1回呼ばれた」契約検証 |
| **VCR/録音** | 外部APIの実応答を録音し再利用（カセット） |

### 6-4. テストスイート分割とタグ付け

実行速度・実行タイミングでスイートを分離する。

| スイート | 実行タイミング | 内容 |
|---|---|---|
| `@fast` | 全コミット | モック中心の結合テスト |
| `@slow` | PRマージ時・夜間 | 実物DB・外部API利用の結合テスト |
| `@e2e` | ステージングデプロイ後 | E2Eシナリオ全体 |
| `@contract` | 提供者変更時 | 契約テスト |

### 6-5. BDD / Gherkin（E2Eシナリオ記述）

```gherkin
Feature: ニュース収集→Slack通知
  Scenario: 正常系 - 朝9時にニュースを収集してSlackに通知する
    Given トリガー時刻が "09:00"
    And RSSフィードが有効
    And Slackトークンが有効
    When Main.runDailyNews() を実行
    Then Slackチャンネル "news" に1件投稿される
    And 実行ログがスプレッドシートに "success" で記録される
```

## Step 7: テストの実行と検証

### 7-1. テスト実行
- 結合テストフレームワークで全シナリオを実行
- 実行時間・失敗シナリオを確認
- カバレッジ（結合カバレッジ・IFカバレッジ）を取得

### 7-2. 欠陥ベースの補強（結合部特有の欠陥傾向）

| 欠陥傾向 | 補強テスト |
|---|---|
| IF契約違反 | スキーマ・型・必須項目の検証 |
| データ形式不整合 | エンコーディング・タイムゾーン・null扱い |
| タイミング・順序 | 非同期処理の完了待ち・順序保証 |
| 部分失敗 | 外部API一部成功時の部分的ロールバック |
| リソース枯渇 | 接続プール・ファイルハンドルの枯渇 |
| 環境差異 | ローカル通過・CI失敗の環境依存 |

### 7-3. 失敗時の対応
- 結合テスト失敗は **実装バグ** / **IF契約違反** / **テスト環境問題** / **テスト誤り** のいずれかを判定
- フレーキー（非決定的）テストは隔離・安定化または除外。放置禁止

- [ ] 設計書の全データフローに対応するテストがあるか

## スキル間連携

- **前段**: `system-architect`（設計書）→ 本スキルが結合境界を抽出
- **前段**: `code-implementer`（実装）→ 本スキルが実装の結合部を検証
- **前段**: `unit-test-designer`（単体テスト設計書）→ 本スキルは単体テスト済み範囲を前提とし重複を避ける
- **後段**: `ci-cd-builder`（CI/CD）→ 本スキルが設計した結合テストをCIに組み込む
- **後段**: `debugger`（デバッグ）→ 結合テスト失敗時の原因特定を委譲
