# 要求分析 業務フロースキル

このスキルはソフトウェア開発における **要求分析の実行手順を定義** する。
「何が必須要件か」「どこまでをスコープに含めるか」の価値判断基準は `requirements-analyzer` エージェントの職種定義を参照すること。

---

## 適用する標準手法・フレームワーク

本スキルは以下の確立された手法を組み合わせて実行する。各Stepで明示的に参照し、根拠を示すこと。

| 手法 | 由来 | 適用Step | 役割 |
|---|---|---|---|
| **REBoK** | Requirements Engineering Body of Knowledge | 全Step | 要求工学プロセスの骨格。要求抽出→分析→仕様化→妥当性確認→管理の5活動を踏襲 |
| **MoSCoW法** | DSDM / Agile | Step 3, 5, 6 | 機能要件の優先度分類（Must / Should / Could / Won't） |
| **Kanoモデル** | 狩野紀昭 | Step 3, 6 | 顧客満足度の観点で要件を分類（当たり前 / 一元 / 魅力 / 無関心 / 逆） |
| **INVEST原則** | Bill Wake (XP) | Step 3, 5 | ユーザーストーリーの品質評価（Independent / Negotiable / Valuable / Estimable / Small / Testable） |
| **SMART基準** | Peter Drucker | Step 5 | 受け入れ基準の品質担保（Specific / Measurable / Achievable / Relevant / Time-bound） |
| **ISO/IEC 25010** | SQuaRE | Step 3, 5 | 非機能要件の8品質特性分類（機能適合性・信頼性・性能効率性・使用性・保守性・移植性・セキュリティ・互換性） |
| **IEEE 830** | IEEE Std 830-1998 | Step 5 | SRS（ソフトウェア要求仕様書）の記述様式。完全・一貫・検証可能・追跡可能・変更容易を担保 |
| **Vモデル** | V-Model XT | Step 5, 6 | 要求→設計→実装→テストの対応関係。各要件に検証活動を紐付ける |
| **CRUDマトリクス** | 構造化分析 | Step 3 | データと機能の対応表。漏れ・重複を検出 |
| **ユースケース記法** | UML | Step 3 | アクターと主シナリオ・例外シナリオで機能を構造化 |

### REBoK 5活動と本スキルStepの対応

```
REBoK 要求抽出  ─┬─→ Step 1: 依頼解釈
                └─→ Step 2: コンテキスト収集
REBoK 要求分析  ───→ Step 3: 要件の分類と構造化
REBoK 要求仕様化 ──→ Step 5: 要件定義書の提示
REBoK 妥当性確認 ──→ Step 6: レビューと合意形成
REBoK 要求管理   ──→ Step 7: 変更管理
```

## Step 1: 依頼の解釈と前提の確認

ユーザーの依頼文を構造化して解釈する。

| 抽出項目 | 確認ポイント |
|---|---|
| 目的 | 何を達成したいか（業務課題・解決したい問題） |
| 対象 | 何を作るか（新規開発 / 改修 / 統合 / 廃止） |
| 利用者 | 誰が使うか（エンドユーザー / 管理者 / システム間） |
| 期待効果 | 成功した状態はどうなるか（定量的・定性的） |
| 暗黙の前提 | 依頼文に書かれていないが前提となっていそうな事項 |

依頼文から読み取れない項目は **不明点リスト** に蓄積し、Step 4 で質問する。

---

## Step 2: コンテキスト収集

既存資産・関連ファイルを読み取り、現状を把握する。

### 収集対象
- 既存コード・設定ファイル（実装改修の場合）
- 関連ドキュメント（README / 仕様書 / 設計書 / 運用手順）
- 既存の類似機能・競合サービス
- ユーザーが過去に提示した制約（セキュリティ・コンプライアンス・予算）

### 確認ポイント
- 既存アーキテクチャとの整合性
- 再利用できるコンポーネント・ライブラリの有無
- 影響を受ける範囲（他システム・他機能への波及）

収集結果は **前提条件** として要件定義書に記載する。

---

## Step 3: 要件の分類と構造化（REBoK 要求分析）

収集した情報を以下の4区分に分類する。**REBoKの要求分析活動** に相当する。

### 3-1. 機能要件（Functional Requirements）
システムが **何をするか** をユーザーストーリー形式で記述する。
**INVEST原則** で各ストーリーの品質を自己評価し、違反があれば書き直す。

```
【US-001】<利用者> は <機能> を使って <目的> を達成できる
  - トリガー：
  - 入力：
  - 出力：
  - 副作用：
  - INVEST自己評価：
    - Independent: ○/×（他ストーリーと依存があるか）
    - Negotiable:  ○/×（実現手段に余地があるか）
    - Valuable:    ○/×（利用者への価値が明確か）
    - Estimable:   ○/×（見積もり可能な粒度か）
    - Small:       ○/×（1スプリントで完了する大きさか）
    - Testable:    ○/×（確認可能な基準があるか）
```

#### ユースケース記法（UML）による補完
複数アクターが関わる、または例外シナリオが重要な機能はユースケースで補完する。

```
UC-001: <ユースケース名>
  アクター：
  事前条件：
  主シナリオ：
    1. アクターが〜する
    2. システムは〜する
    3. ...
  例外シナリオ：
    3a. <異常条件> の場合：
        3a1. システムは〜する
  事後条件：
```

#### CRUDマトリクスによる漏れ検出
データと機能の対応表を作成し、未対応のCRUD操作がないか確認する。

| データ \ 操作 | Create | Read | Update | Delete | 担当US |
|---|---|---|---|---|---|
| <データA> | ○ | ○ | ○ | × | US-001, US-003 |
| <データB> | ○ | ○ | × | × | US-002 |

空欄は意図的除外か要件漏れかを必ず判定する。

### 3-2. 非機能要件（Non-Functional Requirements）
システムが **どう振る舞うか** を **ISO/IEC 25010 (SQuaRE)** の8品質特性で整理する。

| 品質特性 | 記載内容の例 |
|---|---|
| 機能適合性 | 業務ルールへの準拠・計算精度・規格適合 |
| 信頼性 | 稼働率・MTBF・障害時挙動・フォールトトレランス |
| 性能効率性 | 応答時間・スループット・同時接続数・リソース使用量 |
| 使用性 | 学習容易性・アクセシビリティ・UI一貫性・エラー回復性 |
| 保守性 | ログ・監視・デプロイ手順・テスト方針・モジュール性 |
| 移植性 | 環境適応性・データ移行・旧システム廃止・置換容易性 |
| セキュリティ | 認証・認可・暗号化・監査ログ・機密性・完全性 |
| 互換性 | 他システム連携・標準規格準拠・データ交換性 |

### 3-3. 制約条件（Constraints）
変更の余地がない前提を明示する。

- 技術制約（言語・フレームワーク・インフラ・既存システム連携）
- 期間・予算・リソース制約
- 組織・法務・コンプライアンス制約
- 外部依存（API・SaaS・ベンダー）

### 3-4. 対象外（Out of Scope）
**やらないこと** を明示する。スコープクリープを防ぐため最重要。

- 明示的に除外する機能
- 将来対応だが今回スコープ外のもの
- 検討したが見送った案とその理由

### 3-5. 優先度と顧客満足度の二軸評価

各機能要件を **MoSCoW法** と **Kanoモデル** の二軸で評価し、優先度の根拠を明示する。

#### MoSCoW法（開発優先度）
| 分類 | 意味 | 判断基準 |
|---|---|---|
| **Must** | 必須。これがないとリリースできない | 法務・セキュリティ・中核業務フロー |
| **Should** | 重要。Mustの次に優先 | 効率化・UX向上・競合同等機能 |
| **Could** | 可能。余裕があれば対応 | 魅力機能・ニッチ要件 |
| **Won't** | 今回はやらない | 対象外と明示 |

#### Kanoモデル（顧客満足度軸）
| 分類 | 特徴 | 戦略的意味 |
|---|---|---|
| **当たり前（Must-be）** | 不足で不満、あっても満足しない | Must要件の候補 |
| **一元（Performance）** | 充実で満足、不足で不満 | Should要件の候補 |
| **魅力（Excitement）** | ないと不満ではない、あると感動 | Could要件の候補・差別化 |
| **無関心（Indifferent）** | あってもなくても影響なし | Won't要件の候補 |
| **逆（Reverse）** | あると不満 | 対象外・廃止候補 |

#### 二軸マトリクス（各USに必ず付与）
```
US-001:
  MoSCoW: Must
  Kano:   当たり前
  根拠:   <なぜこの分類か1行で>
```

## Step 4: 不明点の特定と質問

Step 1〜3 で蓄積した不明点をユーザーに質問する。

### 質問のルール
- **一度に最大5問**。それ以上は優先度順に絞る。
- **必須か任意か** を各質問に明記する。
- 選択肢がある場合は提示し、自由記述も許可する。
- 「なぜ聞くのか」を1行添える（ユーザーが判断しやすくするため）。
- 推測できるものは推測案を提示し「確認のみ」にする（手戻り削減）。

### 質問テンプレート
```
Q1. [必須/任意] <質問内容>
    理由：<なぜ聞くか>
    推測：<想定される回答>（確認のみでOK）
```

ユーザー回答を得たら Step 3 の要件定義に反映し、新たな不明点が出なければ Step 5 へ進む。

## Step 5: 要件定義書の提示（REBoK 要求仕様化）

**REBoKの要求仕様化活動** に相当する。**IEEE 830** のSRS記述様式（完全・一貫・検証可能・追跡可能・変更容易）に準拠し、以下のフォーマットで要件定義書をMarkdown形式で出力する。省略・変形は禁止。

```markdown
# 要件定義書：{プロジェクト/機能名}

## 1. 概要
- 目的：
- 対象：
- 利用者：
- 期待効果：

## 2. 前提条件
- 既存システム：
- 技術スタック：
- 関連ドキュメント：

## 3. 機能要件
### US-001：<ユーザーストーリー>
- トリガー：
- 入力：
- 出力：
- 副作用：
- 優先度（MoSCoW）：Must / Should / Could / Won't
- 顧客満足度（Kano）：当たり前 / 一元 / 魅力 / 無関心 / 逆
- 根拠：
- INVEST評価：I/N/V/E/S/T 各○×

### US-002：...

## 4. 非機能要件（ISO/IEC 25010 準拠）
| 品質特性 | 要件 | 測定指標 | 目標値 |
|---|---|---|---|
| 機能適合性 | ... | ... | ... |
| 信頼性 | ... | 稼働率 | 99.9%以上 |
| 性能効率性 | ... | 応答時間 | P95 1秒以内 |
| 使用性 | ... | ... | ... |
| 保守性 | ... | ... | ... |
| 移植性 | ... | ... | ... |
| セキュリティ | ... | ... | ... |
| 互換性 | ... | ... | ... |

## 5. 制約条件
- 技術制約：
- 期間・予算：
- 組織・法務：
- 外部依存：

## 6. 対象外（Out of Scope）
- <除外する機能と理由>

## 7. 受け入れ基準（Acceptance Criteria）
### US-001 の受け入れ基準
- [ ] <確認可能な条件1>
- [ ] <確認可能な条件2>
- [ ] <確認可能な条件3>
- SMART評価：S/M/A/R/T 各○×

## 8. トレーサビリティ（Vモデル対応表）
| 要件ID | 設計要素 | 実装モジュール | テストケース | 検証方法 |
|---|---|---|---|---|
| US-001 | 画面A / API X | module_x.py | TC-001〜003 | 単体/結合/E2E |

## 9. 用語集
| 用語 | 定義 |
|---|---|
| ... | ... |

## 10. 未解決事項（Open Issues）
| # | 内容 | 影響度 | 対応期限 |
|---|------|--------|----------|
| 1 | ... | 高/中/低 | 〜 |
```

### 受け入れ基準の書き方（SMART基準 + IEEE 830）
- **Specific（具体的）**：曖昧さのない表現
- **Measurable（測定可能）**：数値・観察で確認できる
- **Achievable（達成可能）**：技術的に実現可能
- **Relevant（関連性）**：該当USの目的と合致
- **Time-bound（期限明確）**：いつまでに、という時間条件があれば明記
- **IEEE 830 準拠**：完全・一貫・検証可能・追跡可能・変更容易

### トレーサビリティの確保（Vモデル）
各要件に **設計→実装→テスト** の対応を付与し、Vモデルの左辺（要求・設計）と右辺（テスト・検証）が1対1で追跡できるようにする。対応の欠落は要件漏れの兆候。

## Step 6: レビューと合意形成（REBoK 妥当性確認）

**REBoKの妥当性確認活動** に相当する。要件定義書を提示後、ユーザーとレビューを行う。

### レビュー観点
- [ ] ユーザーの意図と乖離していないか
- [ ] **MoSCoW法** の Must / Should / Could の分類に納得感があるか
- [ ] **Kanoモデル** で「魅力」要件が過大/過小評価されていないか
- [ ] **INVEST原則** で×の項目がないか（あれば分割・書き直し）
- [ ] **ISO/IEC 25010** の8特性で未検討の品質特性がないか
- [ ] **IEEE 830** の5要件（完全・一貫・検証可能・追跡可能・変更容易）を満たすか
- [ ] **Vモデル** でトレーサビリティに欠落がないか
- [ ] 対象外が過不足ないか
- [ ] 受け入れ基準が **SMART基準** を満たすか
- [ ] 未解決事項の影響度が妥当か

### 合意の確認
修正が落ち着いたら、以下をユーザーに確認する。

```
本要件定義書（vX.X）で合意とみなしてよろしいですか？
合意後は本書をベースに設計・実装へ進みます。
```

合意を得たら、要件定義書を `logs/` または指定フォルダに保存する。
ファイル名：`requirements_<機能名>_<YYYYMMDD>.md`

### テンプレート
本スキルフォルダ内に要件定義書テンプレートを配置済み。出力時は必ずテンプレートをコピーして使用すること。

| テンプレート | パス | 用途 |
|---|---|---|
| 要件定義書 | `templates/requirements-spec-template.md` | Step 5 で出力する要件定義書のひな形（IEEE 830 / ISO 25010 / MoSCoW / Kano / INVEST / SMART / Vモデル準拠） |

### 共通して使える要素（他の設計書テンプレートと共通）
- **メタ情報ヘッダ**: ドキュメントID・バージョン・作成日・レビュー状況
- **変更履歴**: バージョン・日付・変更内容・承認
- **用語集**: プロジェクト固有用語の統一
- **未解決事項**: Open Issues の一覧

### 固有にすべき要素（要件定義書テンプレートを分けた理由）
- MoSCoW法 × Kanoモデルの二軸評価
- INVEST原則によるユーザーストーリー品質評価
- SMART基準による受け入れ基準
- CRUDマトリクスによる漏れ検出
- Vモデル対応表（要件→設計→実装→テスト）
- ISO/IEC 25010 の8品質特性分類

これらは要求分析工程固有の構造であり、基本設計・詳細設計のテンプレート（system-architect スキル所管）とは分離する。

## Step 7: 変更管理（REBoK 要求管理・要件変更が発生した場合）

**REBoKの要求管理活動** に相当する。合意後に要件変更が発生した場合は以下を守る。

1. 変更内容と **理由** を記録する
2. 影響範囲（スケジュール・コスト・他要件への波及）を評価する
2. 影響範囲（スケジュール・コスト・他要件への波及）を評価する
3. ユーザー合意を得てから要件定義書の該当箇所を更新する
4. バージョンを上げ、変更履歴を末尾に追記する

### 変更履歴フォーマット
```markdown
## 変更履歴
| 版 | 日付 | 変更内容 | 理由 | 承認 |
|----|------|----------|------|------|
| 1.0 | 2026-08-11 | 初版 | 新規作成 | - |
| 1.1 | 2026-08-15 | US-003を追加 | 仕様変更 | ユーザー承認済 |
```

---

## 運用メモ

- **推測と確認の分離**：推測できることは推測案を提示し「確認のみ」にすることで、ユーザーの負担を下げる
- **対話は最小限**：1度の質問で複数項目をまとめて聞き、往復回数を減らす
- **文書は生き物**：合意後も変更管理を怠らない。暗黙の前提が顕在化したら即メモ
- **トレーサビリティ**：各要件にID（US-001等）を付与し、設計・実装・テストまで追跡可能にする
