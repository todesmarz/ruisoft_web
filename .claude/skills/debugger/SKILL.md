# デバッグ 業務フロースキル

このスキルはソフトウェア開発における **トラブルシューティングの実行手順を定義** する。
「何を根本原因とするか」「修正範囲をどこまで広げるか」「再発防止策を必須とするか」の価値判断基準は `debugger` エージェントの職種定義を参照すること。

**前提**: 設計書（system-architect 出力）やテスト設計書（unit-test-designer 出力）が存在する場合は Step 1 で必ず読み込み、期待動作の基準として用いる。未整備の場合は Step 0 で仕様の骨子を確認してからデバッグに進む。

**必須出力**: 本スキルは以下の3つを必ず作成・出力する。修正コードのみを出力して完了とすることは不可。
1. **デバッグ報告書**（Markdown）— Step 9 の構成に従い、症状・再現手順・根本原因・修正内容・検証結果・再発防止策を文書化
2. **修正コード**（既存ファイルへの差分）— 根本原因に対する最小限の修正。対症療法のみで完了とすることは不可
3. **再発防止策**（テスト追加・監視・ドキュメント更新のいずれか）— 同一欠陥クラスの再発を防止する仕組み

## 適用する標準手法・フレームワーク

本スキルは以下の確立された手法を組み合わせて実行する。各 Step で明明示的に参照し、根拠を示すこと。

| 手法 | 由来 | 適用 Step | 役割 |
|---|---|---|---|
| **科学的方法（仮説検証）** | Karl Popper | Step 3-5 | 観察→仮説→実験→検証の反復。直感で飛ばさず反証可能な仮説を立てる |
| **根本原因分析 (RCA)** | 産業安全 / ITIL | Step 5 | 表層症状でなく根本原因を特定。5W分析・なぜなぜ分析を活用 |
| **なぜなぜ分析（5W）** | Toyota 生産方式 | Step 5 | 「なぜ」を5回繰り返し根本原因に到達。早期に「人のミス」で打ち切らない |
| **魚骨図（特性要因図）** | Ishikawa | Step 3 | 原因候補を4M（Man/Machine/Material/Method）で網羅的に分類 |
| **二分探索デバッグ** | Jon Bentley | Step 4 | コードを半分ずつ絞り込み原因箇所を特定。大規模コードで有効 |
| **最小再現ケース** | ソフトウェア工学 | Step 2 | バグを再現する最小の入力・手順。ノイズを排除し原因を孤立 |
| **ログ分析** | SRE / Observability | Step 4 | 構造化ログ・タイムスタンプ・相関IDで時系列追跡 |
| **メンタルモデルデバッグ** | Andy Hunt | Step 3-4 | コードが「どう動くべきか」の頭の中のモデルと実装の差を突き止める |
| **ラバーダッキング** | ソフトウェア工学 | Step 3 | 問題を第三者に説明するふりをして暗黙前提を顕在化 |
| **デバッガ活用（ステップ実行）** | gdb / IDE | Step 4 | ブレークポイント・ウォッチ・ステップ実行で実行時状態を観察 |
| **差分デバッグ（git bisect）** | Git | Step 4 | コミット履歴から欠陥導入ポイントを二分探索で特定 |
| **バグ分類（Boehm / ISTQB）** | ISTQB | Step 1, 5 | 欠陥を重大度・優先度・種類で分類し対応順序を決定 |
| **ポストモーテム（ブラウント分析）** | SRE | Step 8 | 非難なしに事実ベースで再発防止策を策定 |
| **複雑度・結合度分析** | ソフトウェア工学 | Step 6 | 修正影響範囲を定量化。高結合箇所は副作用リスクが高い |
| **回帰テスト** | ISTQB | Step 7 | 修正が他の機能を破壊していないことを検証 |
| **防御的プログラミング** | ソフトウェア工学 | Step 8 | 契約条件・入力検証・フェイルファストで再発を防ぐ設計 |

### 科学的方法と本スキルStepの対応

```
観察（症状）   ───→ Step 1: 症状の聞き取りと分類
              └──→ Step 2: バグの再現と最小化
仮説立案       ───→ Step 3: 原因仮説の立案
実験・検証     ──┬─→ Step 4: 仮説の検証（ログ・デバッガ・二分探索）
                └─→ Step 5: 根本原因の特定（RCA・なぜなぜ分析）
結論（修正）   ───→ Step 6: 修正案の作成と影響範囲分析
              └──→ Step 7: 修正の検証（回帰テスト）
再発防止       ───→ Step 8: 再発防止策の策定
報告           ───→ Step 9: デバッグ報告書の作成
```

## Step 0: 仕様の確認（設計書・テスト設計書がない場合）

設計書やテスト設計書が未整備の場合、以下の最小限の骨子をユーザーに確認する。整備済みの場合は Step 1 へ。

| 確認項目 | 内容 |
|---|---|
| 期待動作 | 本来どう動くべきか（仕様・要件） |
| 実際の動作 | 現在どう動いているか（症状） |
| 環境 | OS / ランタイム / ライブラリ版 / 実行コンテキスト |
| 再現性 | 常に発生 / 特定条件のみ / 再現不能 |

期待動作が不明確な場合は **不明点リスト** に蓄積し、Step 9 でユーザーに確認する。

---

## Step 1: 症状の聞き取りと分類

バグ報告・エラーメッセージ・不具合報告を読み込み、**症状を構造化** する。曖昧な報告はここで整理する。

### 1-1. 症状の構造化テンプレート
```
報告元：      {ユーザー/システム/ログ/監視}
症状：        {何が起きているかの1文}
期待動作：    {本来どうあるべきか}
実際の動作：  {現在どうなっているか}
環境：        {OS/ランタイム/版/実行コンテキスト}
再現性：      {常に/条件付き/再現不能}
重大度：      {致命命/高/中/低}
優先度：      {即時/早急/通常/低}
```

### 1-2. バグ分類（ISTQB / Boehm）

| 分類軸 | 例 |
|---|---|
| 種類 | 機能欠陥 / 性能欠陥 / インターフェース欠陥 / データ欠陥 / 文書欠陥 |
| 重大度 | 致命的（システム停止）/ 高（主要機能不可）/ 中（代替手段あり）/ 低（軽微） |
| 優先度 | 即時（業務停止）/ 早急（重大）/ 通常（次リリース）/ 低（機会あれば） |
| 発見経路 | ユーザー報告 / 自動テスト / レビュー / 本番監視 |

### 1-3. 確認ポイント
- 報告に主観・推測が混ざっていないか（事実と推量を分離）
- エラーメッセージ・スタックトレースの原文を保持しているか
- 発生タイミング（初回 / 特定操作後 / 負荷時 / 期間経過後）が記録されているか

---

## Step 2: バグの再現と最小化

**再現できないバグは直せない**。まず確実に再現する手順を確立し、次にノイズを削って最小再現ケースを作る。

### 2-1. 再現手順の確立
- 報告された手順をそのまま実行し、症状が再現するか確認
- 再現しない場合は環境差（OS / 版 / データ / ネットワーク / 権限）を網羅的に比較
- 再現性が不安定な場合は、発生条件を変数として実行回数を重ねる

### 2-2. 最小再現ケースの作成
- 関連しない入力・処理・UI操作を順に削除し、症状が維持されるか確認
- 外部依存（DB / API / ファイル）をスタブ化できないか検討
- 最小ケースが作れたら **必ずテストコード化** し、Step 7 の回帰テストに流用

### 2-3. 再現記録のテンプレート
```
再現手順：
  1. {前提条件}
  2. {操作手順}
  3. {観察される症状}
最小再現ケース：
  入力：{最小入力}
  期待：{期待出力}
  実際：{実際の出力}
再現率：{n/m 回}
```

再現不能な場合は Step 9 で「再現不能バグ」として扱い、観察可能なログ・監視の強化を再発防止策に含める。

---

## Step 3: 原因仮説の立案

症状から **反証可能な仮説** を複数立てる。単一仮説で飛ばさず、候補を網羅してから優先順位を付ける。

### 3-1. 魚骨図（Ishikawa）による原因候補の網羅

| 4M | 原因候補の例 |
|---|---|
| **Man（人）** | 誤操作 / 権限不足 / ドキュメント誤読 |
| **Machine（機械）** | ランタイム版 / OS差異 / リソース不足 / 時刻同期ズレ |
| **Material（材料）** | 入力データ不整 / 外部API応答 / 設定ファイル / 言語・ロケール |
| **Method（方法）** | アルゴリズム誤り / 状態遷移漏れ / 並行処理競合 / エラーハンドリング欠落 |

### 3-2. 仮説の記述形式
```
仮説H1: {原因} が起きているため、{症状} が発生する
検証方法: {ログ/デバッガ/テストでどう確認するか}
確度: {高/中/低}
検証コスト: {低/中/高}
```

### 3-3. 仮説優先順位の付け方
1. 確度が高く検証コストが低いものから検証
2. 確度が低くても検証コストが極めて低いものは先に潰す
3. 確度が高く検証コストが高いものは、低コスト仮説を全て潰してから着手

### 3-4. よくある暗黙前提（ラバーダッキングで顕在化）
- 「この関数は呼ばれないはず」→ 実際は呼ばれている
- 「この変数は初期化されているはず」→ 未初期化パスが存在
- 「外部APIは常に成功する」→ タイムアウト・空応答を想定していない
- 「同期的に実行される」→ 非同期の競合が発生

---

## Step 4: 仮説の検証

立てた仮説を **観察可能な証拠** で検証する。推測で確定させず、必ずログ・デバッガ・テストのいずれかで裏付ける。

### 4-1. ログ分析
- 発生前後のログを時系列で取得（構造化ログ・タイムスタンプ・相関ID）
- エラーレベルのログだけでなく、前後の INFO / DEBUG ログも確認
- ログが不足している場合は **一時的にログを追加** して再現（Step 2 に戻る）

### 4-2. デバッガ活用
- ブレークポイントを症状発生箇所とその上流に設定
- ウォッチ式で変数の遷移を観察
- ステップ実行で制御フローが期待通りか確認
- 条件付きブレークポイントで再現条件下でのみ停止

### 4-3. 二分探索デバッグ
- コードを論理的に半分に分割し、どちら側で症状が発生するか絞り込み
- `git bisect` でコミット履歴から欠陥導入ポイントを特定
- 大規模変更の場合はコミットを分割してから bisect する

### 4-4. 検証結果の記録
```
仮説H1: 検証結果 = {確認/否定}
  証拠: {ログ行 / デバッガ観察 / テスト結果}
  結論: {原因として採用/却下}
```

### 4-5. 確証バイアスの回避
- 自分の仮説を支持する証拠だけでなく、**反証となる証拠** を積極的に探す
- 「直感と違う」観察を見逃さず、それを新たな仮説に組み込む

---

## Step 5: 根本原因の特定（RCA）

Step 4 で特定した直接原因に対し、**なぜなぜ分析（5W）** で根本原因まで遡る。対症療法で終わらせない。

### 5-1. なぜなぜ分析の実行

```
症状: {Step 1 の症状}
  なぜ1: {直接原因} ── Step 4 で特定
    なぜ2: {なぜ1が起きた理由}
      なぜ3: {なぜ2が起きた理由}
        なぜ4: {なぜ3が起きた理由}
          なぜ5: {根本原因 ─ プロセス/設計/知識の欠落}
```

### 5-2. 根本原因の分類

| 分類 | 例 | 再発防止の方向 |
|---|---|---|
| **コード欠陥** | ロジック誤り・未初期化・型不一致 | 修正 + テスト追加 |
| **設計欠陥** | 仕様漏れ・状態遷移未定義・IF不明確 | 設計見直し + 仕様書更新 |
| **知識欠落** | API誤解・言語仕様誤解 | ドキュメント・レビュー基準の更新 |
| **プロセス欠陥** | レビュー漏れ・テスト未網羅 | テスト設計・レビュープロセスの改善 |
| **環境欠陥** | 版差異・設定ミス | 環境管理・IaC化・起動時検証 |

### 5-3. 確認ポイント
- 「人のミス」で打ち切っていないか（なぜ5まで掘る）
- 根本原因が複数ある場合は全て記録（単一原因前提を避ける）
- 根本原因が他の箇所にも潜む可能性を検討（同種欠陥の横展開）

---

## Step 6: 修正案の作成と影響範囲分析

根本原因に対する **最小限かつ本質的な修正** を設計する。対症療法（症状を隠すだけの修正）は不可。

### 6-1. 修正方針の決定

| 修正の種類 | 採用基準 |
|---|---|
| 根本修正 | 根本原因を直接解消。原則これを採用 |
| 暫定修正 | 本番停止中など緊急時のみ。後追いで根本修正を必須化 |
| 緩和策 | 根本修正が困難な場合。影響を縮小する仕組み |

### 6-2. 影響範囲分析
- 修正対象関数・クラスの **呼び出し元** を全て列挙（grep / LSP references を活用）
- 修正が契約（事前条件・事後条件・不変条件）を変更するか確認
- 高結合・高サイクロマティック複雑度の箇所は副作用リスクが高い
- 並行処理・状態遷移が絡む場合はデッドロック・競合の再検討

### 6-3. 修正案の記述形式
```
修正対象: {ファイル:関数}
根本原因: {Step 5 の根本原因}
修正内容: {何をどう変えるか}
修正の根拠: {なぜこの修正で根本原因が解消されるか}
影響範囲: {呼び出し元一覧・副作用リスク}
代替案: {検討したが却下した案と却下理由}
```

### 6-4. 確認ポイント
- 修正が小さすぎて根本原因を残していないか
- 修正が大きすぎて新たな欠陥を混入していないか
- 既存のテストが修正後も通るか（Step 7 で検証）

---

## Step 7: 修正の検証（回帰テスト）

修正が **症状を解消し、かつ他の機能を破壊していない** ことを検証する。

### 7-1. 検証項目

| 検証項目 | 方法 |
|---|---|
| 症状の解消 | Step 2 の最小再現ケースが再現しなくなったか |
| 期待動作の達成 | 設計書・テスト設計書の期待値を満たすか |
| 既存テストの通過 | 既存の単体テスト・統合テストが全て通るか |
| 回帰テスト | 修正前後でテストスイート全体を実行し差分を確認 |
| 境界・例外 | 修正が境界値・例外パスに影響していないか |
| 並行・状態 | 並行処理・状態遷移のテストが通るか |

### 7-2. テストの追加
- Step 2 の最小再現ケースを **回帰テストとして恒久化** する
- 根本原因と同種の欠陥が他の入力で発生しないか、プロパティベーステストで補強
- 修正で新たに保証すべき契約があれば、それを検証するテストを追加

### 7-3. 検証結果の記録
```
症状の解消: {確認/未解消}
既存テスト: {全通過/失敗n件}
追加テスト: {新規m件、全通過}
副作用: {確認された副作用/なし}
```

症状が解消されない、または既存テストが失敗する場合は Step 3 に戻り仮説を再検討する。

---

## Step 8: 再発防止策の策定（ポストモーテム）

**同じバグを二度と出さない仕組み** を設計する。非難ではなく事実ベースで策定する（ブラウント分析）。

### 8-1. 再発防止策の候補

| 手段 | 適用場面 | 効果 |
|---|---|---|
| **テスト追加** | コード欠陥・回帰リスク | 同一入力での再発を自動検出 |
| **プロパティベーステスト** | 同種欠陥の横展開 | 不変条件の乱れを広範に検出 |
| **契約表明（事前/事後条件）** | IF不明確・型不一致 | 実行時検証で早期発見 |
| **入力検証・フェイルファスト** | 不正入力・未初期化 | 不正状態を早期に表面化 |
| **静的解析・Lint強化** | 言語仕様誤解・型欠陥 | コミット前に自動検出 |
| **ログ・監視の強化** | 再現困難・本番限定 | 次回発生時の原因切り分けを迅速化 |
| **設計・仕様書の更新** | 設計欠陥・知識欠落 | 暗黙前提を明文化し認識ズレを防止 |
| **レビュー基準の更新** | プロセス欠陥 | 同種欠陥がレビューで弾かれるよう基準化 |
| **CI/CDゲート追加** | 継続的品質保証 | 修正テストがCIで必ず実行されるよう担保 |

### 8-2. 再発防止策の記述形式
```
根本原因の分類: {Step 5-2 の分類}
再発防止策:
  1. {策} ─ {効果} ─ {実施期限}
  2. ...
横展開候補: {同種欠陥が潜む他モジュール}
```

### 8-3. 確認ポイント
- 再発防止策が「気をつける」で終わっていないか（仕組み化されているか）
- 根本原因の分類に合った手段を選んでいるか（コード欠陥にプロセス改善だけ、等のミスマッチを避ける）
- 実施期限・担当が明確か

## Step 9: デバッグ報告書の作成

Step 1〜8 の成果を **デバッグ報告書** としてMarkdownで出力する。これが本スキルの主成果物。

### 9-1. 報告書の構成

```markdown
# デバッグ報告書: {症状の1行要約}

## 1. 概要
- 報告日: {YYYY-MM-DD}
- 報告元: {ユーザー/システム/監視}
- 重大度: {致命的/高/中/低}
- 優先度: {即時/早急/通常/低}
- ステータス: {解消/暫定対応/調査中}

## 2. 症状
{Step 1 の構造化テンプレート}

## 3. 再現手順
{Step 2-3 の再現記録}
- 最小再現ケース: {入力/期待/実際}

## 4. 根本原因
{Step 5 のなぜなぜ分析}
- 直接原因: {なぜ1}
- 根本原因: {なぜ5}
- 分類: {コード/設計/知識/プロセス/環境}

## 5. 修正内容
{Step 6 の修正案}
- 修正対象: {ファイル:関数}
- 修正の根拠: {なぜこれで根本原因が解消されるか}
- 影響範囲: {呼び出し元一覧}

## 6. 検証結果
{Step 7 の検証記録}
- 症状の解消: {確認}
- 既存テスト: {全通過/失敗n件}
- 追加テスト: {新規m件}

## 7. 再発防止策
{Step 8 の再発防止策}
- 横展開候補: {同種欠陥が潜む他モジュール}

## 8. 添付資料
- エラーログ: {パスまたは抜粋}
- スタックトレース: {抜粋}
- 修正差分: {git diff 抜粋}
- 追加テストコード: {パス}
```

### 9-2. 報告書の保存先
- プロジェクトの `logs/` ディレクトリ、または専用の `debug/` ディレクトリ
- ファイル名: `debug_{症状の短縮形}_{YYYY-MM-DD}.md`
- 例: `debug_news_topics_market_diff_2026-08-11.md`

### 9-3. 確認ポイント
- 第三者が報告書だけで原因と修正を追跡できるか
- 推測と事実が明確に区別されているか
- 修正コード・テストコード・再発防止策が過不足なく記載されているか

---

## 付録: よくある落とし穴

| 落とし穴 | 対策 |
|---|---|
| 症状を直して根本原因を残す | Step 5 のなぜなぜ分析を必ず実行 |
| 単一仮説で飛ばす | Step 3 で複数仮説を網羅してから検証 |
| 確証バイアス | Step 4-5 で反証を積極的に探す |
| 修正が大きすぎる | Step 6 で最小修正を意識、影響範囲を明示 |
| 回帰テストを省略 | Step 7 で既存テスト全件実行を必須化 |
| 「気をつける」で終わる | Step 8 で仕組み化された再発防止策を策定 |
| 再現不能で放置 | Step 2 で再現不能なら監視強化を再発防止策に含める |
| 環境差を見落とす | Step 1 で環境を構造化記録、Step 2 で比較 |
