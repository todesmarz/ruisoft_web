# 技術ドキュメント作成 業務フロースキル

このスキルは **ソフトウェア開発に付随する技術ドキュメントを作成する手順を定義** する。
「読者に合わせてどこまで詳しく書くか」「どの情報を含めどの情報を省くか」「どう構成するか」の価値判断基準は `tech-doc-writer` エージェントの職種定義を参照すること。

---

## 🔄 全体フロー

```
Phase 1: ドキュメント要件の把握（読者・目的・種別・対象システム）
    ↓
Phase 2: 対象システムの調査・情報収集
    ↓
Phase 3: ドキュメント構成の設計（読者別テンプレート選択）
    ↓
Phase 4: ドキュメント執筆
    ↓
Phase 5: レビュー・検証（用語統一・読者レベル適合性・網羅性）
    ↓
Phase 6: 保存・公開
```

---

## 適用する標準手法・フレームワーク

| 手法 | 由来 | 適用 Phase | 役割 |
|---|---|---|---|
| **Diátaxis** | Daniele Procida | Phase 1, 3 | ドキュメントを4つの目的（tutorial/how-to/reference/explanation）に分類。読者ニーズに基づく構成設計 |
| **Minimalism** | John Carroll | Phase 4 | 最小限の説明で実行可能にする原則。冗長な説明より手順の明示を優先 |
| **Information Mapping** | Robert Horn | Phase 3, 4 | 情報をチャンク化し、ラベル付きブロックで構造化。読みやすさと検索性の向上 |
| **Plain Language** | 米連邦政府 | Phase 4 | 平易な言葉で書く原則。専門用語の定義・能動態の使用・短文の推奨 |
| **OpenAPI Specification** | OpenAPI Initiative | Phase 4 | API仕様書の標準フォーマット（旧Swagger） |
| **Diagrams as Code** | Mermaid/PlantUML | Phase 4 | テキストから図を生成。アーキテクチャ図・シーケンス図・ER図の保守性向上 |
| **ARC (Architecture-Readable-Code)** | ソフトウェア文書化 | Phase 4 | コードとドキュメントの一致を保つ原則。コード変更時にドキュメントも更新しやすい構造 |
| **User Story Mapping** | Jeff Patton | Phase 3 | ユーザーマニュアルの構成をユーザージャーニーに沿って設計 |
| **Google Developer Documentation Style Guide** | Google | Phase 4 | 技術ドキュメントの文体・用語・トーンの標準 |
| **Write the Docs principles** | Write the Docs コミュニティ | Phase 4 | ドキュメントの品質原則（正確・最新・検索可能・親しみやすい） |

## Phase 1: ドキュメント要件の把握

ユーザーからドキュメント作成の要件を聞き出す。以下を明確にする。不明点は質問して埋める。曖昧なまま進めない。

### 1.1 読者の特定

ドキュメントの読者を特定する。読者によって情報の粒度・用語レベル・構成が大きく変わる。

| 読者層 | 想定読者 | 求められる内容 |
|---|---|---|
| **プロジェクト外の方** | 顧客・取引先・非技術者 | プロジェクトの概要・目的・価値。技術的詳細は最小限 |
| **エンドユーザー** | 実際にシステムを使う人 | 操作手順・画面説明・トラブル対応。専門用語は避ける |
| **導入者** | システムを導入・設定する人 | セットアップ手順・設定項目・環境要件 |
| **開発者** | システムを開発・拡張する人 | API仕様・アーキテクチャ・コード構成・拡張方法 |
| **運用者** | システムを運用・監視する人 | 運用手順・監視項目・障害対応・リカバリ手順 |
| **チーム内** | プロジェクトメンバー | ナレッジベース・意思決定記録・開発規約・ノウハウ |

### 1.2 ドキュメント種別の特定

以下のいずれかを特定する。明示されていない場合は読者と目的から推定し、ユーザーに確認する。

| 種別ID | 種別名 | 想定読者 | 主な内容 |
|---|---|---|---|
| `overview` | プロジェクト説明資料 | プロジェクト外の方 | プロジェクト概要・目的・機能一覧・価値・スクリーンショット |
| `user-manual` | ユーザーマニュアル | エンドユーザー | 操作手順・画面説明・FAQ・トラブルシューティング |
| `setup-guide` | セットアップガイド | 導入者 | 前提条件・インストール手順・設定項目・動作確認 |
| `api-spec` | API仕様書 | 開発者 | エンドポイント・リクエスト/レスポンス・認証・エラー一覧 |
| `runbook` | 運用手順書・ランブック | 運用者 | 定常運用・監視項目・障害対応フロー・リカバリ手順 |
| `wiki` | wiki・ナレッジベース | チーム内 | 意思決定記録・開発規約・ノウハウ・FAQ・用語集 |
| `architecture` | アーキテクチャドキュメント | 開発者 | システム構成図・モジュール構成・データフロー・技術選定理由 |

### 1.3 その他の要件確認

- **目的**: 読者がドキュメントを読んだ後に何ができるようになるか・何を理解するか
- **対象システム**: どのプロジェクト・モジュール・機能のドキュメントか
- **形式**: Markdown / OpenAPI（YAML） / HTML / PDF 等
- **既存ドキュメント**: 既にドキュメントがある場合は更新か新規作成か
- **制約**: 文字数制限・ページ制限・納期・必須項目

## Phase 2: 対象システムの調査・情報収集

Phase 1 で特定した対象システムについて、ドキュメント作成に必要な情報を収集する。

### 2.1 ソースコード・設定ファイルの読込

- README・既存ドキュメントの確認
- ソースコード構成（ディレクトリ構造・主要モジュール）
- 設定ファイル（package.json / requirements.txt / .env.example 等）
- コード内のコメント・JSDoc・docstring

### 2.2 設計書・要件定義書の確認

前段工程の成果物が存在する場合は読み込む。
- 要件定義書（requirements-analyzer 出力）→ 機能一覧・非機能要件の把握
- システム設計書（system-architect 出力）→ アーキテクチャ・モジュール構成・IF仕様の把握
- 実装報告書（code-implementer 出力）→ 実装内容・テスト結果の把握

### 2.3 実行・動作確認（可能な場合）

- セットアップガイド・運用手順書の場合は、実際に手順を追って検証する
- API仕様書の場合は、エンドポイントを実際に叩いてレスポンスを確認する
- ユーザーマニュアルの場合は、画面操作を追ってスクリーンショットを撮る

### 2.4 関係者へのヒアリング（必要な場合）

- 不明点はユーザー・開発者・運用者に質問する
- 想定読者にインタビューしてニーズを把握する

## Phase 3: ドキュメント構成の設計

読者と種別に応じた構成を設計する。以下のテンプレートを基準とし、対象システムの特性に合わせて調整する。

### 3.1 プロジェクト説明資料（`overview`）の構成

```markdown
# <プロジェクト名>

## 概要
- 一言で何ができるか
- 解決する課題

## 目的・背景
- なぜこのプロジェクトがあるか

## 主な機能
- 機能一覧（3〜7個）

## システム構成（簡易）
- 構成図（Mermaid等）
- 使用技術スタック（一覧）

## スクリーンショット・デモ
- 画面キャプチャ・GIF

## 導入効果・価値
- 期待される効果

## お問い合わせ・リンク
- 連絡先・関連リポジトリ・ライセンス
```

- 確認方法

## 用語集

## 詳細セットアップ

### 3.4 API仕様書（`api-spec`）の構成

OpenAPI Specification（YAML）を推奨。Markdown形式のサマリを併用する。

```yaml
openapi: 3.0.3
info:
  title: <API名>
  version: <バージョン>
  description: <API概要>
servers:
  - url: <ベースURL>
    description: <環境>
paths:
  /<エンドポイント>:
    get/post/put/delete:
      summary: <概要>
      description: <詳細説明>
      parameters: ...
      requestBody: ...
      responses:
        '200':
          description: <成功時の説明>
          content: ...
        '4xx'/'5xx':
          description: <エラー時の説明>
components:
  securitySchemes: ...
  schemas: ...
```

Markdownサマリの構成:
```markdown
# <API名> API仕様書

## 概要
## 認証方式
## 共通仕様（ベースURL・エラーレスポンス形式・レートリミット）
## エンドポイント一覧
### <エンドポイント1>
### <エンドポイント2>
## データモデル
## 変更履歴
```

## Phase 4: ドキュメント執筆

Phase 3 で設計した構成に従って執筆する。

### 4.1 執筆の基本原則

- **読者レベルに合わせる**: 想定読者が知らない専門用語は定義するか避ける
- **能動態で書く**: 「〜されます」でなく「〜する」
- **手順は番号付きで**: 読者が順番に追えるようにする
- **スクリーンショット・図を活用**: 文字だけで伝わらない場合は図解する
- **コード例は実行可能に**: 読者がコピーして動かせる状態にする
- **最新状態を維持しやすい構成**: コードと密結合しすぎない。変更があった際に更新しやすい構造にする

### 4.2 用語統一

- ドキュメント内で用語を統一する（例：「ユーザー」と「利用者」を混在させない）
- 専門用語集を付ける場合は本文の初出時にリンクを張る
- 略語は初出時に正式名称と併記する（例：CI/CD（Continuous Integration / Continuous Deployment））

### 4.3 図表の作成

- 構成図・シーケンス図・ER図は Mermaid 記法で記述する（テキストベースで保守しやすいため）
- スクリーンショットは `images/` 配下に保存し、相対パスで参照する
- 図にはキャプション（「図1: 〜」）を付ける

### 4.4 コード例の記述

- 実行可能なコード例を提供する
- コードブロックには言語を明記する（```python / ```javascript 等）
- 必要に応じてコメントを付ける

## Phase 5: レビュー・検証

執筆したドキュメントを以下の観点で検証する。

### 5.1 読者レベル適合性

- 想定読者が理解できない専門用語が使われていないか
- 読者がドキュメントを読んだ後に目的を達成できるか
- 情報の粒度は読者に適しているか（詳細すぎる・粗すぎる）

### 5.2 網羅性

- 対象システムの主要機能・構成要素が網羅されているか
- 読者がやりたい操作の手順が漏れなく記載されているか
- トラブルシューティングでよくある問題がカバーされているか

### 5.3 正確性

- ソースコード・設定ファイル・実際の動作と一致しているか
- コード例は実行可能か
- リンク・パス・コマンドが正しいか

### 5.4 保守性

- コード変更時にドキュメントも更新しやすい構造か
- 図表はテキストベース（Mermaid等）で保守しやすいか
- バージョン・更新日が明記されているか

### 5.5 検索性

- 目次・見出し構造が適切で、読者が目的の情報を見つけやすいか
- 用語集・インデックスがあるか（長文の場合）

### 5.6 検証結果の記録

問題があれば是正する。重大な問題がない場合は Phase 6 へ。

## Phase 6: 保存・公開

### 6.1 保存先の規約

| ドキュメント種別 | 保存先 | ファイル名規約 |
|---|---|---|
| `overview` | リポジトリルート | `README.md` または `docs/overview.md` |
| `user-manual` | `docs/` | `docs/user-manual.md` |
| `setup-guide` | リポジトリルート または `docs/` | `SETUP.md` または `docs/setup-guide.md` |
| `api-spec` | `docs/` または `api/` | `docs/openapi.yaml` + `docs/api-summary.md` |
| `runbook` | `docs/` | `docs/runbook.md` |
| `wiki` | `docs/wiki/` または `docs/` | `docs/wiki/<topic>.md` |
| `architecture` | `docs/` | `docs/architecture.md` |

※既存のディレクトリ構成がある場合はそれに従う。`AGENTS.md` のディレクトリ構成を参照すること。

### 6.2 フロントマター

各ドキュメントの先頭に以下のメタデータを付与する（Jekyll対応の場合）。

```yaml
---
title: <ドキュメントタイトル>
description: <概要>
last_updated: <YYYY-MM-DD>
document_type: <overview/user-manual/setup-guide/api-spec/runbook/wiki/architecture>
target_audience: <プロジェクト外の方/エンドユーザー/導入者/開発者/運用者/チーム内>
---
```

### 6.3 公開・通知

- ドキュメントを保存したら、ユーザーにファイルパスを通知する
- GitHub Pages で公開する場合は `_config.yml` の対象範囲を確認する
- wiki の場合は目次ページ（`docs/wiki/index.md`）を更新する

## 🔗 他スキルとの連携

- **前段**: 各工程の成果物（要件定義書・設計書・実装コード）が入力になる
- **併用推奨**: `self-review`（ドキュメントの品質チェック）・`phase-gate-check`（ドキュメントの完了基準チェック）
- **後段**: 作成したドキュメントは `self-review` で品質検証し、必要に応じて `stakeholder-review` でステークホルダー視点の確認を行う
