# 単体テスト設計 業務フロースキル

このスキルはソフトウェア開発における **単体テスト設計の実行手順を定義** する。
「何をテスト対象とするか」「どのパターンまで網羅するか」「カバレッジ目標をどこに置くか」の価値判断基準は `unit-test-designer` エージェントの職種定義を参照すること。

**前提**: 設計書（system-architect 出力、または詳細設計書）が存在する場合は Step 1 で必ず読み込む。未整備の場合は Step 0 で設計の骨子を確認してからテスト設計に進む。

**必須出力**: 本スキルは以下の3つを必ず作成・出力する。テストコードのみを出力して完了とすることは不可。
1. **テスト設計書**（Markdown）— Step 9 の構成に従い、テスト対象・パターン網羅の根拠・カバレッジ目標・トレーサビリティを文書化
2. **テストケース**（テスト設計書内の表）— 同値分割・境界値・デシジョンテーブル・状態遷移・例外の各観点で網羅
3. **テストコード**（実装言語のフレームワーク）— FIRST原則・AAA構造に従い、テストケースを自動実装

---

## 適用する標準手法・フレームワーク

本スキルは以下の確立された手法を組み合わせて実行する。各 Step で明示的に参照し、根拠を示すこと。

| 手法 | 由来 | 適用 Step | 役割 |
|---|---|---|---|
| **Vモデル** | V-Model XT | Step 1, 8 | 設計↔テストの対応関係。各設計要素に検証活動を紐付ける |
| **ISTQB シラバス** | ISTQB Foundation | Step 4 | テスト技法の体系。ブラックボックス・ホワイトボックス・経験ベース |
| **同値分割** | ISTQB | Step 4-1 | 入力領域を代表値で分割し、網羅を効率化 |
| **境界値分析** | ISTQB | Step 4-2 | 境界付近の欠陥多発性に基づくテスト |
| **デシジョンテーブル** | ISTQB | Step 4-3 | 条件の組み合わせと期待動作の網羅 |
| **原因結果グラフ** | ISTQB | Step 4-3 | 条件の論理関係を体系的にデシジョンテーブルへ変換 |
| **状態遷移テスト** | ISTQB | Step 4-4 | 状態機械の遷移・遷移漏れを検出 |
| **組み合わせテスト** | ISTQB / 直交表 | Step 4-5 | ペアワイズ・直交表で組み合わせ爆発を抑制 |
| **ステートメントカバレッジ (C0)** | ISTQB | Step 5 | 全命令を1回以上実行 |
| **ブランチカバレッジ (C1)** | ISTQB | Step 5 | 全分岐の真/偽を1回以上実行 |
| **条件カバレッジ (C2)** | ISTQB | Step 5 | 各論理条件の真/偽を1回以上実行 |
| **MC/DC (C3)** | DO-178C / ISTQB Advanced | Step 5 | Modified Condition/Decision Coverage。条件が決定に独立影響 |
| **パスカバレッジ** | ISTQB | Step 5 | 全実行パス。コスト高・通常は部分適用 |
| **FIRST原則** | xUnit | Step 6 | Fast/Independent/Repeatable/Self-validating/Timely |
| **AAA** | xUnit | Step 6 | Arrange-Act-Assert の構造化 |
| **テストダブル** | Gerard Meszaros | Step 6 | Dummy/Stub/Spy/Fake/Mock の使い分け |
| **BDD / Gherkin** | Dan North | Step 6 | Given-When-Then で振る舞いを記述 |
| **プロパティベーステスト** | QuickCheck | Step 6 | 不変条件をランダム入力で検証 |
| **テストピラミッド** | Mike Cohn | Step 3 | 単体>統合>E2E の比率。単体を厚く |
| **欠陥ベース** | ISTQB Advanced | Step 7 | 過去の欠陥傾向からテストを補強 |

### Vモデルと本スキルStepの対応

```
設計書 ───→ Step 1: 設計書の読み込み
        └──→ Step 3: テスト対象の識別
        └──→ Step 4: テストケース設計（パターン網羅）
        └──→ Step 5: カバレッジ目標の設定
        └──→ Step 6: テストコードの実装
        └──→ Step 7: テストの実行と検証
        └──→ Step 8: 設計とのトレーサビリティ確認
```

## Step 0: 設計の確認（設計書がない場合）

設計書が未整備の場合、以下の最小限の骨子をユーザーに確認する。整備済みの場合は Step 1 へ。

| 確認項目 | 内容 |
|---|---|
| テスト対象モジュール | どの関数・クラス・メソッドをテストするか |
| 入力仕様 | 引数・型・値域・制約 |
| 出力仕様 | 戻り値・副作用・例外 |
| 分岐条件 | if/switch/ループの条件式 |
| 状態 | 状態を持つか。状態遷移図の有無 |
| 外部依存 | DB/API/ファイル/時刻/乱数 等 |
| 品質基準 | 必須カバレッジ・性能・実行時間上限 |

不明点は Step 2 で質問する。system-architect スキルの適用を推奨する旨をユーザーに伝えること。

## Step 1: 設計書の読み込みと解釈

設計書（system-architect 出力、または詳細設計書）を読み込み、テスト設計に必要な情報を抽出する。

| 抽出項目 | テスト設計への影響 |
|---|---|
| モジュール構成 | テスト対象の単位（クラス/関数） |
| IF仕様（API/関数） | 入力・出力・例外の契約。テストケースの期待値 |
| データモデル | 入力データの構造・値域・制約 |
| ビジネスルール | デシジョンテーブル・同値分割の条件 |
| 状態遷移 | 状態遷移テストの起点 |
| 非機能要件 | 性能・セキュリティのテスト要件 |
| 受け入れ基準 | テスト合格基準 |

読み込めない項目は **不明点リスト** に蓄積し、Step 2 で質問する。

---

## Step 2: コンテキスト収集と制約の明示化

実装コード・テスト環境・制約を収集し、テスト設計の前提を固める。

### 収集対象
- 実装コード（テスト対象の関数・クラス本体）
- 既存のテストコード・テストフレームワーク（Jest/Vitest/pytest/Unittest/JUnit 等）
- CI/CD 設定・テスト実行環境
- 外部依存のIF（モック化の対象）
- 過去の欠陥履歴（欠陥ベーステストの参考）

### 明示化する制約
- **硬い制約**: テストフレームワーク固定・CI実行時間上限・外部API呼び出し禁止
- **柔らかい制約**: カバレッジ目標・テスト粒度・モック vs 実物

収集結果は **前提条件** としてテスト設計書に記載する。

---

## Step 3: テスト対象の識別と優先度付け（テストピラミッド）

**テストピラミッド** に基づき、単体テストの対象を識別し優先度を付ける。

### 3-1. テスト対象の識別
設計書のモジュール構成から、以下を単体テスト対象として抽出する。

| 対象 | 抽出基準 |
|---|---|
| 公開関数・メソッド | IF仕様に記載されたエントリポイント |
| ビジネスルール関数 | 計算・判定・変換ロジック。欠陥影響大 |
| 状態保持クラス | 状態遷移を持つ。遷移バグの温床 |
| バリデーション | 入力検証。セキュリティ境界 |
| ユーティリティ | 汎用関数。再利用されるため品質重要 |
| 外部IFアダプタ | モック化して契約を検証 |

### 3-2. 優先度付け
| 優先度 | 基準 | カバレッジ目標 |
|---|---|---|
| **S** | 中核業務ロジック・金銭計算・セキュリティ境界 | C1 100% / MC/DC 90%以上 |
| **A** | 主要機能・状態遷移・外部IF契約 | C1 90%以上 |
| **B** | 補助機能・ユーティリティ | C1 80%以上 |
| **C** | UI・単純CRUD・自動生成コード | C0 80%以上 |

優先度は **欠陥影響度 × 変更頻度** で判断する。

---

## Step 4: テストケース設計（パターン網羅）

**ISTQB技法** を組み合わせてパターンを網羅する。各対象について複数技法を併用し、漏れを防ぐ。

### 4-1. 同値分割（Equivalence Partitioning）

入力領域を「同じ振る舞いをする代表値のグループ」に分割し、各グループから代表値を1つ選ぶ。

```
対象: calculateTax(income)
  有効同値クラス:
    - 低所得: 0〜1,000万円 → 代表 500万
    - 中所得: 1,001〜2,000万円 → 代表 1,500万
    - 高所得: 2,001万円〜 → 代表 3,000万
  無効同値クラス:
    - 負の値 → 代表 -1
    - 非数値 → 代表 "abc"
```

### 4-2. 境界値分析（Boundary Value Analysis）

同値クラスの境界付近（境界±1）をテスト。**欠陥は境界に集中する** という経験則に基づく。

```
境界: 1,000万円
  - 999万9,999円（境界直下）
  - 1,000万円（境界）
  - 1,000万1円（境界直上）
```

### 4-3. デシジョンテーブル（Decision Table）

複数条件の組み合わせと期待動作を表で網羅する。**原因結果グラフ** で論理関係を整理してから表化する。

| 条件 | R1 | R2 | R3 | R4 | R5 |
|---|---|---|---|---|---|
| 会員種別=プレミアム | T | T | F | F | - |
| 購入額≥1万円 | T | F | T | F | - |
| クーポン所持 | - | - | - | - | T |
| **期待動作** | 10%割引 | 5%割引 | 3%割引 | 割引なし | クーポン適用 |

- 「-」はドントケア（任意）。ドントケアの圧縮で組み合わせを減らす。
- 各ルール列が1つのテストケース。

### 4-4. 状態遷移テスト（State Transition Testing）

状態機械の遷移を網羅する。**Nスイッチカバレッジ** で網羅深度を指定。

```
状態: 未認証 → 認証済 → ロック
遷移:
  未認証 --正しいPW--> 認証済
  未認証 --誤PW--> 未認証（試行回数+1）
  未認証 --3回誤PW--> ロック
  ロック --管理者解除--> 未認証
```

| カバレッジ | 網羅対象 |
|---|---|
| 0スイッチ | 全遷移を1回以上 |
| 1スイッチ | 2連続遷移の全組み合わせ |
| Nスイッチ | N+1連続遷移の全組み合わせ |

### 4-5. 組み合わせテスト（Pairwise / 直交表）

多条件の組み合わせ爆発を **ペアワイズ** で抑制。全組み合わせ(n^k)を2因子組合せに圧縮。

```
因子: ブラウザ(3) × OS(3) × 画面サイズ(4) × 言語(2) = 72通り
ペアワイズ圧縮 → 約10〜15通り
```

直交表（L9, L18 等）を用いて最小組み合わせを生成する。

### 4-6. 例外・エラーケース

正常系だけでなく **異常系・例外系** を必ず網羅する。

| 分類 | テスト内容 |
|---|---|
| 入力違反 | 型不正・範囲外・null/undefined・空文字・巨大データ |
| 状態違反 | 事前条件未満足・二重実行・排他違反 |
| 外部依存失敗 | DB接続失敗・APIタイムアウト・ファイル不存在 |
| リソース枯渇 | メモリ不足・接続プール枯渇 |
| セキュリティ | SQLインジェクション・XSS・権限違反 |

### 4-7. パターン網羅のチェックリスト

各テスト対象について以下を全て確認し、漏れがないか検証する。

- [ ] 全有効同値クラスを1つ以上テストしたか
- [ ] 全無効同値クラスを1つ以上テストしたか
- [ ] 全境界値（境界±1）をテストしたか
- [ ] デシジョンテーブルの全ルール列をテストしたか
- [ ] 状態遷移の全遷移を1回以上（0スイッチ）テストしたか
- [ ] 全例外・エラーケースをテストしたか
- [ ] 設計書の全ビジネスルールに対応するテストがあるか

## Step 5: カバレッジ目標の設定

**ISTQB カバレッジ基準** で目標を設定し、優先度（Step 3）に応じて適用する。

| カバレッジ | 定義 | 適用優先度 | 目標 |
|---|---|---|---|
| **C0 ステートメント** | 全命令を1回以上実行 | C | 80%以上 |
| **C1 ブランチ** | 全分岐の真/偽を1回以上 | B | 80〜90%以上 |
| **C2 条件** | 各論理条件の真/偽を1回以上 | A | 90%以上 |
| **C3 MC/DC** | 条件が決定に独立影響を与える組み合わせ | S | 90%以上 |
| **パス** | 全実行パス | S（一部） | 重要関数のみ |

### カバレッジの注意点
- **100%カバレッジ ≠ 品質保証**。網羅は「実行した」ことであり「正しい」ことではない
- カバレッジ未達の行は **未テスト理由** を明示する（到達不能コード・環境依存 等）
- **未カバー ≠ 不要**。意図的除外は根拠を残す

## Step 6: テストコードの実装

**FIRST原則** と **AAA** に従い、テストコードを実装する。

### 6-1. FIRST原則

| 原則 | 意味 | 実装上の注意 |
|---|---|---|
| **F**ast | 高速実行 | 外部IOをモック化・並列実行可能に |
| **I**ndependent | テスト間非依存 | 実行順序に依存しない・各テストで状態初期化 |
| **R**epeatable | 再現可能 | 時刻・乱数・環境に依存しない（固定値・シード） |
| **S**elf-validating | 自己検証 | assert で pass/fail が明確・目視判断不要 |
| **T**imely | 適時実装 | 実装直後・設計直後に書く。後回し禁止 |

### 6-2. AAA構造

```javascript
test('calculateTax: 中所得は15%税率', () => {
  // Arrange（準備）
  const income = 15_000_000;

  // Act（実行）
  const result = calculateTax(income);

  // Assert（検証）
  expect(result).toBe(2_250_000);
});
```

### 6-3. テストダブルの使い分け

| 種類 | 用途 | 例 |
|---|---|---|
| **Dummy** | 渡すだけ・使用しない | 未使用引数の埋め草 |
| **Stub** | 固定値を返す | 外部APIの成功レスポンス |
| **Spy** | 呼び出しを記録 | 「関数が2回呼ばれた」検証 |
| **Fake** | 実装済みだが本番不適 | インメモリDB |
| **Mock** | 期待呼び出しを検証 | 「引数Xで1回呼ばれた」検証 |

### 6-4. テスト命名規則

```
test('<対象関数>: <条件> のとき <期待動作>')
```

例:
- `test('validateEmail: 有効形式 のとき true を返す')`
- `test('withdraw: 残高不足 のとき InsufficientFundsError を投げる')`
- `test('login: 3回連続誤PW のとき アカウントをロックする')`

### 6-5. BDD / Gherkin（振る舞い記述）

複雑なシナリオは **Given-When-Then** で記述する。

```gherkin
Scenario: プレミアム会員が1万円以上購入すると10%割引
  Given 会員種別は "プレミアム"
  And 購入額は 12,000円
  When 割引を計算する
  Then 割引後金額は 10,800円
```

### 6-6. プロパティベーステスト

不変条件（プロパティ）を定義し、ランダム入力で検証する。

```javascript
// プロパティ: ソート結果は常に昇順
fc.assert(fc.property(fc.array(fc.integer()), (arr) => {
  const sorted = sortArray(arr);
  for (let i = 1; i < sorted.length; i++) {
    expect(sorted[i]).toBeGreaterThanOrEqual(sorted[i - 1]);
  }
}));
```

## Step 7: テストの実行と検証

### 7-1. テスト実行
- テストフレームワークで全テストを実行
- カバレッジレポートを取得（C0/C1/C2/C3）
- 実行時間・失敗テストを確認

### 7-2. 欠陥ベースの補強
過去の欠陥傾向から **よく見落とすパターン** を補強する。

| 欠陥傾向 | 補強テスト |
|---|---|
| オフバイワン | 境界値±1 の再確認 |
| null/undefined | null・undefined・空配列の入力 |
| タイミング | 並行実行・レース条件 |
| 文字エンコーディング | マルチバイト・絵文字・制御文字 |
| タイムゾーン | UTC・ローカル・サマータイム |
| 浮動小数点 | 誤差・丸め・ゼロ除算 |

### 7-3. 失敗時の対応
- テスト失敗は **実装バグ** か **テスト誤り** かを判定
- 実装バグ: 実装を修正
- テスト誤り: 期待値・前提を修正
- 設計バグ: 設計書を修正し、トレーサビリティを更新

---

## Step 8: 設計とのトレーサビリティ確認（Vモデル）

**Vモデル** に基づき、設計要素とテストケースの対応を確認する。設計通りの実装であることを検証する。

### 8-1. トレーサビリティマトリクス

| 設計要素 | テストケース | カバレッジ | 状態 |
|---|---|---|---|
| IF-001: calculateTax | TC-001〜TC-012 | C1 100% | ✓ |
| BR-003: クーポン併用不可 | TC-013〜TC-015 | MC/DC 100% | ✓ |
| ST-002: アカウントロック | TC-020〜TC-025 | 1スイッチ 100% | ✓ |
| NFR-性能: 100ms以内 | TC-030 | - | ✓ |

### 8-2. 設計との乖離チェック

- [ ] 設計書の全IF仕様に対応するテストがあるか
- [ ] 設計書の全ビジネスルールに対応するテストがあるか
- [ ] 設計書の全状態遷移に対応するテストがあるか
- [ ] 設計書の全例外仕様に対応するテストがあるか
- [ ] 設計書の全非機能要件に対応するテストがあるか
- [ ] テストが **設計書の期待動作** を検証しているか（実装の都合でないか）

### 8-3. 乖離の是正
- テスト不足 → Step 4 でケースを追加
- 設計書の記載漏れ → 設計書を更新（system-architect スキルへフィードバック）
- 実装が設計と乖離 → 実装を修正、または設計を更新

## Step 9: テスト設計書の提示（必須出力）

**本Stepは必須**。テストコードのみを出力してテスト設計書を省略することは不可。設計書はテストケースの根拠・網羅性の証明・レビュー資料として機能する。
