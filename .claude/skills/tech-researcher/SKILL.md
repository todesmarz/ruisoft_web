# 技術調査・スパイク 業務フロースキル

このスキルはソフトウェア開発における **技術調査・スパイクの実行手順を定義** する。
「どの評価軸で比較するか」「導入可否をどう判断するか」「PoCの範囲をどこまで広げるか」の価値判断基準は `tech-researcher` エージェントの職種定義を参照すること。

**前提**: 調査対象が明確でない場合は Step 1 でヒアリングしてから調査に進む。要件定義書（requirements-analyzer 出力）が存在する場合は Step 1 で必ず読み込み、評価軸の優先順位付けに使用する。

**必須出力**: 本スキルは以下の3つを必ず作成・出力する。調査メモのみを出力して完了とすることは不可。
1. **技術調査レポート**（Markdown）— Step 8 の構成に従い、評価軸・比較表・推奨・根拠・リスクを文書化
2. **比較マトリクス**（レポート内の表）— 複数候補を複数評価軸で定量化比較
3. **推奨と意思決定根拠**（レポート内の章）— 推奨候補・推奨理由・導入条件・次ステップを明示
4. **PoCプロトタイプ**（コード）— Step 6 で実施した場合。検証結果とコード

## 適用する標準手法・フレームワーク

本スキルは以下の確立された手法を組み合わせて実行する。各 Step で明示的に参照し、根拠を示すこと。

| 手法 | 由来 | 適用 Step | 役割 |
|---|---|---|---|
| **スパイク（Spike）** | XP（Extreme Programming） | Step 1, 6 | 不確実性を解消するための限定的調査・プロトタイプ |
| **フィジビリティスタディ** | システム工学 | Step 1-7 | 実現可能性の体系的評価。技術・運用・経済の3観点 |
| **PoC（Proof of Concept）** | ソフトウェア工学 | Step 6 | 概念実証。最小プロトタイプで実現性を検証 |
| **トレードオフ分析** | システム工学 | Step 4, 7 | 複数候補を複数軸で比較し根拠を明示 |
| **MoSCoW法** | DSDM / Agile | Step 2 | 評価軸の優先度分類（Must/Should/Could/Won't） |
| **SWOT分析** | 経営戦略 | Step 5 | 候補の強み・弱み・機会・脅威を整理 |
| **デシジョンマトリクス** | 意思決定科学 | Step 4, 7 | 評価軸×候補の定量化比較。重み付け採点 |
| **TMAP（Technology Maturation Assessment）** | 技術経営 | Step 5 | 技術成熟度の評価。採用リスク判断 |
| **総所有コスト (TCO)** | IT経営 | Step 5 | 導入・運用・廃止までの総コスト比較 |
| **ベンダーロックイン評価** | クラウド設計 | Step 5 | 特定ベンダーへの依存度・移行コスト評価 |
| **RFP/RFI** | 調達プロセス | Step 5 | ベンダーへの情報要求・提案依頼 |
| **ベンチマークテスト** | 性能工学 | Step 6 | 定量性能比較。同一条件での計測 |
| **ラビング・チューブ・テスト** | ソフトウェア工学 | Step 6 | 概念実証の最小検証範囲定義 |
| **アクションリサーチ** | 社会科学 | Step 6 | 調査と実装を交互に回す反復アプローチ |
| **アンティパターン調査** | ソフトウェア工学 | Step 5 | 失敗事例・回避すべき設計の調査 |
| **トレーサビリティ** | Vモデル | Step 8 | 調査結果→設計判断の根拠保持 |

### スパイクの種類と本スキルStepの対応

```
スパイク種別 ───┬─→ Step 1: 調査テーマの明確化
              ├─→ Step 2: 評価軸の定義
              ├─→ Step 3: 候補の収集
              ├─→ Step 4: 比較マトリクスの作成
              ├─→ Step 5: 各候補の詳細評価
              ├─→ Step 6: PoC・ベンチマーク（必要時）
              ├─→ Step 7: 推奨と意思決定
              └─→ Step 8: 技術調査レポートの作成

スパイク種別：
  - 調査スパイク（Spike for Research）：情報収集が主。Step 1-5, 7-8
  - 実装スパイク（Spike for Implementation）：PoCが主。Step 1-8 全実施
```

## Step 1: 調査テーマの明確化

**スパイク** の目的を明確化する。曖昧なテーマはここで整理する。

### 1-1. 調査テーマの構造化テンプレート

```
調査テーマ：{何について調査するかの1文}
背景：      {なぜ今この調査が必要か}
目的：      {調査結果を何に使うか（技術選定/導入判断/リスク評価）}
対象範囲：  {何を含み、何を含まないか}
期限：      {調査完了期限}
成果物：    {技術調査レポート / PoCプロトタイプ / 比較表}
想定読者：  {誰がこの調査結果を使うか}
```

### 1-2. 調査種別の判定

| 種別 | 特徴 | 主なStep |
|---|---|---|
| **技術選定** | 複数候補から1つを選ぶ | Step 1-8 全実施 |
| **導入可否判断** | 特定技術を導入するか否か | Step 1, 5, 7, 8 |
| **リスク評価** | 既存技術の継続リスク評価 | Step 1, 5, 7, 8 |
| **性能限界確認** | 特定技術の性能上限確認 | Step 1, 6, 7, 8 |
| **統合可能性確認** | 既存システムとの統合可否 | Step 1, 5, 6, 7, 8 |

### 1-3. 要件定義書の読み込み（存在する場合）

要件定義書（requirements-analyzer 出力）から以下を抽出し、評価軸の優先順位付けに使用する。

| 抽出項目 | 調査への影響 |
|---|---|
| 機能要件 | 必須機能を満たす技術か |
| 非機能要件（ISO 25010） | 性能・セキュリティ・保守性の評価軸 |
| 制約条件 | 言語・予算・期間・運用体制の制約 |
| 対象外 | 評価不要な技術の明示 |

### 1-4. 不明点の質問
テーマ・目的・対象範囲が不明確な場合は **不明点リスト** をユーザーに提示し、回答を得てから調査に進む。

## Step 2: 評価軸の定義と優先度付け

**MoSCoW法** で評価軸を優先度付けする。

### 2-1. 評価軸の候補

| カテゴリ | 評価軸の例 |
|---|---|
| **機能適合性** | 必須機能の有無・拡張性・カスタマイズ性 |
| **性能効率性** | 応答時間・スループット・リソース使用量 |
| **信頼性** | 稼働率・障害復旧・フォールトトレランス |
| **使用性** | 学習コスト・ドキュメント品質・コミュニティ |
| **保守性** | ソース可読性・テスト容易性・モジュール性 |
| **移植性** | プラットフォーム依存・移行容易性 |
| **セキュリティ** | 脆弱性・認証認可・監査ログ |
| **互換性** | 既存システム・標準規格・データ形式 |
| **コスト** | ライセンス・TCO・導入費用 |
| **成熟度** | 版歴・採用実績・コミュニティ規模 |
| **サポート** | 商用サポート・SLA・ドキュメント |
| **ベンダーリスク** | ロックイン度・移行コスト・ベンダー健全性 |

### 2-2. MoSCoW法による優先度付け

| 分類 | 意味 | 例 |
|---|---|---|
| **Must** | 必須評価軸。これを満たさない候補は除外 | 必須機能・セキュリティ・予算内 |
| **Should** | 重要評価軸。高スコアが望ましい | 性能・保守性・コミュニティ |
| **Could** | 可能評価軸。余裕があれば考慮 | 拡張性・エコシステム |
| **Won't** | 今回は評価対象外 | 将来機能・周辺ツール |

### 2-3. 評価軸定義書のテンプレート

```
評価軸E-001: 必須機能カバレッジ
  種別: Must
  定義: 要件定義のMust機能をどれだけカバーするか
  測定方法: 機能チェックリストの達成率
  重み: 5（5段階）
  閾値: 100%未満は候補除外
```

### 2-4. 重み付けの合意
- 各評価軸に重み（1-5）を付与
- Must評価軸は閾値を設定（未達は候補除外）
- ユーザーと重み付けを合意してから次Stepへ

## Step 3: 候補の収集

調査対象となる技術候補を網羅的に収集する。

### 3-1. 収集方法

| 方法 | 内容 |
|---|---|
| **既存知見** | チーム内の過去経験・社内標準 |
| **市場調査** | クラウドベンダー・OSSコミュニティ・業界レポート |
| **類似事例** | 同業他社・同規模プロジェクトの採用事例 |
| **専門家意見** | 外部有識者・コンサルタント・コミュニティ |
| **カンファレンス** | 技術カンファレンス・勉強会・ブログ |
| **ベンダー提案** | RFI（情報要求）でベンダーに質問 |

### 3-2. 候補の長リスト化

まず網羅的に候補を列挙し、**長リスト** を作成する。この時点では絞り込まない。

```
長リスト（例：フロントエンドフレームワーク選定）：
  - React
  - Vue.js
  - Angular
  - Svelte
  - Solid.js
  - Qwik
  - Astro
  - Remix
  - Next.js（React上）
  - Nuxt.js（Vue上）
```

### 3-3. 短リスト化（ショートリスト）

Must評価軸で足切りを行い、**短リスト** に絞る。通常3-5候補。

| 候補 | Must軸1 | Must軸2 | Must軸3 | 判定 |
|---|---|---|---|---|
| React | ✓ | ✓ | ✓ | 短リストへ |
| Angular | ✓ | ✓ | ✓ | 短リストへ |
| Svelte | ✓ | ✗ | ✓ | 除外（Must軸2未達） |
| Qwik | ✗ | ✓ | ✓ | 除外（Must軸1未達） |

### 3-4. 確認ポイント
- 短リストが網羅的か（主要候補を落としていないか）
- Must軸の足切り基準が妥当か
- 廃止候補・レガシー候補を含めているか（比較用）

## Step 4: 比較マトリクスの作成

**デシジョンマトリクス** で短リスト候補を定量化比較する。

### 4-1. デシジョンマトリクスのテンプレート

| 評価軸 | 重み | 候補A | 候補B | 候補C |
|---|---|---|---|---|
| 機能カバレッジ | 5 | 5 (25) | 4 (20) | 5 (25) |
| 性能 | 4 | 4 (16) | 5 (20) | 3 (12) |
| 保守性 | 4 | 4 (16) | 3 (12) | 4 (16) |
| コスト | 3 | 5 (15) | 3 (9) | 4 (12) |
| コミュニティ | 3 | 5 (15) | 4 (12) | 3 (9) |
| **合計** | — | **87** | **73** | **74** |

- 各候補に1-5のスコアを付与
- スコア × 重み = 重み付けスコア
- 重み付けスコアの合計で候補を順位付け

### 4-2. スコアリング基準の明示

スコア付けの基準を明文化し、主観を排除する。

```
評価軸：性能
  5: 業界最高水準（ベンチマーク上位10%）
  4: 平均以上（上位30%）
  3: 業界平均
  2: 平均以下（下位30%）
  1: 著しく低い（下位10%）
```

### 4-3. 感度分析

重み付けを変えた場合に順位が変わるか確認する。

| シナリオ | 重み変更 | 候補A | 候補B | 候補C | 順位変動 |
|---|---|---|---|---|---|
| 基本 | 現行重み | 87 | 73 | 74 | A>C>B |
| 性能重視 | 性能重み5 | 91 | 83 | 76 | A>B>C |
| コスト重視 | コスト重み5 | 95 | 73 | 84 | A>C>B |

順位が大きく変わる場合は、評価軸の重み付けをユーザーと再合意する。

## Step 5: 各候補の詳細評価

**SWOT分析**・**TCO**・**ベンダーロックイン評価** で各候補を深掘りする。

### 5-1. SWOT分析

各候補について強み・弱み・機会・脅威を整理する。

```
候補：React
  強み（Strengths）:
    - 大規模コミュニティ・豊富な学習資源
    - Facebook（Meta）が保守
    - エコシステムが充実
  弱み（Weaknesses）:
    - 学習曲線が急
    - ボイラープレートが多い
    - 状態管理の選定が複雑
  機会（Opportunities）:
    - React Server Components で性能向上余地
    - 採用市場で人材確保容易
  脅威（Threats）:
    - 新フレームワーク（Svelte/Solid）の台頭
    - React の複雑化で離脱ユーザー増加
```

### 5-2. 総所有コスト（TCO）比較

導入から廃止までの総コストを比較する。

| コスト項目 | 候補A | 候補B | 候補C |
|---|---|---|---|
| ライセンス費用 | 0 | 0 | 50万/年 |
| 導入費用 | 100万 | 200万 | 50万 |
| 学習・研修 | 50万 | 100万 | 30万 |
| 運用費用（3年） | 300万 | 200万 | 400万 |
| 移行・廃止 | 100万 | 50万 | 200万 |
| **3年TCO** | **550万** | **550万** | **730万** |

### 5-3. ベンダーロックイン評価

| 評価項目 | 候補A | 候補B | 候補C |
|---|---|---|---|
| プロプライエタリ度 | 低 | 中 | 高 |
| データ移行コスト | 低 | 中 | 高 |
| 代替品の有無 | 多 | 少 | ほぼ無 |
| ベンダー健全性 | 高 | 中 | 高 |
| ロックインリスク | 低 | 中 | 高 |

### 5-4. 技術成熟度評価（TMAP）

| 段階 | 特徴 | 採用リスク |
|---|---|---|
| **研究段階** | 学術・実験室レベル | 極高 |
| **初期段階** | 限定的実装例・版0.x | 高 |
| **成長段階** | 採用事例増加・版1.x | 中 |
| **成熟段階** | 広く採用・安定版・LTS | 低 |
| **衰退段階** | 新規採用減少・後継あり | 中（移行リスク） |

### 5-5. アンティパターン調査

各候補の **失敗事例・回避すべき設計** を調査する。

- 同種プロジェクトでの失敗事例
- 公式ドキュメントの「非推奨」「注意」記載
- コミュニティの批判的意見・移行事例
- 既知のバグ・セキュリティ問題

### 5-6. 関連ドキュメント・事例の収集

| 情報源 | 内容 |
|---|---|
| 公式ドキュメント | 機能・制限・ベストプラクティス |
| GitHub Issues | 既知の問題・対応状況 |
| ベンチマーク記事 | 定量性能比較 |
| case study | 実導入事例・規模・課題 |
| カンファレンス発表 | ロードマップ・将来方向 |

## Step 6: PoC・ベンチマーク（必要時）

**PoC（Proof of Concept）** と **ベンチマークテスト** で実証検証する。全調査で必須ではなく、以下の場合に実施する。

### 6-1. PoC実施判定

| 実施条件 | 実施 |
|---|---|
| 比較マトリクスで順位が接近 | 実施 |
| 性能要件が厳しい | 実施（ベンチマーク） |
| 既存システムとの統合が懸念 | 実施 |
| 候補が新技術（成熟度低） | 実施 |
| 比較マトリクスで明確な差 | 省略可 |

### 6-2. PoC範囲の定義（ラビング・チューブ・テスト）

PoCは **最小限の検証範囲** に絞る。全機能を実装しない。

```
PoC目的：候補Aと候補Bの性能差を検証
PoC範囲：
  - 実装：APIエンドポイント1つ（CRUD）
  - 測定：応答時間・スループット・メモリ使用量
  - 条件：1000 RPS・10万レコード
  - 除外：認証・UI・本番DB
期間：2日
```

### 6-3. ベンチマークテスト

**同一条件** で定量性能を比較する。

| 測定項目 | 候補A | 候補B | 候補C |
|---|---|---|---|
| 平均応答時間 | 50ms | 80ms | 120ms |
| P99レイテンシ | 200ms | 350ms | 500ms |
| 最大スループット | 5000 RPS | 3000 RPS | 1500 RPS |
| メモリ使用量 | 200MB | 350MB | 500MB |
| 冷起動時間 | 2s | 5s | 8s |

### 6-4. PoC結果の記録

```markdown
# PoC結果：{候補名}

## 実装内容
- 実装モジュール：
- 実装規模：{LOC}
- 所要時間：

## 検証結果
| 項目 | 目標 | 実測 | 判定 |
|---|---|---|---|
| 応答時間 | 100ms以下 | 50ms | ✓ |
| スループット | 3000 RPS | 5000 RPS | ✓ |
| 統合可能性 | 既存DB接続 | 成功 | ✓ |

## 発見された課題
- {予期しない制約・不具合}

## コード
- リポジトリ：{URL}
- ブランチ：poc/{候補名}
```

### 6-5. アクションリサーチ（反復調査）

PoC結果を受けて評価軸・候補を見直し、再調査する反復アプローチ。

```
調査 → PoC → 評価軸更新 → 再調査 → 再PoC → ... → 推奨
```

## Step 7: 推奨と意思決定

**トレードオフ分析** に基づき、推奨候補と意思決定根拠を提示する。

### 7-1. 推奨の記述形式

```
推奨候補：{候補名}
推奨度：  {強く推奨 / 推奨 / 条件付き推奨 / 推奨不可}

推奨根拠：
  1. {評価軸1での優位性}
  2. {評価軸2での優位性}
  3. {PoCでの検証結果}

### 7-2. 推奨度の判定基準

| 推奨度 | 条件 |
|---|---|
| **強く推奨** | 全Must軸クリア・合計スコア最高・PoC良好・リスク低 |
| **推奨** | 全Must軸クリア・合計スコア最高・リスク中 |
| **条件付き推奨** | Must軸クリア・条件付きでリスク軽減可能 |
| **推奨不可** | Must軸未クリア・リスク高・PoC不良 |

### 7-3. 代替案の提示

推奨候補1つだけでなく、**第2候補・第3候補** を明示する。

  - {候補Bを選ぶ条件}
第3候補：候補C
  - {候補Cを選ぶ条件}
```

## スキル間連携

- **前段**: `requirements-analyzer`（要件定義書）→ 本スキルが評価軸の優先順位付けに使用
- **後段**: `system-architect`（システム設計）→ 本スキルの推奨結果をアーキテクチャ選定に反映。ADRとして記録
- **後段**: `code-implementer`（実装）→ 本スキルのPoC結果・技術選定を踏まえて実装
- **後段**: `blog-writer`（ブログ執筆）→ 本スキルの調査結果を技術記事として発信（別スキル）
- **補完**: `self-review`（セルフレビュー）→ 調査レポートの品質チェック
- **補完**: `stakeholder-review`（ステークホルダーレビュー）→ 推奨結果の合意形成
