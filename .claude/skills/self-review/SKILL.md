# セルフレビュー 業務フロースキル

このスキルは成果物の **セルフレビューの実行手順を定義** する。
「何を問題とするか」「修正必須か推奨か」の価値判断基準は `self-review` エージェントの職種定義を参照すること。

---

## 適用する標準手法・フレームワーク

本スキルは以下の確立された手法を組み合わせて実行する。各 Step で明示的に参照し、根拠を示すこと。

| 手法 | 由来 | 適用 Step | 役割 |
|---|---|---|---|
| **パッシブレビュー** | IEEE 1028 | Step 1-6 | 成果物を静的に検証する標準レビュー手法 |
| **チェックリストベースレビュー** | IEEE 1028 / Fagan | Step 2-6 | 6観点のチェックリストで網羅性を担保 |
| **Faganインスペクション** | Michael Fagan (1976) | Step 1, 7 | 欠陥発見→記録→修正→再確認のサイクル |
| **ファクトチェック** | 国際ファクトチェックネットワーク (IFCN) | Step 5 | 一次情報照合・情報源明示・推量と事実の区別 |
| **3点確認法** | ジャーナリズム | Step 5 | 1つの事実につき独立した情報源を3つ以上 |
| **ピアレビュー原則** | ソフトウェア工学 | Step 1-7 | 作成者本人が客観視点でレビュー（セルフ=疑似ピア） |
| **SMART基準** | Peter Drucker | Step 6 | 目標達成性の評価（Specific/Measurable/Achievable/Relevant/Time-bound） |
| **KISS原則** | 工学一般 | Step 6 | より良い方法の評価軸（シンプルさ・過剰設計排除） |
| **トレードオフ分析** | システム工学 | Step 6 | 代替案の比較と根拠の明示 |
| **ルーブリック評価** | 教育評価法 | Step 7 | 4段階評価で問題の重大度を分類 |

### Faganインスペクションと本スキルStepの対応

```
Fagan 概要把握   ───→ Step 1: 成果物の読み込みと目的把握
Fagan 欠陥発見   ──┬─→ Step 2: 不整合チェック
                  ├─→ Step 3: 誤字脱字チェック
                  ├─→ Step 4: わかりやすさチェック
                  ├─→ Step 5: ファクトチェック
                  └─→ Step 6: より良い方法と目的達成性チェック
Fagan 欠陥記録   ───→ Step 7: レビュー報告書の作成
Fagen 修正確認   ───→ Step 8: 修正後の再レビュー
```

## Step 1: 成果物の読み込みと目的把握

レビュー対象の成果物を読み込み、**本来の目的** を明確にする。目的が不明確だと全ての判断が揺らぐため最重要 Step。

| 抽出項目 | 確認ポイント |
|---|---|
| 成果物の種類 | ドキュメント / コード / 設計書 / ブログ記事 / 要件定義書 / テスト設計書 |
| 想定読者 | 誰が読むか（エンジニア / 非エンジニア / 顧客 / チーム内） |
| 目的 | 読後に読者が何をできるようになるか、何を決定できるか |
| 成功基準 | どうなれば「目的達成」と言えるか |
| 文脈・前提 | どのプロジェクト・どの段階・どの制約下の成果物か |

### 目明確化のテンプレート
```
成果物：{ファイル名・タイトル}
種類：  {ドキュメント/コード/設計書/...}
読者：  {想定読者}
目的：  {読後に読者が〇〇できる/〇〇を決定できる}
成功基準：{具体的な達成状態}
```

目的が読み取れない場合は **不明点リスト** に蓄積し、Step 7 でユーザーに確認する。

## Step 2: 不整合チェック（一貫性の検証）

成果物内の **論理的一貫性・用語統一・数値整合** を検証する。

### 2-1. 用語の統一性
- 同じ概念に複数の呼称がないか（例：「ユーザー」「利用者」「ユーザ」の混在）
- 略語の定義なし使用がないか
- 初出時に定義されずに後出していないか

### 2-2. 数値・事実の整合性
- 文書内で複数回言及される数値が一致しているか
- 合計・内訳の計算が合うか
- パーセンテージ・比率の計算が正しいか
- 日付・時系列に矛盾がないか（未来の日付・逆転・飛び）

### 2-3. 論理的整合性
- 主張と根拠が矛盾していないか
- 前提と結論が整合しているか
- 「Aである」と「Aでない」が両方書かれていないか
- 図表と本文の記述が一致しているか
- 見出し階層と内容が合致しているか

### 2-4. 構成の整合性
- 目次と本文の見出しが一致しているか
- 章番号・図表番号の欠落・重複がないか
- 相互参照（「前述の」「後述の」「図Xを参照」）の参照先が存在するか

### 不整合チェックリスト
- [ ] 用語が統一されている
- [ ] 数値・計算が文書内で整合している
- [ ] 論理に矛盾がない
- [ ] 図表と本文が一致している
- [ ] 見出し階層が正しい
- [ ] 相互参照の参照先が存在する

---

## Step 3: 誤字脱字チェック（表記の正確性）

**誤字・脱字・表記揺れ・文法誤り** を検証する。

### 3-1. 誤字・脱字
- 漢字の誤変換（例：「必要」→「不必要」、「配布」→「配付」）
- 同音異義語の誤用（例：「効果」「効果」、「適応」「適用」）
- 送り仮名の誤り（例：「大きい」→「おおきい」）
- 助詞の誤り（例：「で」と「を」、「が」と「は」の誤用）
- 脱字（文字・単語の欠落）
- 衍字（不要な文字の混入）

### 3-2. 表記揺れ
- ひらがな・カタカナ・漢字の表記揺れ（例：「出来る」「できる」、「事」「こと」）
- 句読点の揺れ（「、」「，」「。」「．」の混在）
- 全角・半角の混在（英数字・カッコ・スペース）
- 数値の表記（「1,000」「1000」「千」の混在）
- 単位の表記（「秒」「s」「sec」の混在）

### 3-3. 文法・構文
- 主語と述語のねじれ（例：「AのBはCがDする」）
- 助詞の連続・重複（例：「においての」「についての」）
- 敬語の誤用（尊敬語と謙譲語の混在）
- 修飾語の位置の誤り
- 文末表現の不統一（「する」「します」「である」の混在）

### 3-4. 固有名詞・技術用語
- 製品名・サービス名の正式表記（例：「GitHub」「Github」「github」）
- API名・関数名・コマンド名のスペル
- バージョン番号の表記
- URL・ファイルパスの正確性

### 誤字脱字チェックリスト
- [ ] 誤字・脱字がない
- [ ] 表記揺れがない
- [ ] 文法・構文に誤りがない
- [ ] 文末表現が統一されている
- [ ] 固有名詞・技術用語の表記が正確

## Step 4: わかりやすさチェック（可読性の検証）

**読者が理解しやすい構成・表現か** を検証する。

### 4-1. 構成のわかりやすさ
- 読者の「で、それ何？」が冒頭で解消されるか
- 結論ファーストか、本題に入る前に冗長な前置きがないか
- 見出しが内容を的確に表しているか
- 情報の階層が適切か（深すぎず浅すぎず）
- 章立ての順序が読者の理解プロセスに合っているか

### 4-2. 表現のわかりやすさ
- 抽象的な表現に具体例が添えられているか
- 専門用語に初出時の説明があるか
- 一文が長すぎないか（目安：1文50字以内、長くても80字）
- 段落が長すぎないか（目安：1段落5-8文）
- 主語と述語が明確に対応しているか
- 「それ」「これ」等の指示語の参照先が明確か

### 4-3. 読者目線の確認
- 想定読者の知識レベルに合致しているか
- 読者が知りたい情報が過不足なく含まれているか
- 読者の「なぜ？」に先回りして答えているか
- 読者がつまずきそうな箇所に補足があるか
- 読後に「次に何をすべきか」が分かるか

### 4-4. 図表・コードのわかりやすさ
- 図表にキャプション・説明があるか
- 図表だけでは意味が伝わらない場合に本文補足があるか
- コードにコメント・説明があるか
- コードが実行可能で自己完結しているか（必要なimport・前提変数の明示）

### わかりやすさチェックリスト
- [ ] 冒頭で目的・結論が明示されている
- [ ] 見出しが内容を的確に表している
- [ ] 専門用語に説明がある
- [ ] 一文・一段落が適切な長さ
- [ ] 具体例が適切に使用されている
- [ ] 図表・コードに説明がある
- [ ] 読者のつまずき箇所に補足がある

## Step 5: ファクトチェック（内容の正確性）

**記述内容が事実として正しいか** を一次情報で検証する。**IFCNの原則** と **3点確認法** に基づく。

### 5-1. チェック対象の抽出
成果物中の以下を全てリストアップする。

| 対象 | 例 |
|---|---|
| 数値・計測値 | 処理時間・削減率・コスト・バージョン番号・統計 |
| 固有名詞 | ライブラリ名・API名・企業名・人名・サービス名 |
| 技術的事実 | 「〇〇は△△する」「〇〇は△△をサポートする」 |
| コード・コマンド | 実行可能性・現行バージョンでの動作 |
| 日付・リリース情報 | 「最新版」「2026年リリース」などの時制 |
| 引用・参考文献 | 引用元の存在・正確性・文脈の適切性 |
| 因果関係 | 「AだからB」の論理が成立するか |

### 5-2. 一次情報による照合
各項目を **一次情報** で確認する。

| 情報源 | 信頼性 | 用途 |
|---|---|---|
| 公式ドキュメント | 最高 | 仕様・機能・API |
| GitHub リリースノート | 最高 | バージョン・変更内容 |
| 論文・学会発表 | 高 | 学術的事実 |
| 標準規格（ISO/IEEE等） | 最高 | 規格・定義 |
| 公式統計・政府資料 | 高 | 統計・経済指標 |
| 企業公式発表 | 高 | 企業の事実 |
| 二次報道・解説記事 | 中 | 補助的・必ず一次情報で追証 |

### 5-3. 3点確認法の適用
重要な事実（特に数値・断言）は **独立した情報源を3つ以上** で確認する。

```
事実: 「WebAssemblyは主要4ブラウザでサポートされている」
情報源1: MDN Web Docs（公式）
情報源2: Chrome / Firefox / Safari / Edge の各公式リリースノート
情報源3: caniuse.com の対応表
判定: ✓ 確認完了
```

### 5-4. 確認できなかった場合の対処
以下のいずれかで対処し、対処方法を記録する。

| 対処 | 使用場面 |
|---|---|
| 調査を継続 | 確認できそうな場合 |
| 推量形に書き換え | 「〜とされている」「〜と報告されている」 |
| 情報源を明示して注記 | 情報源が限定的な場合 |
| 記述を削除 | 確認不能か不要な場合 |

### 5-5. 絶対にやらないこと
- 確認なしに「〜は〇〇%速い」「〜はバージョンXから対応」と書く
- 一次情報なしに「〜社が採用している」「〜件の実績がある」と書く
- 自分が書いた文章をそのまま事実として信じる（必ず外部で確認）
- 二次情報だけを根拠に断言する
- 情報源を確認せずに「最新」「定番」「業界標準」と書く

### ファクトチェックリスト
- [ ] 全数値・計測値を一次情報で確認した
- [ ] 全固有名詞の表記を公式情報で確認した
- [ ] 全技術的事実を一次情報で裏付けた
- [ ] コード・コマンドの実行可能性を確認した
- [ ] 日付・リリース情報の時制が正確
- [ ] 確認できなかった事実は推量形にするか削除した
- [ ] 重要事実は3点確認法で検証した

## Step 6: より良い方法と目的達成性チェック

**別のより良い方法がないか** と **目的を達成できるか** を検証する。

### 6-1. 目的達成性の評価（SMART基準）

Step 1 で定義した目的に対して、成果物が達成手段として適切か評価する。

| SMART | 問い | 判定 |
|---|---|---|
| **S**pecific | 目的は具体的か | 「理解する」ではなく「〇〇を設定できる」 |
| **M**easurable | 達成を測定できるか | 読後の行動・状態が明確か |
| **A**chievable | 成果物で達成可能か | 読者・前提・情報量が適切か |
| **R**elevant | 目的と関連しているか | 余計な情報・脱線がないか |
| **T**ime-bound | 適時性があるか | 情報が古くないか・時期に合致するか |

### 6-2. より良い方法の探索（KISS原則・トレードオフ分析）

現在の成果物に対して **代替案** を検討し、比較する。

#### 検討軸
| 軸 | 問い |
|---|---|
| シンプルさ | よりシンプルに伝えられないか（KISS） |
| 構成 | 別の章立て・順序でより分かりやすくならないか |
| 表現 | 別の表現・例えでより伝わりやすくならないか |
| 媒体 | 別の形式（図・表・コード）でより明確にならないか |
| 手法 | 別の技術・手法でより良い解決策がないか（コード・設計の場合） |
| スコープ | 情報の過不足はないか（削れる・足すべき） |

#### 代替案の提示フォーマット
```
現状: {現在の記述・実装}
代替案: {より良いと考えられる方法}
根拠: {なぜ代替案が良いか}
影響: {変更による影響・コスト}
推奨: 必須修正 / 推奨 / 検討
```

### 6-3. 過剰設計・過不足のチェック
- 過剰な詳細化で読者が迷子になっていないか
- 本質に関係ない情報が混入していないか
- 逆に必要な情報が欠落していないか
- 読者のレベルに対して難しすぎないか・易しすぎないか

### 6-4. 目的達成性の最終確認
- 読者が成果物を読み終えた時点で、Step 1 の目的が達成できるか
- 読者が「次に何をすべきか」を明確に持てるか
- 成功基準を満たす情報が過不足なく含まれているか

### より良い方法・目的達成性チェックリスト
- [ ] SMART基準の全項目を満たす
- [ ] よりシンプルな表現・構成がないか検討した
- [ ] 代替案を提示し根拠を明示した
- [ ] 情報の過不足がない
- [ ] 読者のレベルに合致している
- [ ] 読後に読者が「次の行動」を持てる

## Step 7: レビュー報告書の作成（必須出力）

**本Stepは必須**。問題点リストのみを出力して報告書を省略することは不可。報告書は修正の根拠・優先順位・是正案を明示する。

以下の構成でレビュー報告書をMarkdown形式で出力する。ファイルは `logs/review/` またはプロジェクトのレビュー格納先に保存する。

- 想定読者：
- 目的：
- 成功基準：

## 2. 総合評価
- 総合判定：A（問題なし）/ B（軽微な修正推奨）/ C（修正必須）/ D（要再作成）
- 判定根拠：

- 評価：A / B / C / D
- 発見事項：

### 3-2. 誤字脱字チェック
- 評価：A / B / C / D
- 発見事項：

### 3-3. わかりやすさチェック
- 評価：A / B / C / D
- 発見事項：

### 3-4. ファクトチェック
- 評価：A / B / C / D
- 発見事項：

- 評価：A / B / C / D
- 発見事項：

### 重大度の定義
| 重大度 | 意味 | 対応 |
|---|---|---|
| **必須** | 事実誤り・論理矛盾・目的未達 | 修正しないとリリース不可 |

|---|---|---|---|---|
| A-001 | {現状} | {代替案} | {根拠} | 必須/推奨/検討 |

## 7. チェックリスト結果
