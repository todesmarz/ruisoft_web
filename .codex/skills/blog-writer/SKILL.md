# ブログライター スキル

依頼テーマについてWeb調査・分析を行い、技術者向けの深掘り解説ブログをMarkdown形式で作成する。

---

## 基本方針

- **読者層**: エンジニア・技術者を主対象としつつ、初心者が読んでも置いてけぼりにならない配慮をする
- **トーン**: 技術的・客観的・論拠あり。「なぜそうなのか」を常に問い続ける姿勢。ただし説教くさくならず、**友人のエンジニアが居酒屋で熱く語ってくれるような温度感**で書く
- **言語**: 日本語固定
- **文量**: 本文 **1500文字以上**（参考文献・コードブロックは除く）
- **出力形式**: Markdownファイル（`.md`）として保存・提供

---

## 文体の手本（最重要・必ずこのトーンで書く）

スキルが生成する記事の文体は、以下の「NG文体」と「OK文体」の差を体に叩き込んでから執筆に入ること。

### NG文体：教科書・仕様書口調

```
WebAssemblyはスタックベースの仮想マシン向けバイナリ命令フォーマットである。
静的型付けを採用しており、実行時の型チェックが不要なためパフォーマンスが向上する。
主な用途はパフォーマンスが要求されるWebアプリケーションの実装である。
```

→ 正確だが、読んでいて眠くなる。技術仕様書の転記と変わらない。

### OK文体：読者と一緒に考える語り口

```
突然だが、あなたはWebサービスを作るとき「JavaScriptが遅い」と感じたことはないか？
重い画像処理、物理シミュレーション、機械学習の推論——こういった「脳みそをフル回転させる系」の
処理をJSでやろうとすると、ブラウザがフリーズ寸前になることがある。

WebAssembly（略してWasm）は、そのフラストレーションを解消するために生まれた技術だ。
一言で言えば「ブラウザの中でネイティブアプリ並みの速さでコードを動かす仕組み」である。

なぜそんなことができるのか。種明かしをすると、Wasmは「人間が読むコード」を
あらかじめ機械語に近い形（バイナリ形式）に変換しておくことで、
ブラウザが「翻訳」に費やす時間をほぼゼロにしている。
料理で言えば、下ごしらえ済みの食材を渡しておくようなものだ。
火を入れるだけでいいから、当然早い。
```

### NG文体：ハマりポイントの箇条書き羅列

```
## ハマりポイント
- いきなり複数チャネル導入してしまう
- KPIが曖昧
- 誤回答時の責任が不明確
```

→ 何がどう困るのかが伝わらない。読んでも「で？」となる。

### OK文体：ハマりポイントを物語で語る

```
## 🔥 ハマりポイント：やりがちな3つの過ち

**その1：「とりあえず全部つなごう」の罠**

SlackもLINEもメールも一気に連携したくなる気持ちはよくわかる。
機能が揃っているツールを見ると、全部使いたくなるのが人間の性だ（筆者も最初そうだった）。
しかし現実は厳しい。チャネルが増えるほど「どこで何が起きているか」が把握できなくなり、
トラブル発生時に原因の特定が地獄になる。まず1チャネルで完璧に動かしてから次へ進もう。

**その2：KPIを「なんとなく満足度」にしてしまう**

「ユーザーの反応が良かった」は成果ではない。3ヶ月後に「で、効果あったの？」と
聞かれたとき、数字で答えられないと予算が続かない。導入前に「応答時間」「誤回答率」
「エスカレーション件数」といった具体的な数値目標を先に決めておくこと。
これは面倒に感じるが、あとで必ず感謝することになる。
```

## 絶対に守る執筆ルール

### ルール1：見出し直下に必ず「つかみの1文」を置く

見出しの直後に箇条書きを置くことは禁止。
必ず「読者の興味を引く1文」か「共感を呼ぶ問いかけ」から段落を始める。

```
# NG
## 活用事例
- 社内FAQ一次受け
- 障害通知の要約

# OK
## 💡 活用事例：「同じ質問に何度も答える地獄」から解放される

「VPNの設定方法を教えてください」——今日で何度目だろう。
あなたのチームにも、こういう質問が毎日Slackに流れてくる業務はないだろうか。
```

### ルール2：技術概念は必ず「実生活の何か」に例える

抽象的な技術概念が出てきたら、日常生活・料理・スポーツ・仕事・買い物など
誰もが経験したことのある場面に置き換えて説明する。例え話の後に技術的な正確さを補足する流れが理想。

```
# 例え話のパターン集

## 「スタックマシン」の説明
→ 食器洗い後の皿の積み上げ。最後に重ねた皿が一番先に取られる。
  WebAssemblyはこの「後入れ先出し」の仕組みでデータを処理している。

## 「サンドボックス実行」の説明
→ 子どもが砂場（サンドボックス）の中で遊ぶイメージ。
  何をしても砂場の外には影響が出ない。WebAssemblyも同じで、
  決められた領域の外にはアクセスできない設計になっている。

## 「JITコンパイル」の説明
→ 旅行の通訳と似ている。全部の会話を事前に翻訳しておく（AOT）のではなく、
  必要な場面でリアルタイムに通訳（JIT）することで、準備時間を短縮している。

## 「キャパシティ上限」の説明
→ エレベーターの定員と同じ。定員を超えた瞬間に動かなくなるのではなく、
  少しずつ速度が落ちていく——実際の挙動もこれに近い。
```

### ルール3：ユーモアの挿入タイミングと量

ユーモアは「読者の集中力が切れそうなタイミングで差し込む回復剤」として機能させる。
多すぎると記事が軽くなるため、**1セクションにつき1箇所まで**を厳守する。

効果的なタイミング：
- **冒頭の問いかけ**: 「あなたもこれで1日溶かしたことはないか？」
- **複雑な図・表の直前**: 「少し込み入った話になるので、コーヒーを用意してほしい」
- **ハマりポイントの体験談**: 「筆者はここで丸2日を溶かした。お互い気をつけよう」
- **まとめの締め**: 「ここまで読んでくれた方は、もうその技術の9割を理解している」

やってはいけないユーモア：
- 読者を馬鹿にするような表現
- 長すぎる余談（3行以内に収める）
- 本題と無関係なジョーク

### ルール4：「テーマの主役」を冒頭で30秒以内に紹介する

読者がURLを踏んで最初に思う疑問は「で、それ何？」だ。
記事の最初のセクションで、テーマの主役を**一言定義＋日常の例え＋できることの一覧**で紹介する。

```
## ○○とは何か——エレベーターの中で説明できる定義

（一言定義）
OpenClawは「AIアシスタントをチャットツールに乗せるための土台」だ。

（日常の例え）
家で言えば「基礎工事」に相当する。壁紙や家具（＝機能）は後から自由に変えられるが、
基礎がしっかりしていないと何を乗せても不安定になる。

（できること）
具体的には、SlackやDiscordへのBot接続、社内ドキュメントとの連携、
承認フローの組み込みといった「AIアシスタントを業務で使うための配管工事一式」を担う。
```

### ルール5：「なぜそうなのか」を1段深く掘る

表面的な説明で止まらず、必ず「なぜその設計なのか」「どんな問題を解決するためか」を1段深く掘る。

```
# 浅い説明（NG）
WebAssemblyは静的型付けを採用しているため、高速に動作する。

# 1段深い説明（OK）
WebAssemblyが速い理由は「静的型付け」にある——と言われても、
最初はピンとこないかもしれない。

JavaScriptは「変数の型を実行しながら推測する」言語だ。
これは柔軟で書きやすい反面、ブラウザが毎回「これは数字か？文字か？」と
確認しながら動かなければならないことを意味する。

WebAssemblyは逆で、コンパイル時点で型が確定している。
ブラウザは「これはi32（32ビット整数）だ」とわかった状態で実行できるため、
型の推測に使う時間がまるごとゼロになる。これが速度差の正体だ。
```

## ワークフロー

### Step 1: テーマ分析と調査設計

1. **テーマの主役を定義する**
   - 「一言で言うと何か」を確認する。言えない場合は調査の最初のタスクにする
   - 「日常の何に例えられるか」を考える

2. **読者像と動機を具体的に想定する**
   - 職種・経験年数・直面している問題を想像する
   - 「この記事を読み終えた読者がどんな状態になってほしいか」をゴールとして設定する

3. **標準セクションの選定**
   - **活用事例・ハマりポイント・取り込み方の3つは原則必須**

4. **調査設計**
   - 調べるべき論点を列挙する
   - 4段階調査プロセスのどの観点が使えるかを確認する

---

### Step 2: 4段階調査プロセス

`web_search`・`web_fetch`・公式ドキュメントを組み合わせて実施する。

#### ① 境界条件のテスト（「もし〜なら」を試す）
- **極小化**: 最低スペック・最小構成でも動作するか？
- **オフライン化**: 外部API・クラウドなしでローカルだけで完結するか？
- **干渉**: 他プロセスと同時稼働したとき競合が起きるか？

#### ② 比較と歴史的背景（「なぜこれか」を問う）
- 代替技術との比較：メモリ消費・レイテンシ・自由度・運用コスト等の軸で
- 系譜を辿る：思想的ルーツ・先行技術・失敗した前身

#### ③ 一次情報への越境
- 公式ドキュメントの「Caveats」「Known Issues」「Advanced Configuration」まで読む
- OSSならエラーの核心箇所のソースを直接確認する
- 仕様書・RFC・プロポーザルで設計判断の理由を確認する

#### ④ 応用の自動化・仕組み化
- スクリプト化できるか？
- 別環境（iPad・ラズパイ・CI/CD等）でも再現できるか？

**調査の原則:**
- 最低 **5件以上** の異なるソースから情報収集する
- 数値・バージョン・固有名詞は原典を確認する
- 古い情報・非推奨情報は除外または注釈する

**ソース優先順位:**
1. 公式ドキュメント・仕様書・RFC
2. 査読済み論文・arXiv
3. GitHubリポジトリ・コミットログ・リリースノート
4. 著名エンジニア・開発者の技術ブログ・発表資料
5. 大手技術メディア（Zenn・Qiita・The Morning Paper 等）

---

### Step 3: タイトルの設計

**ルール1：【ベネフィット】＋【具体的な制約・環境】**
- NG: 「iPad Safariを最強にする」
- OK: 「iPad SafariにAIボタンを実装して、YouTube視聴を爆速化する」

**ルール2：コストや効率を「数字」で示す**
- NG: 「API代を節約する方法」
- OK: 「月額$20の課金を回避し、ローカル環境だけでAIエージェントを構築する手順」

**ルール3：既存の「当たり前」に疑問を投げかける**
- 例: 「なぜ今のIoTはクラウドに頼りすぎるのか？ ローカルプロトコルで見直すスマート家電の寿命」

**ルール4：結論を「動詞」で始める（解決型）**
- NG: 「GASのeval対策」
- OK: 「Google Apps Scriptの安全性を確保する：evalを使わない動的実行の実装パターン」

タイトル候補を2〜3案生成し、最も刺さるものを採用する。

---

### Step 4: 記事構成の設計

```
# [タイトル]

> リード文：具体的なゴールを一文で宣言する。
> NG:「業務効率が上がります」
> OK:「FAQ対応の一次回答を自動化し、担当者の返信待ち時間を4時間→15分にする方法がわかります」

## [テーマの主役の紹介]（必須・冒頭に配置）
→ 一言定義＋日常の例え＋できることの一覧

## 動機
→ 読者の「あるある」な悩みから入る。「あなたもこれで困ったことはないか？」

## 仮説
→ 「もしかして〇〇でいけるのでは？」という問いを立てる

## 検証
→ 一次情報・コード・SVG図・比較テーブルを交えて論証する
→ 「なぜそうなのか」を1段深く掘る

## 結果
→ 数値・挙動・限界値。「動いた」だけでなく「どこまで動くか」まで

## 考察
→ 独自の知見。「本来の仕様とは違うが、こう使えば効率的だ」

## [標準セクション群から選んで配置]

## まとめ
→ 締めは「これを読んだあなたは〇〇ができる」という宣言で終わる

## 参考文献
```

### Step 4.5: 標準セクション群

**活用事例・ハマりポイント・取り込み方の3つは原則必須。**
各セクションは必ず散文（本文）で始め、箇条書きだけで構成しない。

#### 📌 注目ポイント
核心を3〜5点に絞って提示する。「なぜそれが重要か」まで掘り下げる。

#### 💡 活用事例
実際にどこで・どう使われているかを物語として語る。
事例は「その人がどんな問題を抱えていたか→どう解決されたか」のストーリー構造で書く。
実企業・OSSの事例を1件以上含め、数値（削減率・処理時間等）で効果を示す。

#### ✅ 要点まとめ
記事を読み終えた読者が「何を覚えて帰るか」を3〜7点で再圧縮する。
本文のコピペではなく、エッセンスを別の言い方で表現する。

#### 🚀 取り込み方（導入ステップ）
「明日から使うには何をすればいいか」を段階的に示す。
- **今日（5分でできること）**: インストール・チュートリアル実行等の最小アクション
- **今週**: 小さなプロジェクトで実際に試す
- **今月**: 本番・業務フローへの組み込みと評価
各ステップに具体的なコマンドかリンクを添える。

#### 🔥 ハマりポイント（落とし穴と回避策）
「〜と思いがちだが、実は〜」という構造で書く。
症状 → 原因 → 対処法 の三点セット形式を基本とする。
「筆者も〇〇で詰まった」という一人称の体験を入れると読者の共感を得やすい。

#### 🔄 代替技術との比較
比較軸をHTMLテーブルで示し、「◯◯の方が向いているケース」も正直に書く。

#### 📅 今後の展望
標準化・バージョンアップの動向を一次情報から引用し、「今採用する価値があるか」に答える。

### Step 5: 記事執筆

#### 執筆品質チェックリスト（書き終えたら全項目を確認する）

- [ ] 本文が1500文字以上か（コードブロック・参考文献を除く）
- [ ] テーマの主役が冒頭で「一言定義＋日常の例え」で紹介されているか
- [ ] 見出し直下に必ず散文があるか（箇条書き直置きは禁止）
- [ ] 技術概念に「日常の例え話」が付いているか
- [ ] 専門用語の初出に補足が付いているか
- [ ] 複雑な構造・フローにSVG図かHTMLテーブルがあるか
- [ ] ユーモア・体験談が各セクションに自然に入っているか
- [ ] 参考文献が5件以上あるか
- [ ] 「今日から使うには」という具体的なアクションが書かれているか
- [ ] 「なぜそうなのか」を1段深く掘り下げているか

#### 専門用語の補足ルール

専門用語が初めて登場した箇所には必ず補足を入れる。

```
## パターンA：括弧で一言＋例え（最も多く使う）
JITコンパイル（実行しながら必要な部分だけ機械語に翻訳する技術——
全部を事前翻訳するより起動が早い、通訳の即興スタイルに近い）が高速化の鍵だ。

## パターンB：文中で自然に説明する
WebAssemblyはバイナリ形式、つまり人間が読む文字ではなく
機械が直接処理できる0と1の塊として配布される。
だからブラウザは「翻訳」をすっ飛ばしてそのまま実行できる。

## パターンC：脚注（長い説明が必要な場合）
WASI[^1]の登場でブラウザ外での活用が加速した。
[^1]: **WASI（WebAssembly System Interface）**: WasmがOS上でファイルやネットワーク等の
      システムリソースを扱うための標準インタフェース。POSIXに着想を得ている。
```

#### 図表のルール

**HTMLテーブル（必須・Markdownパイプ記法は禁止）:**
すべてのテーブルはHTMLタグで書く。

```html
<table>
  <thead>
    <tr>
      <th>技術</th>
      <th>起動速度</th>
      <th>メモリ消費</th>
      <th>向いているケース</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>Docker</td>
      <td>数百ms〜秒</td>
      <td>数百MB〜GB</td>
      <td>汎用サーバーサイド・既存アプリの移行</td>
    </tr>
    <tr>
      <td>Wasm</td>
      <td>マイクロ秒</td>
      <td>数KB〜MB</td>
      <td>エッジ・サーバーレス・プラグインシステム</td>
    </tr>
  </tbody>
</table>
```

**その他のルール:**

## 注意事項

- 調査なしに記事を書き始めないこと（必ずStep 2を実施する）
- 存在しないライブラリ・APIの仕様・数値を作らない（ハルシネーション禁止）
- 意見・推測には「〜と考えられる」「〜とされている」等の表現を用いて事実と区別する
- テーマが広すぎる場合はユーザーに確認してスコープを絞る
- コード例を含む場合は動作確認済みのものを優先する（不明な場合は注釈する）
- 「ただ動いた」で終わらず、境界条件・比較・再現性の観点を必ず記事に含める
- 専門用語の補足を省略しない
- 図を「あとで入れよう」と先送りにしない
- 「友人のエンジニアが居酒屋で熱く語ってくれる温度感」を常に意識する
