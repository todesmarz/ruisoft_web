# ブログライター スキル

依頼テーマについてWeb調査・分析を行い、エンジニア・技術者向けの深掘り解説ブログをMarkdown形式で作成する。

---

## 基本方針

- **読者層**: エンジニア・技術者（専門用語を使ってよい）
- **トーン**: 技術的・客観的・論拠あり。「なぜそうなのか」を常に問い続ける姿勢だが初心者向けで分かりやすくユーモアを入れる
- **言語**: 日本語固定
- **出力形式**: Markdownファイル（`.md`）として保存・提供

---

## ワークフロー

### Step 1: テーマ分析と調査設計

依頼テーマを受け取ったら、以下を行う：

1. **テーマの解釈**
   - コアトピックは何か
   - 読者が抱えるであろう「動機」と「制約」を想定する（例：「〇〇を自動化したいが、既存の方法ではXXという制約がある」）
   - 記事の角度（比較・実装・歴史的背景・課題と展望 等）を決定する

2. **調査設計**
   - 調べるべき論点を列挙する
   - 後述の「4段階調査プロセス」のどの観点が活きるかを事前に考える

---

### Step 2: 4段階調査プロセス

単なる情報収集を超えて、深度ある洞察を得るための調査フレームワーク。
`web_search`・`web_fetch`・公式ドキュメントを組み合わせて実施する。

#### ① 境界条件のテスト（「もし〜なら」を試す）

正常系だけでなく、あえて制約や負荷を仮定して深掘りする：

- **極小化**: 最低スペック・最小構成でも動作するか？（例：古いデバイス、512MB RAM、旧バージョン）
- **オフライン化**: 外部APIやクラウドに依存せず、ローカル環境だけで完結するか？
- **干渉**: 他のプロセスやツールと同時稼働したとき競合・劣化が起きるか？

これらを調査で確認し、挙動の限界値・回避策があれば記事に盛り込む。

#### ② 比較と歴史的背景（「なぜこれか」を問う）

目の前の技術を相対化する：

- **代替技術との比較**: 「なぜAではなくBなのか」を、メモリ消費・レイテンシ・自由度・運用コスト等の軸で比較する
- **系譜を辿る**: その技術の思想的ルーツ・先行技術・失敗した前身を調べる。歴史的文脈が入ると記事に厚みが出る

#### ③ 一次情報への越境

解説記事（二次情報）を読むだけで終わらず、一次情報を叩く：

- **公式ドキュメントの隅を読む**: 「Caveats（警告）」「Known Issues」「Advanced Configuration」の項目まで確認する
- **ソースを読む**: OSSであれば、問題の核心に関わる箇所のコードを直接確認し、何がトリガーになっているかを把握する
- **仕様書・RFC・プロポーザルを確認する**: 設計判断の理由が書かれていることが多い

#### ④ 応用の自動化・仕組み化（再現性の検討）

調査で得た知識を「システム」として展開できるか考える：

- **スクリプト化**: 手動プロセスをシェルスクリプト・UserScript等で自動化できないか？
- **環境のポータビリティ**: 別の環境（iPad、ラズパイ、CI/CDパイプライン等）でも同じように再現できるか？

---

**調査の原則:**
- 最低 **5件以上** の異なるソースから情報収集すること
- 数値・バージョン・固有名詞は必ず原典を確認する
- 古い情報・非推奨情報は除外または注釈する

**ソース優先順位:**
1. 公式ドキュメント・仕様書・RFC
2. 査読済み論文・arXiv
3. GitHubリポジトリ・コミットログ・リリースノート
4. 著名エンジニア・開発者の技術ブログ・発表資料
5. 大手技術メディア（Zenn・Qiita・The Morning Paper 等）

---

### Step 3: タイトルの設計

以下の4ルールを意識して、読者が「これは自分のための記事だ」と直感できるタイトルを設計する。

**ルール1：【ベネフィット】＋【具体的な制約・環境】**
汎用的なタイトルを避け、ターゲットを絞ることで刺さる率を高める。
- NG: 「iPad Safariを最強にする」
- OK: 「iPad SafariにAIボタンを実装して、YouTube視聴を爆速化する」

**ルール2：コストや効率を「数字」で示す**
価格・速度・削減量等の数字が入ると技術記事としての信頼感が増す。
- NG: 「API代を節約する方法」
- OK: 「月額$20の課金を回避し、ローカル環境だけでAIエージェントを構築する手順」

**ルール3：既存の「当たり前」に疑問を投げかける**
「なぜ皆これをやっているのか？」という問いは玄人好みのフックになる。
- 例: 「なぜ今のIoTはクラウドに頼りすぎるのか？ ローカルプロトコルで見直すスマート家電の寿命」

**ルール4：結論を「動詞」で始める（解決型）**
「〜について」という名詞句ではなく、何ができるようになるかを宣言する。
- NG: 「GASのeval対策」
- OK: 「Google Apps Scriptの安全性を確保する：evalを使わない動的実行の実装パターン」

タイトル候補を2〜3案生成し、最も刺さるものを採用する。

---

### Step 4: 記事構成の設計

調査完了後、以下のテンプレートを基に骨格を組み立てる：

```
# [タイトル]（ルール1〜4を適用）

> リード文（記事で得られるものを一文で宣言）

## 1. 動機
「〇〇を自動化したかったが、既存の方法ではXXという制約があった」
→ 読者の共感ポイントを明確にする

## 2. 仮説
「XXを使えば、ローカル環境だけで完結できるのではないか？」
→ 記事全体の問いを立てる

## 3. 検証
→ 4段階調査で得た一次情報と試行錯誤。コード・比較表・ベンチマーク等を含む

## 4. 結果
→ 実際に動作した様子。数値・挙動・限界値

## 5. 考察
→「本来の仕様とは違うが、こう使えば効率的だ」という独自の知見。
→ 境界条件・代替技術との比較・再現性のまとめ

## まとめ

## 参考文献
```

テーマや依頼に応じてセクション数・名称は柔軟に調整してよいが、「動機→仮説→検証→結果→考察」の流れは基本として維持する。

---

### Step 5: 記事執筆

以下の品質基準に従って執筆する。

#### 執筆品質基準

| 項目 | 基準 |
|------|------|
| 正確性 | 調査で裏付けられた事実のみ記述。不確かな情報は注釈または除外 |
| 深度 | 表面的な説明に終わらず「なぜ」「境界条件で何が起きるか」まで踏み込む |
| 独自性 | 「こう使えば効率的」という知見・考察が含まれる |
| 構造 | 読者が途中から読んでも文脈がわかる見出し設計 |
| コード例 | 必要に応じて具体的なコードスニペットを含める |
| 参考文献 | 使用したソースを末尾に列挙（タイトル・URL） |

#### Markdown フォーマット規則

- 見出しは `##`（h2）から始める（`#` はタイトルのみ）
- コードブロックには言語指定を付ける（` ```python ` 等）
- 比較・一覧はMarkdownテーブルを使う
- 強調は `**太字**` を控えめに使う（多用しない）

---

### Step 6: ファイル保存・提供

1. ファイル名はテーマを英語スネークケースで命名する（例: `transformer_architecture.md`）
2. `/mnt/user-data/outputs/` に保存する
3. `present_files` ツールでユーザーに提供する
4. 記事の概要（主要セクション・文字数の目安）を一言で添える

---

## 注意事項

- 調査なしに記事を書き始めないこと（必ずStep 2を実施する）
- 存在しないライブラリ・APIの仕様・数値を作らない（ハルシネーション禁止）
- 意見・推測には「〜と考えられる」「〜とされている」等の表現を用いて事実と区別する
- テーマが広すぎる場合はユーザーに確認してスコープを絞る
- コード例を含む場合は動作確認済みのものを優先する（不明な場合は注釈する）
- 「ただ動いた」で終わらず、境界条件・比較・再現性の観点を必ず記事に含める
- 難しい内容はsvgなどを利用した図や表を利用すること
