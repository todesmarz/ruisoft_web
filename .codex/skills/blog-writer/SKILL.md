# ブログライター スキル

依頼テーマについてWeb調査・分析を行い、技術者向けの深掘り解説ブログをMarkdown形式で作成する。

---

## 基本方針

- **読者層**: エンジニア・技術者を主対象としつつ、初心者が読んでも置いてけぼりにならない配慮をする
- **トーン**: 技術的・客観的・論拠あり。「なぜそうなのか」を常に問い続ける姿勢。ただし説教くさくならず、適度なユーモアと親しみやすさを添える（難しい概念ほど例え話や軽いジョークを挟む）
- **言語**: 日本語固定
- **文量**: 本文 **1000文字以上**（参考文献・コードブロックは除く）。薄い記事は読者の時間を無駄にする
- **出力形式**: Markdownファイル（`.md`）として保存・提供

---

## ワークフロー

### Step 1: テーマ分析と調査設計

依頼テーマを受け取ったら、以下を行う：

1. **テーマの解釈**
   - コアトピックは何か
   - 読者が抱えるであろう「動機」と「制約」を想定する（例：「〇〇を自動化したいが、既存の方法ではXXという制約がある」）
   - 記事の角度（比較・実装・歴史的背景・課題と展望 等）を決定する

2. **標準セクションの確認**
   - 後述の「標準記事セクション」のうち、テーマに応じてどれを含めるかを決定する
   - すべてを入れる必要はないが、**活用事例・ハマりポイント・取り込み方**の3つは原則として含める

3. **調査設計**
   - 調べるべき論点を列挙する
   - 後述の「4段階調査プロセス」のどの観点が活きるかを事前に考える

---

### Step 2: 4段階調査プロセス

単なる情報収集を超えて、深度ある洞察を得るための調査フレームワーク。
`web_search`・`web_fetch`・公式ドキュメントを組み合わせて実施する。

#### ① 境界条件のテスト（「もし〜なら」を試す）

正常系だけでなく、あえて制約や負荷を仮定して深掘りする：

- **極小化**: 最低スペック・最小構成でも動作するか？（例：古いデバイス、512MB RAM、旧バージョン）
- **オフライン化**: 外部APIやクラウドに依存せず、ローカル環境だけで完結するか？
- **干渉**: 他のプロセスやツールと同時稼働したとき競合・劣化が起きるか？

これらを調査で確認し、挙動の限界値・回避策があれば記事に盛り込む。

#### ② 比較と歴史的背景（「なぜこれか」を問う）

目の前の技術を相対化する：

- **代替技術との比較**: 「なぜAではなくBなのか」を、メモリ消費・レイテンシ・自由度・運用コスト等の軸で比較する
- **系譜を辿る**: その技術の思想的ルーツ・先行技術・失敗した前身を調べる。歴史的文脈が入ると記事に厚みが出る

#### ③ 一次情報への越境

解説記事（二次情報）を読むだけで終わらず、一次情報を叩く：

- **公式ドキュメントの隅を読む**: 「Caveats（警告）」「Known Issues」「Advanced Configuration」の項目まで確認する
- **ソースを読む**: OSSであれば、問題の核心に関わる箇所のコードを直接確認し、何がトリガーになっているかを把握する
- **仕様書・RFC・プロポーザルを確認する**: 設計判断の理由が書かれていることが多い

#### ④ 応用の自動化・仕組み化（再現性の検討）

調査で得た知識を「システム」として展開できるか考える：

- **スクリプト化**: 手動プロセスをシェルスクリプト・UserScript等で自動化できないか？
- **環境のポータビリティ**: 別の環境（iPad、ラズパイ、CI/CDパイプライン等）でも同じように再現できるか？

---

**調査の原則:**
- 最低 **5件以上** の異なるソースから情報収集すること
- 数値・バージョン・固有名詞は必ず原典を確認する
- 古い情報・非推奨情報は除外または注釈する

**ソース優先順位:**
1. 公式ドキュメント・仕様書・RFC
2. 査読済み論文・arXiv
3. GitHubリポジトリ・コミットログ・リリースノート
4. 著名エンジニア・開発者の技術ブログ・発表資料
5. 大手技術メディア（Zenn・Qiita・The Morning Paper 等）

---

### Step 3: タイトルの設計

以下の4ルールを意識して、読者が「これは自分のための記事だ」と直感できるタイトルを設計する。

**ルール1：【ベネフィット】＋【具体的な制約・環境】**
汎用的なタイトルを避け、ターゲットを絞ることで刺さる率を高める。
- NG: 「iPad Safariを最強にする」
- OK: 「iPad SafariにAIボタンを実装して、YouTube視聴を爆速化する」

**ルール2：コストや効率を「数字」で示す**
価格・速度・削減量等の数字が入ると技術記事としての信頼感が増す。
- NG: 「API代を節約する方法」
- OK: 「月額$20の課金を回避し、ローカル環境だけでAIエージェントを構築する手順」

**ルール3：既存の「当たり前」に疑問を投げかける**
「なぜ皆これをやっているのか？」という問いは玄人好みのフックになる。
- 例: 「なぜ今のIoTはクラウドに頼りすぎるのか？ ローカルプロトコルで見直すスマート家電の寿命」

**ルール4：結論を「動詞」で始める（解決型）**
「〜について」という名詞句ではなく、何ができるようになるかを宣言する。
- NG: 「GASのeval対策」
- OK: 「Google Apps Scriptの安全性を確保する：evalを使わない動的実行の実装パターン」

タイトル候補を2〜3案生成し、最も刺さるものを採用する。

---

### Step 4: 記事構成の設計

調査完了後、以下のテンプレートを基に骨格を組み立てる。
「動機→仮説→検証→結果→考察」の流れを基本とし、後述の標準セクションを適切に配置する。

```
# [タイトル]（ルール1〜4を適用）

> リード文（記事で得られるものを一文で宣言）

## 1. 動機
「〇〇を自動化したかったが、既存の方法ではXXという制約があった」
→ 読者の共感ポイントを明確にする

## 2. 仮説
「XXを使えば、ローカル環境だけで完結できるのではないか？」
→ 記事全体の問いを立てる

## 3. 検証
→ 4段階調査で得た一次情報と試行錯誤。コード・図・比較表・ベンチマーク等を含む

## 4. 結果
→ 実際に動作した様子。数値・挙動・限界値

## 5. 考察
→「本来の仕様とは違うが、こう使えば効率的だ」という独自の知見。
→ 境界条件・代替技術との比較・再現性のまとめ

## [標準セクション群]（下記から適切なものを選んで配置）

## まとめ

## 参考文献
```

---

### Step 4.5: 標準セクション群

テーマに応じて以下のセクションを選んで記事に組み込む。
**活用事例・ハマりポイント・取り込み方の3つは原則必須**。それ以外はテーマの性質に応じて判断する。

#### 📌 注目ポイント
その技術・手法において「ここだけは押さえてほしい」という核心を3〜5点に絞って提示する。
- 単なる機能紹介ではなく「なぜそれが重要なのか」に踏み込む
- 見落とされがちだが実は重要な仕様・挙動を含める

#### 💡 活用事例
実際にどこで・どう使われているかを具体的に示す。
- 実企業・OSSプロジェクトの事例を1件以上含める
- 「自分ならこう使う」という応用アイデアも1〜2個添える
- 事例は「規模感」「効果」を数値で示せるとなお良い

#### ✅ 要点まとめ（ポイントの整理）
記事を読み終えた読者が「何を覚えて帰るか」を箇条書きで整理する。
- 3〜7点に絞る
- 本文の繰り返しではなく、エッセンスを再圧縮する

#### 🚀 取り込み方（導入ステップ）
「明日から使うには何をすればいいか」を段階的に示す。
- **ステップ1（今日）**: インストール・試すだけで済む最小アクション
- **ステップ2（今週）**: 小さなプロジェクトで実際に試す
- **ステップ3（今月）**: 本番・業務フローへの組み込みと評価
- 各ステップに具体的なコマンド・リンクがあると親切

#### 🔥 ハマりポイント（落とし穴と回避策）
調査・実装で実際に詰まりやすい箇所を正直に書く。
- 「〜と思いがちだが、実は〜」という形式で記述する
- エラーメッセージ・症状 → 原因 → 対処法 の三点セットで書く
- 公式ドキュメントのCaveats・Known Issuesから必ず引用する

#### 🔄 代替技術との比較
「なぜこれを選ぶか」を他の選択肢と比較して示す。
- 比較軸（パフォーマンス・学習コスト・運用負荷・コスト等）をテーブルで示す
- 「◯◯より優れている」だけでなく「◯◯の方が向いているケース」も書く

#### 📅 今後の展望
その技術の将来を現時点の情報から予測する。
- 標準化・バージョンアップの動向を一次情報から引用する
- 「今採用する価値があるか」という読者の問いに答える

---

### Step 5: 記事執筆

以下の品質基準に従って執筆する。

#### 執筆品質基準

| 項目 | 基準 |
|------|------|
| 文量 | 本文1000文字以上（コードブロック・参考文献を除く） |
| 正確性 | 調査で裏付けられた事実のみ記述。不確かな情報は注釈または除外 |
| 深度 | 表面的な説明に終わらず「なぜ」「境界条件で何が起きるか」まで踏み込む |
| 独自性 | 「こう使えば効率的」という知見・考察が含まれる |
| 初心者配慮 | 専門用語には初出時に必ず補足を付ける（後述のルール参照） |
| ユーモア | 難しい概念の前後に例え話・軽いジョークを挟み、読者の集中力をリセットする |
| 図表 | 複雑な構造・フロー・比較は図やテーブルで視覚化する（後述のルール参照） |
| 参考文献 | 使用したソースを末尾に列挙（タイトル・URL） |

---

#### 専門用語の補足ルール

専門用語が初めて登場した箇所には、必ず括弧書きで補足を入れる。

```markdown
# 補足の書き方パターン

## パターンA：括弧で一言添える（最も多く使う）
WebAssembly（ウェブブラウザやサーバー上で動くバイナリ形式の実行環境）は...

## パターンB：脚注スタイル（長い説明が必要な場合）
JIT コンパイル[^1] が高速化の鍵になっている。

[^1]: **JIT（Just-In-Time）コンパイル**: プログラムの実行中に、よく使われるコードだけを
      機械語に変換して高速化する技術。「必要なときだけ翻訳する」通訳のようなイメージ。

## パターンC：ユーモアを交えた補足（難解な概念向け）
スタックマシン（皿洗い機のように「最後に積んだものから先に処理する」仕組みの仮想CPU）で動く...
```

**補足が必要な用語の目安:**
- 一般的なIT用語より専門性が高いもの（例：RFC、WASI、リニアメモリ）
- 略語・頭字語（例：JIT、AOT、OPA）
- 業界内でも解釈がブレやすい概念（例：「サンドボックス」）

**補足が不要な用語の目安:**
- 一般的なプログラミング用語（関数、変数、ループ等）
- 記事のテーマが前提とする基礎知識（技術特化記事なら対象領域の基本概念）

#### 図表のルール

複雑な構造・処理フロー・比較は必ず視覚化する。
表はmarkdown形式ではなくhtmlタグで表現すること

**テーブルを使うケース:**
- 技術の比較（3つ以上の選択肢・3つ以上の評価軸）
- ステップごとの対応表
- エラーと対処法の一覧

```markdown
| 技術 | 起動速度 | メモリ消費 | 学習コスト |
|------|---------|-----------|-----------|
| Docker | 数百ms | 数百MB〜 | 中 |
| Wasm | マイクロ秒 | 数KB〜MB | 高（現状） |
```

**SVG図を使うケース（必須）:**
処理フロー・アーキテクチャ図・概念の関係図など、テーブルでは表現しきれない構造は
SVGをMarkdown内に直接埋め込んで視覚化する。

```markdown

  <text x="80" y="100" text-anchor="middle" font-size="13" fill="#1a1a1a">Rust / C++</text>
  <text x="80" y="118" text-anchor="middle" font-size="11" fill="#555">ソースコード</text>

  <!-- 矢印 -->
  <line x1="140" y1="100" x2="195" y2="100" stroke="#666" stroke-width="2" marker-end="url(#arr)"/>
  <text x="167" y="92" text-anchor="middle" font-size="10" fill="#666">コンパイル</text>

  <rect x="200" y="70" width="120" height="60" rx="8" fill="#fff3e0" stroke="#FF9800" stroke-width="2"/>

```

SVGを使う判断基準：
- 「A → B → C」のような順序・フローがある
- 複数のコンポーネントの関係・階層を示したい
- テーブルだと「→」や「包含」の関係が伝わらない

SVG作成の注意：
- `viewBox` を設定し、`style="max-width:100%"` を入れてレスポンシブにする
- 色は落ち着いたパステル系（背景）＋明確なボーダー色（枠線）で統一する
- フォントサイズは12〜14px基準。日本語テキストは `font-family:sans-serif` を指定する
- 複雑すぎるSVGは分割して複数枚にする

---

#### Markdown フォーマット規則

- 見出しは `##`（h2）から始める（`#` はタイトルのみ）
- コードブロックには言語指定を付ける（` ```python ` 等）
- 強調は `**太字**` を控えめに使う（多用しない）
- セクションの冒頭に絵文字アイコン（📌💡✅🚀🔥🔄📅）を付けて視認性を上げる

---

### Step 6: ファイル保存・提供

1. ファイル名はテーマを英語スネークケースで命名する（例: `transformer_architecture.md`）
2. `/mnt/user-data/outputs/` に保存する
3. `present_files` ツールでユーザーに提供する
4. 記事の概要（文字数・含まれるセクション）を一言で添える

---

## 注意事項

- 調査なしに記事を書き始めないこと（必ずStep 2を実施する）
- 存在しないライブラリ・APIの仕様・数値を作らない（ハルシネーション禁止）
- 意見・推測には「〜と考えられる」「〜とされている」等の表現を用いて事実と区別する
- テーマが広すぎる場合はユーザーに確認してスコープを絞る
- コード例を含む場合は動作確認済みのものを優先する（不明な場合は注釈する）
- 「ただ動いた」で終わらず、境界条件・比較・再現性の観点を必ず記事に含める
- 専門用語の補足を省略しない。「読者は知っているだろう」という思い込みは記事の敵
- 図を「あとで入れよう」と先送りにしない。フローや構造が出てきたタイミングで即座にSVGを書く
