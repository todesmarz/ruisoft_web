# MySQLよりPostgreSQLが選ばれやすくなってきた要因（2026時点）

## 1. 結論（答え）
MySQLからPostgreSQLへ選定が寄る主因は、**「標準SQLへの忠実さ」「複雑な要件への拡張性」「クラウド/OSSエコシステムとの相性」**です。特に新規開発では、将来の機能追加や分析要件を見据えてPostgreSQLを先に選ぶケースが増えています。

## 2. 課題（読者の悩み）
- なぜ最近は「とりあえずPostgreSQL」が増えたのか
- MySQLで困っているわけではないのに、なぜ移行議論が起きるのか
- どの条件ならMySQL継続が合理的で、どの条件ならPostgreSQLが有利か

## 3. 解決方法（判断手順）
以下の手順で選定すると、感覚ではなく再現可能な判断になります。

1. **要件を分類**する（OLTP中心 / 分析混在 / 地理情報 / 全文検索 / JSON活用）。
2. 各要件に対して、次の観点で点数化する（1〜5点）。
   - SQL機能（CTE, Window関数, 複雑JOIN）
   - 型と制約（JSONB, ARRAY, DOMAIN, CHECK）
   - 拡張性（拡張モジュール、将来の機能余地）
   - 運用性（監視、バックアップ、レプリケーション）
   - チーム習熟度（既存ノウハウ）
3. 合計点が高い方を一次候補にする。
4. 最後にPoCで以下を比較する。
   - 実クエリのp95レイテンシ
   - 障害復旧手順の所要時間
   - スキーマ変更時の作業難易度

## 4. 理由（なぜそうなるか）
### 4-1. SQL/トランザクション設計の自由度
PostgreSQLは標準SQLに忠実で、複雑クエリや制約設計がしやすく、**アプリ側にロジックを逃がさなくて済む**場面が多い。

### 4-2. 型システムと拡張性
JSONB、配列、カスタム型、拡張モジュール（例: PostGIS）により、単一DBで扱える要件が広い。

### 4-3. クラウド時代の「可搬性」重視
マネージドPostgreSQLが主要クラウドで充実し、ベンダー依存を抑えて運用しやすい。SaaS/OSS側の先行サポートもPostgreSQL中心になりやすい。

### 4-4. 開発組織の意思決定変化
「最初は単純でも、将来の要件増に耐える設計」を重視するチームが増え、初期の選定でPostgreSQLに寄る。

## 5. 補足（注意点・応用）
- **MySQLが不利という話ではない**。読み取り中心・既存資産が厚い・運用ノウハウが揃っているならMySQL継続は合理的。
- 移行時は以下を先に確認する。
  - 照合順序/文字コード差異
  - `AUTO_INCREMENT` と `SEQUENCE/IDENTITY` の差
  - UPSERT構文差
  - トランザクション分離レベルとロック挙動
- 「新規はPostgreSQL、既存はMySQL維持」のハイブリッド戦略も現実的。

## 6. まとめ
- PostgreSQL優位の背景は、**高機能化したアプリ要件**と**将来拡張への備え**。
- ただし正解はワークロード依存で、既存運用資産が強いならMySQL継続が最適な場合も多い。
- 感覚ではなく、要件点数化 + PoC計測で決めると失敗しにくい。
