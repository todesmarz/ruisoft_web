# マルチエージェント・ハーネスをいつ使うか：判断基準の完全ガイド

> 「とりあえずマルチエージェントにすれば賢くなる」は誤解だ。構成を複雑にするほど、デバッグコスト・レイテンシ・費用は跳ね上がる。**何のために使うのか**を明確にしてから選べ。

---

## はじめに

Claude Code や各種エージェントフレームワークの普及により、「エージェントを使えば何でも解決する」という空気が出てきた。しかし実際に運用してみると、**シングルエージェント + 適切なプロンプトで十分だったケースが大半**だったという経験は少なくない。

本稿では以下の3つの問いに答える。

1. **マルチエージェントはどんな問題を解くか**——そしてどう判断するか
2. **ハーネスはどんな問題を解くか**——そしていつ必要になるか
3. **シングル → マルチ → ハーネスへの移行基準**——段階的に判断する方法

---

## 1. まず「シングルエージェント」で考える

マルチエージェントやハーネスを検討する前に、**シングルエージェントで解けるか**を先に問え。

シングルエージェントで十分な条件：

- タスクが一人の「賢い人間」が順番にこなせる範囲に収まる
- ツール呼び出しが5〜10回以内で完結する
- 中間結果を別エージェントに渡す必要がない
- リアルタイム性は不要（数秒〜数十秒の応答で許容される）

**判断の原則**：複雑さを追加するコストは常にある。追加する前に「シングルで無理な理由」を明確に言語化できるか確認する。

---

## 2. マルチエージェントを使う判断基準

### 2.1 並列化できる独立タスクがある

**これが最も正当なユースケースだ。**

単一エージェントは逐次実行が基本だ。複数の独立した調査・処理を直列にこなすと、待ち時間が単純に積み上がる。

```
悪い例（直列）:
  エージェント → [ニュース取得 3s] → [DB検索 2s] → [競合調査 4s] → 合計9s

良い例（並列マルチエージェント）:
  オーケストレーター
    ├── エージェントA: ニュース取得 (3s)
    ├── エージェントB: DB検索 (2s)
    └── エージェントC: 競合調査 (4s)
  → 合計4s（最長タスクで律速）
```

**判断チェック**: 「このタスク群に順序依存はあるか？」——YESなら並列化は難しい。NOなら並列化の恩恵が大きい。

---

### 2.2 コンテキストウィンドウを保護したい

大規模なコード探索・ドキュメント解析・Web検索などを1つのエージェントに全部やらせると、コンテキストが汚染され、後半の推論品質が落ちる。

マルチエージェントにすると：

- サブエージェントが大量の検索結果を処理して**要約だけ**を返す
- メインエージェントは「要約済みの情報」しか見ない
- コンテキストがクリーンに保たれ、推論精度が維持される

**判断チェック**: 「このタスクでコンテキストが2〜3万トークンを超えそうか？」——YESなら分離を検討する。

---

### 2.3 専門分業が必要なタスク構造

異なる役割・スキルセットが求められるタスクは、単一プロンプトで両立させるより専門エージェントに分けた方が品質が上がる。

```
例：ブログ記事生成パイプライン

  リサーチャー（情報収集）
       ↓
  ライター（構成・執筆）
       ↓
  エディター（品質チェック・修正提案）
       ↓
  パブリッシャー（フォーマット変換・投稿）
```

各エージェントは自分の役割に特化したシステムプロンプトを持ち、前段の出力を受け取るだけでよい。

**判断チェック**: 「このプロンプトに複数の"帽子"を被せているか？」——YESなら専門分業を検討する。

---

### 2.4 マルチエージェントを**使わない**方が良いケース

| 状況 | 理由 |
|------|------|
| タスクが小さい（ツール1〜3回） | オーバーヘッドの方が大きい |
| エージェント間に強い依存関係がある | 並列化の恩恵がなく、デバッグが複雑になる |
| レイテンシが厳しい（<1秒要求） | エージェント間通信がボトルネックになる |
| デバッグ能力が低い段階 | 問題の所在が見えにくくなる |

---

## 3. ハーネスを使う判断基準

ハーネスとは「エージェントを動かすための外側の仕組み」だ。スケジューリング・状態管理・ポリシー適用・監視などを担う。

### 3.1 自動化・繰り返し動作が必要

**最も典型的なユースケース。**

「毎朝9時にニュースを収集してSlackに投稿する」「コミット前にLintを実行する」——これらはエージェントへの指示では実現できない。**ハーネスのSchedulerがトリガーする**必要がある。

```
判断の原則：
  「毎回〜する」「〜のたびに〜する」という要件 → ハーネスのhookで実装する
  Claude の「覚えておいて」では永続しない
```

---

### 3.2 タスクが長く、途中で失敗するリスクがある

数十ステップにわたる長大なタスクは、途中で失敗したとき「最初からやり直し」では困る。

ハーネスが提供するもの：

- **チェックポイント保存**: 各ステップの完了状態をState Storeに記録
- **再開（Resume）**: 失敗したステップから再実行
- **タイムアウト管理**: 無限ループの検出と強制終了

**判断チェック**: 「このタスクが途中で止まったとき、最初からやり直せるか？」——NOならハーネスの状態管理が必要だ。

---

### 3.3 複数エージェントの調整が必要

マルチエージェントを使うと決めたとき、誰がエージェントを起動し、結果を集約し、エラーを処理するかを管理する層が必要になる。それがハーネスのオーケストレーター機能だ。

```
ハーネスが管理すること:
  - サブエージェントの起動・終了
  - タイムアウトと再試行ポリシー
  - 結果の集約と次ステップへの受け渡し
  - 部分失敗時のロールバック（Sagaパターン）
```

---

### 3.4 ポリシー・コンプライアンスの強制

エージェントが「機密情報を外部APIに送ってはならない」「承認なしに本番DBを変更してはならない」といった制約を守るには、LLMへの指示だけでは不十分だ。

ハーネスがポリシーレイヤーとして：

- ツール呼び出し前に入力を検査する
- 違反を検出したら即時停止する
- 人手レビューキューに送る

**判断チェック**: 「このエージェントが間違った行動をとったとき、被害が許容範囲か？」——NOならポリシー制御のあるハーネスが必須だ。

---

### 3.5 ハーネスを**使わない**方が良いケース

| 状況 | 対応 |
|------|------|
| 1回限りのタスク | スクリプト or 直接CLI実行で十分 |
| ステートレスな処理 | ハーネスの状態管理は不要 |
| チームにSRE知見がない段階 | まずシングルエージェントで経験を積む |

---

## 4. 判断フローチャート

```
タスクがある
    ↓
シングルエージェントで解けるか？ → YES → シングルで実装（終了）
    ↓ NO
独立した並列タスクがあるか？ → YES → マルチエージェント（並列）
タスクが専門分業を要するか？ → YES → マルチエージェント（パイプライン）
    ↓ NO/BOTH
繰り返し・スケジュールが必要か？  → YES → ハーネス（Scheduler）
長大タスクで状態管理が必要か？    → YES → ハーネス（State Store）
ポリシー制御が必要か？             → YES → ハーネス（Policy Layer）
複数エージェントを調整するか？    → YES → ハーネス（Orchestrator）
    ↓ ALL NO
シングルエージェントで再検討（終了）
```

---

## 5. 段階的移行の原則

最初から「フル装備のハーネス + マルチエージェント」を作ろうとするのは避けるべきだ。複雑さは段階的に追加する。

### フェーズ1：シングルエージェントで動かす

- まずタスクが解けることを確認する
- ツールの種類と呼び出し回数を計測する
- コンテキスト使用量・レイテンシ・コストを記録する

### フェーズ2：ボトルネックを特定する

- 「並列化できれば速くなるか？」を計算する
- 「コンテキストが溢れているか？」をログで確認する
- 「失敗時のリカバリが辛いか？」を運用して確かめる

### フェーズ3：必要な機能だけ追加する

問題が確認できたら、解決策を最小単位で追加する。

| 確認された問題 | 最小の解決策 |
|----------------|--------------|
| 逐次実行が遅い | 該当タスクだけ並列サブエージェント化 |
| コンテキスト汚染 | 重い処理をサブエージェントに委譲 |
| 失敗時やり直しが辛い | State Store + チェックポイントを追加 |
| 毎回手動実行が必要 | Schedulerを追加 |

**原則：追加する前に「これがないと本当に困るか」を自問する。**
