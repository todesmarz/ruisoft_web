# エージェントハーネスを実装して運用品質を上げる：設計・監視・安全制御の実践ガイド

> LLMエージェントは「賢いモデル」だけでは本番で安定しません。本記事では、実装・運用・安全性まで含めたハーネス設計を、失敗パターンから逆算して解説します。

## 1. 動機
PoC段階ではうまく動くエージェントでも、本番では次の要因で簡単に不安定になります。

- 外部APIの遅延/失敗でワークフローがハングする
- ツール実行の副作用で再試行時に二重実行が起きる
- 権限境界が曖昧で、想定外の操作を許してしまう
- 失敗時のトレースが不足し、再現できない

特に2025–2026年の実装トレンドでは、単発回答ではなく「複数ツールをまたぐタスク実行」が主流になっており、**モデル品質より実行制御の設計差**が成果を左右します。

## 2. 仮説
エージェントを以下の5層に分離すれば、障害時の回復力・観測性・安全性を同時に引き上げられる。

1. **Planner**: 目標を実行可能ステップへ分解
2. **Tool Router**: ツール選択と引数検証
3. **Executor**: タイムアウト/リトライ/キャンセル制御
4. **State Store**: 中間状態・チェックポイントの永続化
5. **Policy Gate**: 権限評価、機密フィルタ、承認ワークフロー

## 3. 検証
### 3.1 最小構成と本番構成の差分

| 構成要素 | 最小構成（PoC） | 本番構成（Production） | 実務上のポイント |
|---|---|---|---|
| 実行制御 | 固定タイムアウト + 単純リトライ | 冪等キー + バックオフ + サーキットブレーカ | 「再試行で壊れない」設計を先に作る |
| 状態管理 | メモリ中心 | ステップ単位チェックポイント | 再開可能性（Durability）が運用品質を決める |
| 可観測性 | ログのみ | トレース + メトリクス + 相関ID | 失敗解析時間を短縮できる |
| 安全制御 | 手動レビュー | ツール別権限 + 承認必須操作 | 高リスク操作の自動防波堤 |
| 変更管理 | 一括デプロイ | Canary + 回帰評価 + ロールバック | モデル更新の事故を局所化 |

### 3.2 障害シナリオでの境界条件テスト

| シナリオ | 典型的な失敗 | 対策 |
|---|---|---|
| 外部API 429/5xx | リトライ嵐でコスト増 | 指数バックオフ + 上限回数 + キャッシュ |
| ツールタイムアウト | ステップが宙ぶらりん | ハートビート + 中断可能設計 |
| 部分成功後の再試行 | 二重課金/二重更新 | 冪等キー + 実行ログ照合 |
| 誤ったツール選択 | 予期しない副作用 | スキーマ検証 + allowlist |
| 機密データ流出 | 出力に秘密値混入 | 出力フィルタ + マスキング + 監査ログ |

### 3.3 実装で最初に置くべきイベント設計

後からUserScript/自動化で拡張しやすくするため、以下のイベントを統一命名で発火しておくと運用が楽になります。

```json
{
  "event": "agent.step.completed",
  "run_id": "r-20260408-001",
  "step_id": "tool_call_03",
  "tool": "search",
  "latency_ms": 842,
  "status": "success"
}
```

- `run_id` / `step_id` は必須
- `status` は `success|retry|failed|blocked`
- 監視とアラートは `event` を軸に集約

## 4. 結果
この設計を採用すると、次の効果が期待できます。

- 障害時に「どこから再開すべきか」を機械的に判断できる
- 失敗原因の追跡に必要な情報（入力・出力・ツール・時間）が揃う
- 高リスク操作の誤実行を事前に遮断できる
- モデル更新を段階展開できるため、品質劣化の影響範囲を限定できる

## 5. 考察
エージェント運用の難しさは、モデル推論ではなく**分散システム運用の難しさ**に近いです。したがって、次の観点を最初から設計に含めるべきです。

- **可観測性は後付け不可**：先に相関IDを全ステップへ通す
- **Policyはコードとして管理**：レビュー可能な設定にする
- **人手介入を前提化**：全自動前提より、承認ポイントを明示する

## まとめ
- エージェントハーネスは「安全装置付き実行基盤」として設計する。
- 本番品質は、再開可能性・可観測性・権限制御で決まる。
- 正常系デモではなく、失敗シナリオの設計・検証が最優先。
